# Activity log and patient privacy

The activity log, restriction, export, anonymisation and retention: read before any change that reads or changes patient data.

Roadmap step 7. What it records and why: `docs/governance/` (the data inventory, the DPIA and the rights procedure).
- **The activity log** (`ActivityEntry`, through `IActivityLog` in `MedApp.Application/Activity/Common`), separate from the pathway audit, records who read or changed patient data, sign-ins (refused ones too, with the account's ID when the username exists, and the two-factor step: see [Auth](auth.md)), sign-outs, account, role and specialty membership changes (`StaffSpecialtiesChanged`), and email, password reset and two-factor security events (`ISecurityEventLog`), with the request's address.
  - **Reads:** a handler returning a patient's data calls `RecordViewsAsync`: `PatientViewed` (the patient's page, timeline and its overview, a FHIR read), `PatientListed` for each patient in a list's results (patient and pathway search, retention review, a FHIR search), `PathwayViewed` (a pathway's page, a note deletion request's dialog, or `PatientViewed` once its pathway is deleted). The same view by the same person within `Activity:ViewWindowMinutes` (5) adds nothing.
  - **One item about a patient:** `RecordViewAsync(action, patientId, details)` records a view that its details name, deduplicated on the details too: opening a referral records `ReferralViewed` with `{referralId}`, once per person and referral over the window. The referral search records `PatientListed` for each patient shown ([Referrals](referrals.md)).
  - **Records nothing, on purpose:** the GP practice directory (`GET api/practices`, `…/{id}`: organisations and counts) and the user's own full name and job title (`GET api/auth/me/details`); the side nav's pin labels (`GET api/patients/labels`, `GET api/pathways/patient-pathways/labels`: at most 20 names and titles the user chose); the admin-only logs; insights (counts only); a user's own notifications; a calendar read `withoutAppointments`; the side nav's count of referrals awaiting triage (`GET api/referrals/awaiting-triage/count`). The deprecated `GET api/patients` records one `PatientsSearched` entry ("all"), so it's in no patient's access report.
  - **Files:** `AttachmentsViewed` and `AttachmentDownloaded` ([Attachments](attachments.md)). **A demographics (PDS) lookup:** `DemographicsLookedUp`, with whether anyone was found, never the NHS number.
  - **`EndpointCoverageTests`** (integration tests) lists every GET endpoint with what it records, and fails on any it doesn't know: classify a new one there.
  - **Referral changes** go in the referral's own history (`ReferralEvent`, through `ReferralChange`, in the same save), as pathway changes go in the pathway audit: not also in the activity log.
  - **Changes to a patient:** build the entry with `activityLog.Entry(...)` and pass it to the repository method (`AddAsync`, `UpdateAsync`, `DeleteAsync`, `IPatientRecordRepository.SaveAsync`), which saves both in one `SaveChangesAsync`, so no change can miss the log.
  - **Details never hold a patient's details or clinical text:** field names, never values (a patient's contact details are `addressLines`, `postcode`, `mobilePhone` and `practice`; a member of staff's `StaffDetailsChanged` names `fullName` and `jobTitle`); filter names, never terms (`nhsNumber`, never the number). The only free text is an admin's reason for a restriction, dispute or keep, which anonymising replaces; anonymising's own reason is a fixed choice, with an optional note that must hold no patient details.
  - **Who:** the actor (user and address) comes from `IActivityContext` (`HttpActivityContext` in the API, `DevToolActivityContext` in `medapp-dev`), not the command. Pathway commands still take a `PathwayActor`.
  - **It fails closed:** a read or sign-in whose entry can't be written fails (500).
  - Action numbers are stored, so never renumber `ActivityAction`. No foreign keys, like the audit log.
  - `GET api/activity/search` (admins) searches it; a patient's page shows its latest entries about them as the access report.
- **Restricted and disputed records** (Articles 18 and 16): admins set them with a reason (`PUT api/patients/{id}/restriction` and `.../dispute`).
  - A restricted or anonymised record can't be changed, nor its pathways, appointments, referrals or files: `PatientRules.EnsureCanChange` (409), applied by `GetForUpdateOrThrowAsync` to every pathway change, its namesake in `AppointmentRepositoryExtensions` to every appointment change, `ReferralWorkflow.WhyCantEdit` (through `GetForEditOrThrowAsync`) to registering and editing a referral, and the attachment handlers to every upload and delete. Registering a referral for a restricted patient says to give the letter to an admin (hazard H-40).
  - **So care can be paused safely,** a restricted record's pathways can still be blocked or cancelled with a reason, and its appointments cancelled (`GetForCancelOrThrowAsync`): `ChangePatientPathwayStatusHandler` loads them through `GetForPauseOrThrowAsync` for those two statuses (`PatientRules.PausesWhileRestricted`). A restricted record's referrals can still be withdrawn or marked entered in error (`GetForCloseOrThrowAsync`; not once anonymised). Restricting a record with pathways under way, open appointments or referrals awaiting triage needs `ConfirmOpenPathways` (400 without it); the dialog shows how many of each, and the API's message if it still asks. Hazard H-22.
  - `GetForUpdateAsync` is called only by those two guards; a convention test checks it, and that every pathway command uses one.
  - A pathway's response gives `ReadOnlyReason` (every `Can...` flag false; only Blocked and Cancelled allowed while restricted) and the patient's flags (`PatientFlags`) for the banners on the pathway, edit and patient-pathways pages. Disputed is a banner only.
- **Patients have a row version** (`Patient.RowVersion`): a save from a copy read before someone else's is a 409 (`SaveChangesOrConflictAsync`, `PatientRules.ChangedMeanwhileMessage`), so a stale edit can't undo a restriction or anonymisation. `SaveChangesOrConflictAsync` takes the message to give (appointments use it too).
- **Everything about a patient** is loaded by `IPatientRecordRepository` (`PatientRecordRepository`) for the subject access export (`GET api/patients/{id}/export`, admins, `no-store`, itself logged) and anonymisation. **A new table holding patient data must be added there** (referrals and their history are). The export has its own types (`Exported…Response`): staff by username only, never account IDs, network addresses or notification read times, and the JSON holds exactly what the printable page shows.
- **Anonymisation** (`POST api/patients/{id}/anonymise`, admins, `PatientAnonymiser`) replaces identifying details and free text with placeholders in place, across every table, keeping IDs and structure. **The result is pseudonymised, not anonymous:** the patient ID, year of birth, dates, templates and who did what remain, so it's still personal data. It needs the patient's full name typed and a reason from `AnonymisationReason` (optional note), and is refused while a pathway is under way, an appointment is open (Requested or Booked: cancel it or record its outcome first), a referral awaits triage, or the record is restricted. It replaces referrals' reasons, referrers, decision details and redirect destinations, and clears their ODS codes and directory practices. It removes the patient's address, postcode, mobile and practice link (and sets their reminder choice back to none); the practice stays in the directory. Deleting a patient is unchanged (refused with pathways, appointments or referrals).
- **Retention** (`RetentionOptions`, the `Retention` section of `appsettings.json`; `RetentionSchedule`): `GET api/patients/retention-review` lists records past their minimum period; an admin reviews, keeps (`POST api/patients/{id}/retention/keep`, with a reason and a review date up to two years ahead) or anonymises. **Nothing is ever deleted automatically.**
  - **Retention classes** (PR 27, decision 139): a pathway template's `RetentionClass` (stored by number: `Standard = 0`, `Oncology = 1`, `Maternity = 2`, `MentalHealth = 3`), set on the template editor and copied onto each pathway; changing a template's class changes its existing pathways' too (`UpdatePathwayTemplateAsync`, one save). A record's period is the longest of the adult or child rule and each of its pathways' classes (`Retention:Classes`, years from the conclusion of treatment, at least 1, checked at startup; defaults for the DPO to confirm). The review's `retentionClass` says what set it (`RetentionBasis`: Adult, Child, Oncology, Maternity, MentalHealth). A deleted pathway's class stops counting (`docs/todo.md`).
  - The conclusion of treatment counts the pathway audit and the referral history too, so a deleted pathway, or a referral closed without one, still counts; a patient with a referral awaiting triage isn't listed; a 29 February birthday falls on 1 March in other years (`RetentionSchedule.AddYears`).
- **Sign-ins:** one throttled by `LoginThrottling` (429) is refused before the handler, so it's not in the activity log (the throttling logs it at Warning). A name no account could have (`UsernameRules.CouldExist`) is logged as a refused sign-in with no account. Signing out everywhere is logged (`SignedOutEverywhere`), and a password change or reset in the same transaction as the change and the end of the sessions.
- **The operational purge** (a scheduled job, `docs/agents/jobs.md`) deletes sessions and the activity log's sign-in and security events after 12 months, notifications after 6, untouched notepads and expired sign-in codes, **as a dry run until `Retention:Operational:DryRun` is turned off**. Never patient records, nor the activity log's patient entries or account and role changes. The rest of operational data isn't purged yet (`docs/todo.md`).
- **Texts and emails to patients** (`PatientMessages`, PR 26, DPIA risk 32; [Calendar](calendar.md), Patient reminders): every message is stored with its destination and text, read through `GET api/appointments/{id}/messages` (`PatientViewed`), exported with the patient's reminder choice, and anonymised (destination `[Removed]`, text replaced, waiting ones cancelled). A Did not attend's follow-up detail (`Appointment.DnaFollowUpDetail`, and `detail` in its history) is free text: admins only on the timeline, replaced on anonymisation. Sending is a disclosure to a processor (GOV.UK Notify, when Live): `docs/governance/sub-processors.md` and `international-transfers.md`.
- **Patients' contact details and the GP practice directory** (PR 12, `docs/centre-phases-3-5-plan.md` decisions 78 to 80; DPIA risk 31): all optional on the patient: `AddressLines` (up to 3 lines of 100, stored as one column joined by line feeds: `PostalAddress`), `Postcode` (UK format only, stored upper case with one space: `UkPostcodes`), `MobilePhone` (a UK mobile, stored as `+447…`: `UkPhoneNumbers`), `PracticeId` (from the directory, restricting key) and `ReminderChannel` (`None = 0`, `Text = 1`, `Email = 2`, `TextAndEmail = 3`, stored by number; on the patient form since PR 26, logged as `reminderChannel`, exported, set to None on anonymisation). They go through the patient's create and update (null leaves one as it is, empty removes it, `Guid.Empty` removes the practice), with the same restriction guard, row version and activity entry (field names only). A practice newly chosen must exist (404) and not be archived (409); one archived since it was chosen stays. `PatientResponse` gives `practiceId` always and `practice` (`PracticeSummaryResponse`) on a single patient's response only. The export gives them, with the practice by name and code (`PatientRecord.Practice`).
  - **The directory** (`Practice`, `api/practices`, `PracticeRules`): name (200, not unique), optional ODS code (`OdsCodes` format, unique when present: `IX_Practices_OdsCode`), address, postcode, phone (UK format) and secure email (its domain must be in `Letters:SecureEmailDomains`, `nhs.net` when unset: `LettersOptions`), `Version` with `expectedVersion` on every change, archived not deleted once a patient or referral has it (409; the foreign keys refuse a race). `ViewPatients` reads, `EditPatients` changes. Organisation data: it records nothing when read.
  - **Synthetic only** in tests and seeds: `ZZ` postcodes, Ofcom's drama range (`07700 900000` to `900999`), invented practices, never a real practice's name or ODS code.
- **Staff full name and job title** (`ApplicationUser.FullName`, `JobTitle`, 100 each, for letters): `GET`/`PUT api/auth/me/details` (`UseApp`), `PUT api/auth/users/{username}/details` (`ManageUsers`), through `IStaffDetailsService` (written directly, not through the user manager, so the security stamp and sessions are untouched), logged as `StaffDetailsChanged = 48` (field names only, the account as target), on `UserResponse` for the Users page. Staff personal data: in the staff privacy notice.
