# The light demo (GitHub Pages)

The React app as a static site with no server, for recruiters to try: https://aliator.github.io/MedApp/. Read before changing anything in `MedApp.Web/src/demo/`, the demo build, or a page or endpoint its tour uses, and **before any PR that adds or changes an endpoint, a page or a rule** (below).

## Keeping it up to date (the rule)

**Every change to the full app is made to the light demo in the same PR** (the owner, 18 November 2026: "any changes that are made to the local deployment are also made to the light version as well").
- **A new or changed endpoint, page or rule** updates the demo's handlers (`src/demo/handlers/`) and seed (`seed.ts`, `slices/`) in the same PR. Simplified rules are fine; the demo's copy of a rule should refuse what the API refuses, in short.
- **What the demo can't do** (files, PDFs, email, post, background jobs, real sign-in, downloads) is listed in `src/demo/notInLightDemo.ts` with a one-line reason. (`NOT_IN_THE_LIGHT_VERSION` in `tour.ts` keeps the visitor-facing list; nothing shows it since the Read Me was removed, 20 November 2026.)
- **Enforced by `src/demo/parity.test.ts`:** it reads every path and method in `src/api/schema.d.ts` and fails unless each one has a handler or is in `notInLightDemo` (and fails on a listed one that's gone from the API, or handled as well, or a path handled twice). So a new endpoint fails the web tests until its PR classifies it. `npm run typecheck` checks the handlers' shapes against the DTOs.
- **A new page in the side nav** renders with data for every account (no 501s): check it with `npm run dev:demo`.

## How it works

- **A separate build.** `npm run build:demo` is Vite's `demo` mode (`vite.config.ts`): client only (`index.html`'s `#root` is created, never hydrated), under `/MedApp/` (Vite's `base` and the router's `basepath`), into `dist-demo/`, with `index.html` copied to `404.html` so a deep link loads the app (GitHub Pages serves `404.html` for any unknown path; no redirect script). `npm run dev:demo` runs it locally with Vite on port 5174, needing no API.
- **Kept out of production.** Everything demo is behind the build-time constant `__LIGHT_DEMO__` (`define` in `vite.config.ts`, declared in `src/lightDemo.d.ts`), true only in the demo build, and loaded by dynamic `import()`. Other builds and the tests have it false, so the bundler drops the demo's code. Proven by grepping `npm run build`'s client output (`dist/`, not `dist/ssr`) for `Not available in the light demo`, `medapp-light-demo` and `installLightDemo`: none is there. What production keeps: a doc comment in the server bundle.
- **The hooks into the app** (each one line, behind `__LIGHT_DEMO__`): `entry-client.tsx` starts the stand-in before rendering; `router.tsx` sets the base path; `routes/login.tsx` shows the account picker (`DemoLoginPage`); `AppLayout` renders the walkthrough (`DemoWalkthrough`) and doesn't start `LiveNotifications`; `AppSideNav` adds the Walkthrough item at the top (`walkthroughNavEntry`, `src/demo/walkthroughNav.tsx`).
- **A stand-in API in the browser** (`src/demo/install.ts`): `window.fetch` sends every request for this origin's `/api/...` to a table of handlers (`src/demo/api/http.ts`, `src/demo/handlers/`) instead of the network. Each handler is registered with `on(method, path, handler)` for a path in `src/api/schema.d.ts`, and its return type is that endpoint's DTO, so `npm run typecheck` guards the shapes. A path with no handler answers a 501 ProblemDetails, "Not available in the light demo" (logged with `console.info`), and the page shows its usual error state.
- **State** is one record in IndexedDB (`medapp-light-demo`, `src/demo/store.ts`): read once at start, written after every change that succeeded. Without IndexedDB it runs in memory. **Reset** (`resetDemo`: the walkthrough's Reset the Demo, offered when a step's record is gone or the step was done already) clears it, seeds again (keeping who's signed in) and reloads. Records are kept close to the DTOs (`src/demo/state.ts`); what depends on the viewer (`can...` flags, overdue, the current stage) is worked out per answer, and a patient's timeline is read from their pathways, appointments and referrals (`handlers/patients.ts`).
- **The seed** (`src/demo/seed.ts`) is a small TypeScript copy of part of the demo clinic (`tools/MedApp.DevMcp/DemoData`): **one clinic, Dermatology, and the lab** (the owner, 19 Nov; tests needing a second clinic add one with `src/test/otherClinic.ts`), 11 synthetic patients (NHS numbers only from the 999 range, valid check digits), Dermatology's ten reviewed templates, nine pathways (one on hold, one overdue, one at a stage needing consent, one at a branch point, one back from the lab), three referrals, appointments, this week's and next week's calendar blocks, a meeting and notifications.
- **Dermatology's ten templates** are the owner's reviewed ones: `docs/pathways/dermatology.yaml` (the source of truth), copied field for field in `src/demo/dermatologyReviewed.ts` (keep the two in step) and mapped onto the model by `dermatology.ts` (choice nodes, lab stages, shared stage definitions; routes back become repeatable routes, a repeating stage or an end, as its comment says).
- **Slices:** each area's records and seed are in their own file under `src/demo/slices/` (`lab.ts`: specimens, types, the lab test catalogue (MC13), results; `clinical.ts`: letters, letter templates, the MDT list, consent; `setup.ts`: practices, sites and rooms, hours, clinics, roles, monitoring, jobs and the rest of setup), with their handlers in `handlers/lab.ts`, `handlers/clinical.ts` and `handlers/setup.ts`. `DemoState` is the base and every slice; each slice's seed runs after the base's, reading it. Fixed IDs come from `id(kind, n)` (`ids.ts`), one `kind` per group.
- **The stage gates** (`StageGates`, without an override) refuse finishing a stage in the demo as in the API, simplified: the lab's (`labGate`: the last stage while a specimen is open; a stage that waits for results, or the last, while a result awaits sign-off), the letter's and consent's (`clinicalGate`). Every finish calls them (`handlers/pathways.ts`). Fixed IDs in `src/demo/ids.ts`; dates relative to the day it's seeded. **The C# seed can't be exported for it:** it runs the API's commands against SQL Server, and Pages builds in CI with neither. Bump `SEED_VERSION` when the seed's shape changes, so visitors' older copies are seeded again. **It's seeded again on a new day** (`isCurrent` in `store.ts`: the kept copy's `seededOn` must be today, keeping who's signed in), so its dates always fit the day the visitor comes back. **Every account has a calendar today and this week** (the owner, 20 November 2026): blocks for Nadia Thornbury, Ravi Aldous and the admin on weekdays this week and next, and, when it's seeded on a Saturday or Sunday, weekend sessions with the centre and the three accounts working that weekend (`weekendCover` and the centre's hours in `slices/setup.ts`); `seedCalendar.test.ts` checks a weekday, a Saturday and a Sunday.
- **Tree pathways** (MC8, `handlers/pathways.ts`, `src/api/pathwayRoutes.ts`): a pathway's stages follow `links` (copied from the template's, by stage order; a list template's are `chainLinks`). Current = to do with nothing before it to do (`currentStages`); a branch point's branches are its successors' routes up to their join. - **The relay** (MC7, `handlers/pathways.ts`, `canWorkStage` in `teamWalls.ts`): a stage's `ownerTeamId` (the lab's Histology and Lab tests) is worked only by that team; finishing or skipping into another team's stage hands over (each current stage of a fork on its own) (`reachNext`: grant, `PathwayHandedOver` notification, `StageHandedOver` in the audit log); Pick Up (`StagePickedUp`); the `View` search (`OurTurn`, `NewForUs`, `AwaitingLab`, `BackFromLab`) behind My Worklist's team views.

## Adding a handler

1. Run `npx vitest run src/demo/parity.test.ts`: it lists the endpoints with neither a handler nor a reason. Find the request the page makes (`npm run dev:demo`, the console's `[light demo] Not available` line, or `src/api/*.ts`).
2. In the area's file in `src/demo/handlers/` (or a slice's), `on('get', '/api/...', ({params, query, body}) => ...)`, returning the DTO. Call `me()` first (a 401 when signed out, as the API), and `requirePermission(...)` where the API needs one. Refuse with `refuse(problem(409, '...'))`, `notFound('The ...')` or `invalid({field: ['...']})`.
3. Keep rules simple, and add what the full version does that this doesn't to `NOT_IN_THE_LIGHT_VERSION` (`tour.ts`) when a visitor would notice.
4. A test in the area's test file in `src/demo/handlers/` (`startLightDemo`, `call` from `src/test/lightDemo.ts`).
5. Or, when the demo can't do it, list it in `src/demo/notInLightDemo.ts` with a reason.

## What's simplified or left out

**Covered:** every page in the side nav, for both accounts, with data, and the actions behind them: sign in, pathways and stages (optional stages, branches, unlocking, reinstating), notes and their deletion, status, assignments, referrals (register, edit, triage, withdraw, information requests, the clock's pauses), the lab (its home at `/lab` for `r.aldous`, MC17; specimens through their statuses on `/lab/samples`, types and lab tests, MC13), results (seen, sign-off, reassign, entered in error), letters (write, approve, return, withdraw, correct, record as sent), letter templates, the MDT list (list, defer, withdraw, outcomes), consent forms and records, calendars, templates, closed days, clinics, meetings, appointments, booking and Did not attend, the notepad, settings, notifications, Insights, the setup pages (teams, the stage library, pathway templates, sites and rooms with hours, practices, activity types, roles, monitoring rules including service alerts), the audit and activity logs, privacy (restriction, dispute, the retention review, the export page) and data requests.

**Simplified:** few concurrency checks beyond `expectedVersion`; no locks; the audit log is worked out from the records, and the activity log from seeded entries and the demo's own sign-ins, views and changes; Insights' history (last week's figures, stage times, throughput) is made up; roles held by someone, and users, can't be changed; monitoring rules are kept but nothing fires them; the scheduled jobs are listed with made-up runs. Data requests (`handlers/dataRequests.ts`): kept as an optional list on the state, made on first read with one open request (`SEEDED_DATA_REQUEST`, Tobias Lund's, due within the week, so the admin's Needs your attention has a line); the review lists pathway notes only.

**Not there** (`notInLightDemo.ts` lists each endpoint with its reason): files (attachments, a specimen's report, an external result, a consent scan), PDFs (letter and template previews, the data-request pack's download), sending letters (`send` refuses: record it as sent instead), email and two-factor, real sign-in and passwords, creating and deleting users, running a job, FHIR and the demographics lookup, live notifications, server rendering. The patient timeline doesn't show specimens, results, letters, the MDT or consent yet.

## Decisions (taken on the owner's behalf, 18 November 2026)

- **Fetch is patched in the page, not a service worker** (no Mock Service Worker): no extra file to serve under `/MedApp/`, nothing that outlives the tab, and no dependency. Plain IndexedDB (a few lines) rather than a library.
- **The whole state is one IndexedDB record**, rewritten after each change: simple, and small at this size.
- **A 501 for a path with no handler,** so it can't be mistaken for a real 404 or 409.
- **The timeline is derived** from the records rather than stored, so no handler has to remember to add to it.
- **Switching account and Reset reload the page,** rather than clearing caches by hand, and close any half view.
- **`src/demo/**` is excluded from the coverage thresholds** (`vite.config.ts`): it's never in the production build, and has its own tests (the tour, the handlers, the store, the seed and each page).
- **The notepad's "never in browser storage" rule doesn't apply here** (`notepad.md`): the demo's data is synthetic and there's no server.
