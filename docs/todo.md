## Community specialist centre

The plan to make MedApp fit a referral-led community specialist centre (outpatient specialties, a lab, visiting consultants), in five phases. Each phase leaves the app in a state that can be shown. The demo is inspired by such a centre, but no real centre's name or logo goes in the repo.

**Phase 1: done.**
- **The vocabulary:** pathways, pathway templates and the screen-only labels, in `docs/glossary.md`. `tools/rename-procedures-to-pathways.py` brings a branch from before the rename across.
- **One seeding script:** `tools/seed-demo-data.sh` (and `.ps1`) wipes the local database and replays the demo clinic; it's the only way demo data gets in, kind's demo data included.
- **The new demo clinic:** 18 months of a referral-led outpatient centre (dermatology, gynaecology, urology, diabetes, biomechanics), described in `docs/demo-data.md`.

**Phase 2: the front door.**
- **Referrals and triage:** a referral record (the referring GP practice, when it arrived, the letter, the specialty asked for), an inbox of new referrals, and a clinician's triage decision (accept, reject or redirect, with a reason). Accepting creates the pathway: the clinician decides, the app records.
  - **Referrals and triage are built** (PR 5, `feature/referrals`, and PR 6, `feature/triage`: `docs/agents/referrals.md`). **Referrals mustn't be used with patients until the CSO has verified the triage controls** (hazards H-40, H-41, H-44).
  - **The waiting-time clock is built** (PR 7, `feature/waiting-clock`: `docs/agents/referrals.md`). Left for later: a notification or monitoring rule when a breach happens or a pause's review date passes (Phase 4, needing a scheduled job: hazards H-42 and H-43); an accepted pathway still open when the clock's migration ran keeps the target date it had until its clock next moves it (a pause, a resume, a new priority); and an API copy from before the clock, during a rollout, registers referrals with no clock (target 0 days, counted from 1 January 0001), which the clock's PR can't fix by itself: deploy the API before anyone registers a referral, or correct those referrals' clock columns (`TargetDays`, `WaitStartOn`, `TargetOn`) afterwards.
  - **A referral redirected between specialties more than once keeps only the latest redirect's detail** (`Referral.RedirectDetail`); the history records every move, without text. A table of redirections would keep each, if that's ever needed.
  - **Register Referral is shown to everyone signed in** (the Referrals page's button and the patient page's Referrals card, `TODO(useCan)` in both) until `useCan` lands (PR 3); the server refuses anyone without `RegisterReferrals` with a 403. The referral page's own actions already follow the response's flags (`CanEdit`, `CanClose`, `CanAttachFiles`).
  - **The inbox opens on every specialty:** the search takes `mine` and `specialtyIds`, and the side nav's count is already the viewer's specialties', but the page has no specialty filter yet (PR 8).
  - **Two people registering the same letter at the same moment** both pass the duplicate check (it reads before either saves). The second shows on the patient's Referrals card and is marked entered in error, or rejected as a duplicate at triage (H-44). A lock or a unique index would close it, if it's ever seen.
  - **The clinical safety case report** (`docs/clinical-safety/clinical-safety-case-report.md`) lists H-40 to H-44 but still lacks H-37 to H-39, and its summary's counts are from hazard log version 0.9: bring it up to date with the hazard log before the first release.
- **Specialties:** every pathway type, clinic and member of staff belongs to one, with filters, worklists and Insights by specialty.
- **A waiting-time clock:** built (PR 7, above).
- **Roles and permissions, the rest** (the policy layer is built: `docs/agents/auth.md`):
  - **`GET api/auth/roles` (every role's name), kept one release** after the Roles and Permissions page so a page loaded before it still works during a rollout: remove it (and `GetAllRolesQuery`, `IIdentityReadService.GetRoleNamesAsync`) in the next release. The Users page reads `GET api/roles`.
  - **The roles page, later:** step-up (the admin's password again) before a role change, as for other admin actions (ASVS 7.5.3); a preview of exactly whose access changes (today it says how many hold the role, though someone with another role granting the same permission isn't affected).
  - **After every account is on a starting role:** take the everyday clinical and booking permissions from Admin and archive "All staff (before roles)" (open question 10), as a small change of its own before a real team uses MedApp.

**Phase 3: clinic to lab to result to letter.**
- **Contact details, practices and staff details are built** (PR 12, `feature/patient-contact-gp`: `docs/agents/privacy.md`). Left from it:
  - **The offline demographics stub gives no GP practice**, as it knows no ODS codes; the real PDS gives one, to match against the directory when PDS is wired in.
  - **Demo data** for practices, contact details and staff names comes with Phase 3's demo data (PR 17).
  - **Looking practices up in the national ODS service** stays for later (plan, section 8): the directory is typed.
- **Lab specimen tracking:** a specimen with its own ID (taken, sent, received, reported, with turnaround times), linked to the stage that took it, its report attached as a file. MedApp tracks and shows; it doesn't interpret.
- **Results sign-off:** every result marked seen and acted on by a named clinician, and a list of results nobody has signed off, so none is missed.
- **Letters:** clinic letters and discharge summaries from templates, as PDFs, to the GP and the patient, with a record of when each was sent.
  - **Letter templates and the PDF engine are built** (PR 15, `feature/letter-templates`: `docs/agents/letters.md`). Left from it:
    - **PDF/A:** letters are made in PDFsharp's PDF/A-1a mode and pass veraPDF 1.30 while every character is Windows-1252, but one with other characters (Ł, ł, ş, ğ, common in Polish and Turkish names) fails clause 6.3.5, as PDFsharp 6.2 writes no CIDSet for the extra font it then embeds. Before claiming PDF/A: add the CIDSet (a fix upstream, a post-processing step, or a font without the second encoding), and check again with veraPDF (`verapdf/cli`, `--flavour 1a`). GP systems accept plain PDF meanwhile (plan, decision 98).
    - **Tags are coarse:** each page's text is one paragraph element, so headings and lists aren't tagged as such (PDFsharp can't tag what MigraDoc lays out). A screen reader reads the text in order; finer tags need per-element rendering or another library.
    - **PDFsharp and MigraDoc stay on 6.2.x:** 6.5.0 and later are AGPL-3.0 (Dependabot ignores them). If 6.2 stops getting fixes, decide between buying empira's commercial licence, staying on 6.2 with the NuGet audit as the alarm, or another MIT library.
    - **Deleting an unused template** comes with letters (PR 16), which know whether one was used; until then templates are only archived.
    - **The letter font covers Latin scripts only:** PR 16 must refuse (with `FindUnsupportedCharacters`) a patient's name, address or body text it can't show, naming the characters, rather than print `?`.

**Phase 4: day-to-day running for a real team.**
- **Pathways that branch:** optional stages, or a choice of next stage, each with an audit entry, instead of stages strictly in order (a benign result means discharge, a malignant one treatment).
  - **Built** (PR 20, `feature/branching-pathways`: `docs/agents/pathways.md`). **Not to be used with patients until the CSO has verified H-51's controls.** Left for later:
    - **Demo data** gets its branches, optional stages and skips in PR 28.
    - **During a rollout,** an API copy from before this release doesn't know stages can be skipped: it shows a skipped stage as the current one, and would let staff finish it. Make no template with optional stages or branches until every copy runs this release (the chart's two-release rule).
- **Clinics, rooms and longer hours:** clinic sessions with a set number of slots, in a named room at a named site; evening and weekend clinics; working hours for each person or site (today everyone's day is 08:00 to 18:00 UK time, Monday to Friday, except closed days).
- **Roles that limit what people see:** the starting roles (Clinician, Nurse, Booking, Lab, Manager) limit what each does since Phase 2, but every role still sees every patient. The privacy items naming roles (hiding restricted patients from lists, an `Auditor` read permission) build on it.
- **Patient reminders and the Did not attend list are built** (PR 26, `feature/patient-reminders`: `docs/agents/calendar.md`, Patient reminders). Left from it:
  - **Turning the real sender on** is the customer's: their own GOV.UK Notify service (or another provider's adapter, for a customer Notify won't serve), its two templates (`((message))`; `((subject))` and `((message))`), the API key in the secret store as `PatientMessages__Notify__ApiKey`, the sub-processor notice (`docs/governance/sub-processors.md`) and `PatientMessages:Mode=Live`. Try it against Notify's test key (messages accepted, never delivered) before a live one.
  - **The chart sets no mode,** so kind and Azure are Off: kind should be Offline into its Mailpit (`PatientMessages__Mode`, `PatientMessages__SenderName` in the chart's values) and Azure Live once a customer has a Notify service. A deploy change, tried on kind before it merges (`docs/agents/deploy.md`).
  - **Telling the patient when a calendar drag moves an appointment:** the booking dialog offers it; a drag on the grid doesn't (it moves without asking).
  - **A session's room moved** moves its Booked appointments' room (perhaps to another site) without offering to tell the patients.
  - **Messages about a cancelled pathway's or a closed day's appointments:** cancelling a pathway leaves Booked appointments for staff to cancel (and tell); closing a day tells nobody yet.
  - **Video appointment links** in reminders come with video appointments (PR 34).
  - **A message's content kept for as long as the record:** messages are part of the patient record and kept with it; whether their text and destination should be purged sooner (a few months) is the DPO's decision (`docs/governance/retention-schedule.md`).
  - **Demo data:** offline messages for past appointments, some not sent and some failed, follow-ups recorded and three waiting (PR 28).
- **Adjusted with them:**
  - **Monitoring rules for a service:** a referral not triaged in two days, a result not signed off, a visit waiting too long to be booked.
  - **Who may finish a stage without its visit:** a senior clinician, not whoever is an admin. **Built** (PR 24, `feature/stage-permissions`): `OverrideStages` split into `UnlockStages` and `FinishWithoutVisit`, the starting role Senior clinician, the built-in Admin role without `FinishWithoutVisit`, and the `StageFinishedWithoutVisit` monitoring event. Left for later:
    - **Demo data** moves the consultants and the GP with a special interest to Senior clinician, and takes both off Clinician (PR 28), as the release note asks admins to do where their senior clinicians alone should unlock stages and finish one without its visit. Until then Clinician keeps both, so nobody lost anything.
    - **Skipping a stage whose visit is Required** needs `FinishWithoutVisit` too, but isn't a monitoring event (decision 136 names finishing only): add `StageSkippedWithoutVisit`, or fire `StageFinishedWithoutVisit` for it, if admins ask.
    - **During a rollout,** an API copy from before this release doesn't know the two new names (a name code doesn't know grants nothing), so for the minutes of a rollout it refuses unlocking, reinstating and the visit bypass to everyone but the built-in Admin role: it fails closed.

**Phase 5: soon after, and before a real team uses it.**
- **Team meeting (MDT) list:** pathways put forward for discussion, and the outcome recorded on each.
- **Consent records:** which consent form, signed when, attached to the stage.
- **Reports for whoever pays for the service:** activity, waits, missed appointments and turnaround times, by specialty and month, with a CSV download, built on Insights.
- **Outcome questionnaires:** scores before and after treatment, recorded and shown, never scored into advice.
- **Private patients:** fees, invoices and insurer details.
- **The full data-request pack:** see Privacy, "A GDPR report for a patient's data request".
- **Longer retention classes:** a centre doing cancer work needs more than the adult and child periods (Privacy, "Retention classes per template").
- **Several sites or organisations in one deployment:** multi-tenancy (roadmap step 8), before a second centre shares the system.
- **Links to NHS systems:** the e-Referral Service, the real demographics lookup (Patient identity, "The real PDS lookup"), letters sent to GP systems, and the lab's own system. Each needs NHS onboarding, which takes months.
- **Video and phone consultations:** an appointment type and a link; the call happens in another tool.
- **Before a real team uses it:**
  - **Re-check the medical device decision:** waiting-time breach flags, triage and results lists move the app closer to decision support. Update `docs/clinical-safety/intended-purpose-and-device-decision.md` before building them.
  - **The clinical safety case and hazard log,** with the new hazards: a referral lost before triage, a result never signed off, a letter sent to the wrong GP.
  - **NHS and security assurance:** the Data Security and Protection Toolkit, the digital technology assessment (DTAC) and a penetration test.
  - **A clinical read of the new labels:** the status shown as "Discharged" (stored as `Completed`) is a label staff give a pathway whose stages are finished; the Clinical Safety Officer should confirm staff won't read it as the patient's discharge being recorded or sent anywhere (`docs/clinical-safety/intended-purpose-and-device-decision.md`, Status workflow).
  - **Put the safety gates back:** Testing, "Before first live use, make CI strict again".
  - **Background jobs and file scanning:** Privacy, "Turn the operational purge on", and Attachments, "A real malware scanner".

## Accessibility

The axe audit (`npm run a11y` in `tools/ui-parity`: every screen in dark, light and a colour theme, WCAG 2.2 A and AA) passes, and the Accessibility card has the text size, the hover delay and the switches in `src/app/accessibility.tsx`. The statement is at `/accessibility`. Still to do:

- **Three colour themes just under 4.5:1 on secondary text.** Measured against the secondary text colour (subtitles, Back, descriptions), Y2K's light page is 4.19:1, and the header bars of Chocolate's light cards and Butter's dark cards 4.41:1. The custom colour check (`textContrast`) now counts secondary text; these themes were left as they are so they don't change how they look. Decide whether to adjust them (a test lists them in `src/app/colours.test.tsx`).
- **Insights at high zoom.** At 400% zoom (320 x 256 CSS pixels, WCAG 1.4.10's test), the header and filters fill the window, the area under them is 0 px high and the document doesn't scroll, so no chart can be reached. At 200%, each 30rem chart card is taller than the area it scrolls in. Let the whole page scroll when the window is that short, and check the other `fill` pages for the same (review of #94).
- **A list's sort button in its card layout names itself differently from what it shows** (axe `label-content-name-mismatch`, WCAG 2.5.3): `RowCards` shows "Sort: When" but is named "Sort by When, descending", so a voice user saying what they see doesn't match it. Start its name with the visible text ("Sort: When, descending"). Found by the Apply Template branch's audit, on the Audit Log in a half view (`pathway-restricted-half`); it's on every list shown as cards.
- **Escape after Tab in a dialog takes two presses.** Tab from a dialog's title lands on its Close button, whose tooltip shows on keyboard focus; the tooltip is a layer of its own in Astryx's dismissal stack (`useLayerDismissal`), above the dialog, so the first Escape dismisses the tooltip (as WCAG 1.4.13 asks) and only the second closes the dialog. Every dialog (`DialogFrame`'s `DialogHeader`), on `main` too; found in #110's browser check (Log Out, 1366 px). Not MedApp's code: ask Astryx for a dialog Close button whose tooltip doesn't take an Escape of its own (or whose Escape closes both), rather than dropping the tooltip.
- **Screen reader pass by hand.** NVDA and VoiceOver through the main tasks (find a patient, work a stage, finish a pathway), and keyboard-only use of every dialog: focus trapped, and returned on close.

## Features

- **Calendar follow-ups.** What staff calendars and appointments left out (`docs/calendar-plan.md`, section 8):
  - **More closed days** (built: `docs/calendar-plan.md`, decisions 72 to 75; working hours are in the centre plan, phase 4): Scotland's and Northern Ireland's bank holidays, a closed day for some people or sites only, and marking appointments on a closed day outside the Calendar page's grid (lists, the pathway page, Home). Closing a day already says what's on it and tells those staff.
  - **More kinds of booking:** recurring appointments, rooms and resources, and booking several staff for one appointment.
  - **After walk-ins** (built: decisions 74 to 78): a list of appointments recorded after the event (and those withdrawn as entered in error), for admins to review (hazard H-39), and monitoring them as an event; regenerating `MedApp.Web/src/api/schema.d.ts` with `npm run gen:api` (hand-edited when walk-ins were built, as the AppHost wasn't running).
  - **Patients booking for themselves** (reminders are in the centre plan, phase 4).
  - **Requested appointments left waiting:** flag or notify ones requested long ago and still not booked.
  - **Printing a day list.**
  - **Meetings** (`docs/calendar-plan.md`, decisions 50 to 60): recurring meetings; a meeting's own history (who changed what), as appointments have; notifying attendees when only a meeting's title or notes change (today only a move, an invitation or a cancellation tells them); and letting staff arrange meetings among themselves, not only admins. Accepting and declining are built (decision 71); a reason or a "maybe" with a reply, and reminding those who haven't replied, are not.
  - **Sharing or copying calendar templates:** templates are each person's own (`docs/calendar-plan.md`, decisions 50 and 51), and there's no way to give one to someone else. That has costs (review of #99, finding 5):
    - **A change for a team:** twelve nurses who shared "Clinic week" before the migration each have their own copy; moving everyone's lunch to 12:30 is now twelve edits, one person at a time on each person's templates page, where it was one.
    - **A new starter:** an admin can't give them an existing pattern (setting their default week to someone else's template is a 404), so has to rebuild the day templates and the week template by hand in the newcomer's set.
    - **Unused templates** went to one admin, who can't apply them to anyone else either.
    - **The fix:** a "Copy to..." action for admins: copy a day template, or a week template with its day templates, into chosen people's sets (new rows from today, names kept). Keeping copies in step afterwards would need a shared template or a link back to the original, which personal templates deliberately don't have.
  - **Tidy up templates with accounts:** deleting an account (or taking every staff role away) leaves its day and week templates, and its default week rows, where no list shows them (`docs/governance/retention-schedule.md`). Delete the ones nothing refers to, and give the rest (archived) to an admin, or delete them with the rows.
  - **The team view for many people:** it loads every calendar shown in one set of queries and draws a column for each person. Who, when chosen, is at most 100 people, but the default (everyone, which sends no IDs) has no limit: with 400 staff, one page load reads 400 calendars, draws 400 columns and records `PatientListed` for every patient booked with any of them that day (review of #99, finding 7). Cap everyone at the first 100 by name, saying "Showing 100 of 400: choose who in Who", or ask for a choice above 100; a large organisation will want teams or groups to choose from instead of the whole staff list.
  - **Template edits that undo a day's changes.** Editing a day template's block gives it a new row, and a day's exception (the block removed or moved for one day) points at the old row, so the block comes back on that day, possibly over an appointment booked in its place. Keep a block's identity across versions (a lineage ID the exceptions key on), or at least list the future days' changes an edit will drop before saving (review of #93, finding 2).
- **More monitoring.** Admins' monitoring rules (Administration, Monitoring) and each person's switch for assignment notifications are built (`docs/agents/monitoring.md`). Still to do:
  - **An overdue event,** for rules and for the assignees. It isn't a change anyone makes, so it's a job on the scheduled job runner (`docs/agents/jobs.md`), with a record of which pathways it has already reported.
  - **Audit the rules** (who added, changed or deleted which rule), and let a staff member, or the DPO, see the rules that name them (DPIA risk 24).
  - **Tidy up with accounts:** deleting an account should delete the rules it owns and the rules that name it, and its notification choices (`docs/governance/retention-schedule.md`). Until then they stay, and send nothing.
  - **More people in the picker:** the Monitoring page offers the first 100 accounts by username (the API's largest page), and says so under the field when there are more. A searchable picker, on `api/auth/users/search`, would suit a bigger organisation.
  - **More choices for each person** (Account Settings), once there are more kinds staff receive (the three appointment kinds, booked, rescheduled and cancelled, can't be switched off yet); and rules an admin sets for someone else (for example a team lead's), kept apart from that person's own choices so they can't undo them.
- **More from email** (the email service, optional staff addresses, "Forgot your password?" and security notices are built). Still to do:
  - **Notification emails,** opt-in per person. They must never carry free text that may hold clinical information (a notification's title is a pathway's title), so send "You've been assigned a pathway" with a link, not its title.
  - **A retry for failed emails.** The queue is in memory and best effort: a message that fails, or is still queued when the API stops, is lost (logged). Every email today is a link or a notice that can be asked for again; a durable outbox (a table) would be needed before sending anything that can't.
  - **Share the reset request counts between API copies** (Valkey), as for sign-in throttling, and the per-account code and address-change limits and the hourly email cap (`AccountAttemptLimiter`, `EmailBudget`), which each copy also counts on its own.
  - **Wrap the data protection keys without Azure** (`ProtectKeysWithCertificate`, a certificate from a Secret, in the chart), so a cluster without Key Vault doesn't store them unwrapped beside the security stamps; today the API and `NOTES.txt` only warn (review of #86, finding 9).
  - **The page server in a Deployment of its own,** whose network policy allows only the API: on Azure it shares the API's pod, so it can reach the mail relay, the Key Vault and Microsoft Entra ID (allowed by name), which are shared services (review of #86, finding 4; threat model risk 5).
- **Two-factor authentication: what's left.**
  - **Hash recovery codes** (ASVS 6.5.2): Identity stores them in clear in `AspNetUserTokens`; a custom `IUserTwoFactorRecoveryCodeStore` could keep salted hashes. Encrypting authenticator keys at rest (data protection) is the same kind of change.
  - **Two-factor for everyone,** not just admins, as a setting (and on by default for new deployments), then **passkeys** (.NET 10 Identity) and single sign-on (roadmap step 4).
  - **A written procedure for resetting someone's two-factor** (how an admin checks who's asking), for deploying organisations (ASVS 6.4.4).
  - **The first admin set up with two-factor** at their first sign-in when the requirement is on (today they're held to set it up, like any admin).
  - **In-app notifications to admins** when an admin turns two-factor on, off or has it reset (today only by email, to admins with a confirmed address).
  - **Codes by email: a reset link gets past them** (threat model T-52, ASVS 6.4.3): for an account using them, "Forgot your password?" and the next sign-in code both go to its mailbox, so the mailbox alone takes the account over. **Accepted by the product owner on 18 November 2026** for this optional method; look at it again before first live use: send no reset link to these accounts (an admin resets them), or ask for a recovery code at the first sign-in after a reset by link.
  - **Codes by email: a rollback and roll forward can mix up the method** (the review of #118, finding 5): see `docs/agents/email-2fa.md`, two-factor, for the check to run after rolling forward.
  - **Codes by email, mail allowance:** codes have their own fifth of `Email:MaxPerHour` (plus whatever links leave), so on Azure's managed domain (8 an hour) a few sign-ins still use it up; a customer that wants codes by email needs a custom domain with a larger quota.
  - **Codes by email in the demo data:** `reset_demo_data` has no account using them yet.
- **File attachments: what's left.** Attachments are built (`docs/agents/attachments.md`). Still to do:
  - **A real malware scanner.** Every file is "Not scanned" today (`NoMalwareScanner`). On Azure, turn on Microsoft Defender for Storage's malware scanning for the attachments account (about £8 a month per account plus about 12p per GB scanned; `deploy/azure/README.md`), and have the API read its verdict (the blob index tag it writes, or its Event Grid event) into `ScanStatus`, holding downloads until a file is scanned. Elsewhere (kind, other hosts), a ClamAV container behind `IMalwareScanner`. Decide what staff see while a scan is pending.
  - **Purging deleted files' bytes** after a retention window (proposed: 30 days, for the DPO to decide; `docs/governance/retention-schedule.md`), a job on the scheduled job runner (`docs/agents/jobs.md`). Until then, deleted files' bytes are kept. The `DeletedAtUtc` index is there for it. Restoring a deleted file (admins) could come with it.
  - **The files themselves in the subject access export.** The export lists every file's details (deleted ones too), but not its contents; add them, for example as a ZIP beside the export's JSON, streamed from the file store and recorded as one export. Anonymisation already renames and deletes the files; their bytes go with the purge.
  - **Storage hardening on Azure:** a customer-managed key, and passwordless access (workload identity) instead of the account key in Key Vault, which needs the API's network policy to reach Entra ID (`deploy/azure/README.md`, "Not yet").
  - **Previews:** HEIC/HEIF thumbnails (SkiaSharp's Linux build can't decode HEIC), and a safe PDF preview (rendered to an image on the server, never shown inline). Today both are download only.
  - **Longer lists:** a list shows the newest 200 files of a patient, pathway or stage and says how many there are; page it if real use gets near that.
  - **E2E tests:** the `e2e` job runs without file storage, so no journey uploads a file. Add Azurite to it and a journey (attach, download, delete).
  - **Snapshots:** `medapp-dev`'s snapshots and demo data cover only the database, not Azurite's blobs.
  - **Check the storage connection string at startup.** A malformed attachments connection string (a mistyped Azurite key, say) isn't noticed until the first upload, which then fails with a 500 (a `FormatException` from `BlobServiceClient`). Validate it when the API starts, so a bad deploy fails at once with a clear message.
- **A customisable home screen.** Let each person arrange their home screen from "widgets" they choose, move and resize: for example today's calendar, My Worklist, overdue work, recent notifications, and the admin insights charts. The layout is saved with their account, like their other settings, and admins can set a default for everyone. Moving and resizing needs a keyboard and click alternative to dragging (WCAG 2.5.7).
- **Find accounts still using `DefaultPassword1`.** Accounts created before #53 got that published password, and may still have it; until this check exists, an admin should reset their passwords or ask their users to change them. Add a one-off check that tests each account's hash with Identity's `PasswordHasher.VerifyHashedPassword` (no side effects, and SQL can't do it because the hashes are salted), then for each match sets a generated password (or locks it), revokes its sessions and lists the usernames. As a `medapp-dev` tool for local databases, and as an admin report or API command (like `create-first-admin`) for deployed ones (PR #53 review, finding 1).
- **Refuse to delete an account with open work** (clinical hazard H-21, before first live use). Deleting a leaver's account leaves their open pathways assigned to "Deleted user", on nobody's task list. List the account's open assignments and refuse the delete until they're reassigned, as it already refuses an account with upcoming bookings. Deactivating accounts instead of deleting them (roadmap step 4) is the longer-term fix.
- **Deleting pathway notes: what's left.** Built: admins delete a note, with a reason (soft: hidden from the pathway page, kept with its versions, audited as `NoteDeleted`, on the admins' timeline and in the export); staff ask an admin to, with a reason (`PathwayNoteDeletionRequest`), every admin is told, and the request opens in a dialog (the note, the patient as the banner shows them, the pathway, who asked, when and why) with Delete note and Keep note; the requester is told the outcome. Clinical hazard H-38. Not built yet:
  - **Restoring a deleted note,** by an admin, with a reason, so a wrong deletion is undone on the page rather than copied back from the timeline (H-38's further control).
  - **A list of waiting requests** for admins, so none is left undecided once its notification has been read or cleared (H-38's further control). Today a request is only reached from its notification, or from the note's "Deletion requested" on the pathway page.
  - **Staff withdrawing their own request.**
  - **Telling the requester when a request is closed without a decision** (its pathway deleted, or the record anonymised); today they aren't told.
  - **Purging a deleted note's text** after a retention window, if the DPO decides deleted notes shouldn't be kept for the whole record's period (DPIA risk 4). Today a deleted note's text stays, for admins, until the record is anonymised.
  - **"Entered in error" as well as deleting:** a note still shown, struck through and labelled, for corrections that should stay visible to staff. Deleting hides it from everyone but admins.

## Testing

- **Before first live use, make CI and reviews strict again.** While MedApp isn't live, speed comes first, deliberately (the owner's decision, 18 November 2026): a pull request runs a light tier by default (#123), the integration tests, E2E, image scan and coverage thresholds run on `main` after the merge without gating Publish, merges don't wait for CI (admins bypass the required checks), and each merge gets one quick, low-effort review (`AGENTS.md`, CI and Git workflow). - **Known rough edges of the CI tiers** (#123), left for later:
  - **A broken commit can deploy to kind:** `main`'s full run and Publish start together. The issue "Full suite failing on main" is the only signal.
  - **A migration merges on the unit tests alone** unless someone asks for `ci:full`: nothing detects one. `ci:none` is honoured for anything but workflow, deploy, Dockerfile and package manifest changes; it trusts whoever adds it.
  - **A superseded run on `main` is cancelled,** so when two merges land close together, a failure is reported against the later commit only.
  - **The light web tier runs only the changed files' own tests** (`Page.tsx` runs `Page.test.tsx`), so a change that breaks another file's test is found on `main`. `vitest related` was tried and ran three quarters of the suite for one page, because the route tree imports every page.
  - **The full tier is as slow as `e2e` and `image`** (about 6 minutes each). `e2e` could build its tests and install Chromium while the image builds; `image` spends about 2 minutes exporting the build cache.
  - **A pull request's own dependency changes aren't audited by `npm audit` in the light tier** (dependency review and the image scan still run); `main`'s run and the nightly one are.
  - **Any label change restarts a pull request's run** (cancelling the one in progress), not only `ci:` labels; after a passing run it skips at once.
  - **The "nothing to test again" skip doesn't chain:** it needs the latest run of the commit before to have run the jobs itself, so a second docs-only push in a row (or one after a label change) runs the tier again. The `changes` job would have to record what a skipped run stood for.
  - **A full run starts 11 jobs at once** (GitHub allows this account 20), so two or three at a time queue: seen on 18 November, when a burst of Dependabot PRs stretched a 6-minute run to 23.
  - **Publish skips pushes that change only tests, `tools/`, docs or `.github/`,** so the environment branches lag `main` in those files until the next deploy.
- **Reloading with a half view open re-renders the page.** The half view's page is kept in the browser tab (`sessionStorage`), which the server can't read, so its render has no half view, the browser's first render has one, and every reload logs "Hydration failed" and rebuilds the page in the browser (`AppLayout`, `useState(() => storedPath())`). Otherwise it's only proven to translate (`PatientTimelineTranslationTests`) and run in memory (PR #64 review, finding 6).

Use Testing Library's own `reactStrictMode` option, give `renderApp` it too, then try `configure({reactStrictMode: true})` across the suite to find other effects that break when run twice (review of #109, finding 3).

- **Split `MedApp.Web/AGENTS.md` like the root one.** It's over 50,000 characters, loaded whenever an agent works in `MedApp.Web`. Keep its core rules there and move long component and page detail to `docs/agents/web-*.md`, with a Read before you change table, as the root `AGENTS.md` does.
