# CI workflows

What each CI job does, coverage, CodeQL, Dependabot and the supply chain rules: read before changing a workflow, a dependency gate or an action. The per-change rules are in the root `AGENTS.md` (Testing a change, CI, and Checking CI after a merge).

`.github/workflows/main.yml` (CI) runs on PRs to `main` in a **tier**, and in full on `main`. **The light tiers are a deliberate choice while MedApp isn't live:** speed first, and what a light PR missed is found on `main` and fixed afterwards (`docs/todo.md`, Testing, has what changes before first live use).
- **`changes` chooses the tier** from the PR's labels and its whole diff against its base (not the last push). The path rules are in one place, `.github/scripts/ci-plan.sh`, with a table of cases (`ci-plan.test.sh`) that `changes` runs first; it also checks `AGENTS.md` is at most 40,000 characters. The run's summary says the tier, what chose it and what's skipped. A job skipped by its `if` counts as passing a required check.
  - **`none`:** nothing builds or tests. Only docs changed (`docs/`, a `*.md` at the root, `tools/ui-parity/`), or the PR has the **`ci:none`** label (a small fix).
  - **Light, the default,** by the side that changed:
    - **Web** (`MedApp.Web/`): `web-checks` alone: lint, type check, the theme check, and the changed files' own Vitest tests (each changed test file, and the test beside each changed source file; no coverage). Not the tests that import them: the route tree imports every page, so `vitest related` ran three quarters of the suite for one page. The production build only if the PR changed what it reads beyond the source (`package*.json`, `vite.config.ts`, `tsconfig*.json`, `index.html`, `server/`, the entry files).
    - **.NET** (the projects, `MedApp.sln`, `global.json`, `tools/MedApp.DevMcp`, the browser demo's `MedApp.Browser`, `MedApp.Browser.Tests` and `tools/MedApp.BrowserDb`): `unit-tests`.
    - No `integration-tests`, `e2e` or `image`. A file no rule knows gets both sides' checks.
  - **Full:** the **`ci:full`** label (it wins over `ci:none`): everything for the sides that changed. A web-only PR runs no .NET tests, and a .NET-only one no web jobs; `image` and `e2e` run for either. Nothing adds the label automatically.
  - **Never light, whatever the label:** a change under `.github/` runs everything (a workflow change must prove itself); `deploy/` runs `helm`; the Dockerfile, `.dockerignore`, `.trivyignore`, `global.json`, the image's csproj files and `MedApp.Web/package*.json` run `image`. `ci:none` isn't honoured for those: the PR gets the default tier. `dependency-review` and CodeQL always run.
  - **Unsure means more:** a comparison that fails, or lists 300 files or more, is the full tier. If `changes` itself fails, every job runs, in full (each job's `if` skips only on a value `changes` set, and keeps `!cancelled()`).
  - **A label change starts a run,** so a label takes effect at once. Each PR has one run at a time: a newer one cancels it.
  - **Nothing to test again:** a push of only `docs/` (a review document), or a label change, skips every job when the latest run of that commit (the one before, for a push) passed with every job this one would run, and nothing has merged into the base since it started. A new file under `docs/` that a build or test reads would break this: put such a file elsewhere.
- **No automatic full suite** (the owner, 18 November 2026): pushes to `main` get the light tier (builds, lint, type checks, no tests). Run `gh workflow run main.yml -f tier=phase` (unit and web suites) at the end of each phase and `-f tier=full` (everything) at the end of each stage. A failure on `main` opens or updates one issue.
- **The six required checks keep their names** (`web`, `helm`, `unit-tests`, `image`, `integration-tests` and `e2e`), and mean "what the tier asked for passed". `web` and `integration-tests` are small jobs after the real ones, passing only if those did what the tier asks; a failed, cancelled or wrongly skipped one fails it. With nothing to run on their side, they're skipped too.
- `web`'s jobs check `MedApp.Web`:
  - `web-checks`: `npm ci`, lint, type check, the built theme is up to date; in full also `npm audit --audit-level=high` (high or critical fails, except IDs in `ACCEPTED`: see the supply chain rules) and the production build (`npm run build`: client, server rendering bundle, page server).
  - `web-tests` (full only): every Vitest test with coverage, in three shards (`--shard`, by file); each shard's thresholds are 0 on the command line, and it saves its results and coverage as a blob.
  - `web-coverage` (full only): merges the blobs (`vitest --merge-reports`) and holds the report to `vite.config.ts`'s thresholds, as one run of the whole suite would be.
- `image` builds `MedApp.API/Dockerfile` as Publish does, without pushing, sharing Publish's build cache. Trivy then scans it: findings with a fix go to code scanning (SARIF), and a critical one with a fix fails the job. Trivy runs from its own image pinned by digest (`TRIVY_IMAGE`), never `aquasecurity/trivy-action`, whose tags were hijacked in March 2026.
- `dependency-review` fails, and comments on, a PR adding or updating a dependency (npm, NuGet, actions) with a known high or critical advisory.
- `helm` lints and renders the chart (`deploy/helm/medapp`) in its main configurations (own SQL Server, kind's values with External Secrets and TLS, an external database, Azure's), and compiles and lints the Bicep (`deploy/azure`). It also renders Traefik, cert-manager, External Secrets and Argo CD at `deploy/versions.sh`'s versions with every values file and `--set` that `deploy/kind/up.sh` and `deploy/azure/bootstrap.sh` use: after changing one of those values files, run the same `helm template` locally.
- `unit-tests` builds the whole solution and `tools/MedApp.DevMcp` (not in `MedApp.sln`), then runs `dotnet test MedApp.UnitTests` in Release with coverage, and `dotnet test MedApp.Browser.Tests` (the browser demo's route coverage).
- `integration-tests`' three shards (`integration-tests (shard 1)` and so on) run `dotnet test MedApp.IntegrationTests` in Release, each with its own SQL Server and Azurite (Testcontainers). The first two run the namespaces in the job's `SHARD_1` and `SHARD_2`, balanced by time; **the last runs every test not in those namespaces** (a negated filter from the same lists), so a new namespace always runs somewhere. A shard that runs no test fails, and `integration-tests` adds up how many ran.
- `e2e` tests the production image under the chart's restrictions (read-only root with a writable `/tmp`, all capabilities dropped, no privilege escalation; one copy, no Valkey). It builds the image from earlier runs' cache (on a cold cache both it and `image` build from scratch), starts SQL Server and Azurite (the chart's image, for attached files: approving a letter files its PDF) on the runner's loopback with random masked secrets, migrates with `/app/efbundle`, runs `create-first-admin` with a generated password, starts the API on http://localhost:8080 and runs `MedApp.E2ETests`. Failed tests' traces are the `e2e-traces` artifact. The cookie stays `Secure` (browsers keep it from `http://localhost`).
- `coverage-comment` posts one sticky PR comment with the .NET classes and React files under 80% line coverage, only in the full tier (a light run measures none), with only the side that ran.
- **How long** (November 2026, without waiting for a runner): `none` under half a minute; light about 2 minutes for web (`web-checks`) and 2.5 to 3 for .NET (`unit-tests`); full about 6 (each integration shard about 5, the web jobs 4 in all, `e2e` and `image` up to 6 when the app's code changed). Before the tiers and shards, every PR took about 9. A full run starts 11 jobs at once, so several at a time queue for runners.

**Coverage** aims at everything with behaviour worth testing:
- **.NET** counts handlers, validators, domain logic, Infrastructure services and the API (controllers, middleware, authentication, server rendering). Excluded: commands, queries, DTOs, repositories, DbContext, migrations, generated code (`obj/`), the Aspire service defaults, wiring (`ServiceExtensions`, `ApplicationBuilderExtensions`, `Program`), and the services that are only SQL against the real database: `SessionService`, `IdentityTransactions`, and the role and permission queries (`RolePermissionQueries`, `PermissionHolders`, `LastAdminGuard`, `StandardRoleSetup`), covered by integration tests, uncounted.
- **React** counts `src/` except generated code, the theme build, test helpers, thin route files, the browser entry and the light demo (`src/demo`, never in the production build; it has its own tests). CI's `web-coverage` job (and `npm run coverage` locally) fails below `vite.config.ts`'s thresholds, just under today's figures (99% lines, statements and functions, 92% branches), in the full tier, so on `main` after every merge.
- New code comes with tests. Leave a branch uncovered only when it's unreachable or needs a real browser or database, and say so in the PR.

`.github/workflows/pages.yml` builds the light demo (`npm run build:demo`) and deploys it to GitHub Pages on each push to `main` touching `MedApp.Web/**` (or itself), and by hand: `build` with `contents: read`, `deploy` with `pages: write` and `id-token: write`, one at a time (`pages` concurrency group). See `docs/agents/light-demo.md`.

`.github/workflows/codeql.yml` runs CodeQL (C#, JavaScript and TypeScript, and the workflows) on PRs to `main`, pushes to `main` and weekly, into code scanning alerts.

`.github/dependabot.yml` proposes monthly grouped updates (minor and patch in one pull request per ecosystem, major versions in another) for GitHub Actions, NuGet, npm (`MedApp.Web`, `tools/ui-parity`) and Docker. Bump the Dockerfile's `ARG` image tags and `DOTNET_EF_VERSION` by hand: it can't read them.

**Supply chain rules:**
- **Pin every third-party action to a full commit SHA,** its tag in a comment (`uses: actions/checkout@<sha> # v4.4.0`). Resolve the SHA from the tag yourself (`gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, dereferencing an annotated tag), never from a README. Dependabot keeps them current.
- **Give each job only the permissions it needs,** at the job, not the workflow.
- **NuGet audit:** every csproj treats NU1903 (high) and NU1904 (critical) as errors, transitive packages too, so a new advisory fails the build until the package is updated. There's no `Directory.Build.props`, because the Dockerfile copies only the csproj files before restoring.
- **When a gate fails overnight** (an advisory with no fix yet, or a base image Microsoft hasn't rebuilt), don't switch the gate off. Accept that one issue for a short, dated time, in the same PR as a `docs/todo.md` entry it expires with:
  - **NuGet:** `<NuGetAuditSuppress Include="https://github.com/advisories/GHSA-…" />` in an `ItemGroup` of only the affected csproj, with a comment giving the reason, the date added and the review date (at most 30 days).
  - **npm:** an `overrides` entry in `MedApp.Web/package.json` forcing a fixed version of the transitive package, if one exists. If not, add the advisory's GitHub ID to the `web-checks` job's `ACCEPTED` (space-separated), with a comment on what it is and why it's safe to wait, and set `ACCEPTED_UNTIL` at most 30 days on. Only those IDs pass, and after that date the audit counts them again by itself.
  - **Trivy:** a root `.trivyignore`, one line per CVE with an expiry (`CVE-2026-12345 exp:2026-12-31`) and the reason in a comment above, passed to both Trivy runs (`--ignorefile /out/.trivyignore`). It stops being ignored on that date.

`.github/workflows/e2e.yml` runs the E2E suite by hand against a running app at a URL you give, as an admin from the `E2E_USERNAME` and `E2E_PASSWORD` repository secrets. **Those secrets don't exist yet: create them for a known deployment first.** Without them the run fails. It saves no traces, as they record the real credentials.
