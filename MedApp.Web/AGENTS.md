# AGENTS

Guidance for AI coding agents working in `MedApp.Web`, the React app replacing the Blazor client. The repo-wide rules are in the root `AGENTS.md`; the migration plan is `docs/react-migration-plan.md`. `README.md` describes the layout and scripts.

## MedApp conventions

- **Only Astryx for UI.** Components map 1:1 to an Astryx component, or are composites built only from Astryx primitives (plan section 4). No other UI library and no hand-rolled widgets; keep `style` overrides to layout values the components have no prop for, using tokens.
- **Icons:** `AppIcon` from `src/components/shared/icons.ts`, never `@remixicon/react` directly. Add new icons there.
- **Pickers open in a fixed place:** `AnchoredSelector` and `AnchoredMultiSelector` (`src/components/forms/AnchoredSelector.tsx`), never Astryx's `Selector` or `MultiSelector` directly (ESLint refuses them). Their list opens below the field (above only when it can't fit), scrolled to the selected option, the first option when nothing is. Astryx's `Selector` otherwise lays its list over the field, measured from where it was last scrolled, so a list scrolled and closed reopens somewhere else.
- **Routes** are thin files in `src/routes/` that point at a page component in `src/pages/`. Signed-in pages go under `src/routes/_app/`; a page that needs a permission uses `beforeLoad: requirePermission('ViewInsights')` (`src/auth/auth.ts`), which sends anyone without it to `/no-permission`, saying what the page needs.
- **Show what the person can do, by permission, never by role:** `useCan(permission)` (or `can(user, permission)`) from whoami's permissions, beside the API's own `can...` flags where a response has them (the API works those out from the viewer's permissions too). The permissions and their descriptions are in `src/auth/permissions.ts`, a copy of the API's catalogue that `permissionCatalogue.test.ts` keeps in step. Roles are only for showing (`src/auth/roles.ts`). A request the API refuses for a missing permission (`permission_missing`) shows the API's words wherever the page shows a refusal, and `PermissionMissingWatcher` says so in a toast and reads whoami again once no dialog is open. Tests sign in with `adminUser`, `staffUser`, `managerUser`, `nurseUser` or `userWithRoles(...)` (`src/test/render.tsx`).
- **Pages share one layout:** `Page` gives every page the same content width (`PAGE_MAX_WIDTH`), so titles and cards line up; don't pass `maxWidth` without a reason. A Back button (`backHref`/`onBack`) sits under the title, with `backLabel` as its tooltip.
- **Every page about one patient shows `PatientBanner`** under its header, through `Page`'s `banner` prop: the patient's page, Edit Patient, the export page, the patient's pathways, the pathway page, Edit Pathway and New Pathway so far, and any new page that shows or changes one patient's record. It's a clinical safety control (wrong patient), so don't put it inside something that folds or scrolls away: a page with a form taller than the window is a `fill` page whose form scrolls in its card under the banner (Edit Patient, Edit Pathway, New Pathway). The export page, a long printable document, is the one exception, and its banner heads the page. It words an appointment recorded after the event (`isRecordedAfterEvent`) as "recorded after the event … by …", never booked, with "requested" only for a visit that was waiting in Requires Appointment (`appointmentHistoryWords`, as `AppointmentDialog` decides), and its history's `RecordedAfterEvent` (with the outcome, and "was in Requires Appointment") and `EnteredInError` (with the reason) entries in words. `src/app/patientBanners.test.tsx` renders every route under `/patients/$id` and `/pathways/` and checks each has the banner; a new route there must be added to it. Pathway responses carry the patient (`patient`: `PathwayPatientResponse`), so a pathway page needs no extra patient read for it.
- **Fit the window; scroll the cards, not the page.** Pages that show more than a short form use `Page` with `fill`, and their cards fill the space. A card's open parts scroll inside it; the page never does.
  - The few pages that do scroll as a whole (Account Settings, the accessibility statement) line up with the rest: the main area always keeps room for a scrollbar on both sides (`STABLE_SCROLLBAR` in `AppLayout`), as each half of a half view does. Where scrollbars take up space (Windows), a page would otherwise move sideways as soon as it scrolls.
- **Build reusable patterns, not one-off page wiring.** When a page needs a layout or behaviour that another page could plausibly use, make it a composite in `src/components/` with its own test and a doc comment saying when to use it, then use it from the page. Look for an existing one first, and extend it rather than writing a near-copy. Signs a piece should be shared: you're reaching for flex or measuring code in a page, a second page wants the same thing, or the user describes it as a rule ("headers should look like…").
  - The shared building blocks so far:
    - `Page` and `PageHeader`: the frame, title and Back, and a `banner` under the header (the `PatientBanner`). The header's actions wrap under the title when they don't fit beside it (a phone, a half view). A page's own messages (load and save errors) go in its `message`, a rounded banner in the middle of the header, so they never push the content down: it starts from no width and takes what the title and actions leave (at least 12rem), wrapping its own words, so even a long one keeps the actions on the title's line on a wide screen. A long standing warning or note (one that stays while a state lasts: a restricted record, the retention review's specialty warning, a read-only pathway) is a `SummaryAlert` there, not an `AlertMessage`: errors (a failed load or save) stay `AlertMessage`s, in full. In a half view, Close half view sits outside the part that wraps, top right. Pass a page's actions as a fragment (or a wrapping group), never a group that doesn't wrap, so the header can wrap them among themselves. On a form, `ValidationAlert` takes the form's `fields` and lists only the messages that aren't already on a field.
    - `SummaryAlert` (`src/components/shared/`): a standing message as a short label in a status banner, with the key fact after it (`summary`: "Restricted record: changes paused"), so what matters most is on screen, and the whole message over the page in an Astryx hover card (`useHoverCard`, so its label can be a real button that also opens it on a click). The label is a button named "<label>: <summary>, show details", whose words wrap rather than being cut short with "…" (`LABEL_STYLE`); the overlay is on the popover colour, as menus are. The message opens on hover, keyboard focus, a click or a tap, stays while the pointer moves onto it, and goes on Escape or when the pointer or focus leaves (WCAG 1.4.13). A click only ever opens it; a tap's toggle is the hover card's own, so the click handler checks whether it was open when the press began, never the click's pointer type (iOS Safari reports a tap's click as a mouse's). Screen readers get the whole message without opening it: it's visually hidden in the banner and describes the button, and for a warning that hidden message alone is the alert (announced when it appears, as `AlertMessage`'s is), so the button and the open overlay are outside it and opening the overlay never announces it again. Each new use hides its detail, so decide what must stay on screen (`summary`, or a separate message where the user acts, as the booking dialog's refusal). Tests open it with `openAlertDetails(user, label)` (`src/test/render.tsx`, which finds the label with or without its summary) and look inside with `within`. Astryx's layers take Escape only while `:popover-open` matches, which jsdom never does, so a test of Escape stubs it (`SummaryAlert.test.tsx`).
    - `TwoColumns`: two equal cards side by side.
    - `useNarrowerThan(rem)` (`src/components/views/`): whether an element is narrower than a width in rem, from a `ResizeObserver`, false until measured (so the server's render matches). For a layout that depends on a card's own width, not the window's (the Calendar's compact week).
    - `PanelCard` and `PanelHeader`: a header bar, a scrolling body and a pinned footer. With `isBodyKeyboardScrollable`, a body that's scrolling is a Tab stop named by the title (`useOverflows` tells it when), for a body with nothing the keyboard could scroll it by, such as a chart or a table of numbers. Leave it off for bodies of fields, buttons or links.
    - `FoldingCard`: sections under header bars that fold, scrolling together as one (not each on its own).
    - `CardSection`: titled sections in `ViewCard` and `FormCard`, whose titles become header bars.
    - `FormCard` with `fill`: a long form whose sections scroll inside the card, its footer pinned.
    - `DataTable`: a filling, paged table.
    - `PathwayCells`: status, priority, due and progress cells.
    - `TextCell`: plain text in a table cell, kept to its lines.
    - `PageControls`: a list's page buttons (DataTable uses it); each "…" opens a box to type a page number.
    - `ListFilterBar`: a list's search as an Astryx PowerSearch, above its table (`DataTable`'s `search`): a token per filter, kept in the URL; choices take "is any of" and "is not any of". Every list with a search uses it, with a `list` key for its favourites.
    - `ListFavourites`: the star beside a list's search: the list's quick filters, and the person's saved searches (save, rename, delete, and one to start the list on), with the one showing said in the star's name and tooltip ("Favourites (showing My open work)"; a saved search's name wins over a quick filter with the same filters). Nothing sits beside the star: the bar's tokens show the filters.
    - `RowCards`: a table's rows as cards, which `DataTable` switches to by itself when its columns don't fit even at their narrowest.
    - `RichTextField` and `RichText`: formatted text (stage notes and instructions, pathway notes), edited with a toolbar (Astryx's `RichTextEditor`) and shown read-only (Astryx `Markdown`, which never runs HTML). It's stored as Markdown, so plain text written before reads as it was. Tests can't type into it under jsdom: use `setRichText`, `typeRichText` and `richText` from `src/test/richText.ts`.
    - `RuleSentence` and `describeRule` (`src/pages/monitoring`): a monitoring rule as a plain sentence with the choices in bold, used by the Monitoring page's list and its editor's preview, so they always agree. Each row's switch is named by that sentence (a switch's name stays put; its state says on or off), held still with `isLoading` while its own save runs, and handles its own outcome with `mutateAsync` (a mutation runs per-call callbacks only for its latest call).
    - `NotificationBell`: the bell beside the MedApp heading, with the unread count and a list of the newest. The count sits over the bell's top right corner (absolutely placed, letting clicks through), so the bell is one size with or without it, in the open side nav and its folded icons alike; it's hidden from screen readers, as the bell's name says how many are unread. A notification opens what it's about: a pathway's its page, an appointment's the Calendar on it, a meeting's its day there, with the meeting open (`?meeting=<id>`, when it has a `meetingId`: not a cancellation), an admin's "Note deletion requested" the request on its pathway's page (`/pathways/<id>?deletionRequest=<request id>`), and "Referral triaged" (one you registered, accepted, rejected or redirected by someone else: `referralId`) the referral. `LiveNotifications` (in `AppLayout`) keeps a SignalR connection to the API's notifications hub, so new ones show at once on any page. A notification with a `calendarDate` and no appointment or pathway (the meeting kinds, and `DayClosed`: a day closed with something of yours on it, with the closed day icon) opens that day on the Calendar (`/calendar?date=…&view=day`). `StageVisitWithdrawn` (a finished stage's only visit marked entered in error, with the entered in error icon) has no appointment, so it opens its pathway. Tests get a stand-in connection (`src/test/signalr.ts`): `liveHub.push('notification', …)` delivers one.
    - `PatientTimeline`: a patient's history across their pathways and appointments (the patient page): what's due, filter chips by kind and pathway (`ToggleButton`s), and the feed by UK day with "Load more" (an infinite query, `src/api/timeline.ts`). It sits in a card's scrolling body and lays out its own padding; the page holds its filters. The API decides what staff and admins see, so it shows whatever comes back.
    - `PathwayNotes` (`src/components/pathways/`): a pathway's notes, in their own folding section of the pathway page: Add Note (a `RichTextField`; Ctrl+S adds it, through `useSaveShortcut`), then every note, newest first, with who wrote it, when, "Edited" with when, and its text (`RichText`). Your own notes have Edit (`canEdit`), which sends the version it started from; a 409 (someone, or another tab, saved it first) shows the API's message with Reload. Only while the pathway takes notes (`canAddNotes`). Delete (`canDelete`) and Request Deletion (`canRequestDeletion`) follow the API's flags, which are for the signed-in user (admins delete, in any status; everyone else asks; neither while the record is restricted or anonymised), with no role check of their own. Each opens a `ConfirmDialog` showing the patient (a compact `PatientBanner`: the dialog covers the page's) and the note, and asking why: a required choice and an optional detail (`NoteDeletionReasonFields`, with the reasons and their words in `src/api/noteDeletion.ts`; the detail is 500 characters, required for Other; the API's 400 shows on `reason` and `detail`, a 409 in its words, after which the pathway is read again). Delete sends the note's `version` as `expectedVersion`, so a note edited since is refused. Deleting is soft, so the note just leaves the list (`useNoteDeletionActions`). A note with a waiting request (`deletionRequestId`) shows a "Deletion requested" token, with admins' Review Request kept beside it (they wrap together). Every note's buttons are named for their note (`noteButtonName`: "Delete note by k.ashford, 3 Nov 2026, 10:32"), each starting with its visible words, so a screen reader tells them apart. Saving goes through `usePathwayNoteActions` (`src/api/pathways.ts`), which puts the note into the cached pathway at once, so it shows wherever that pathway is open. Notes are no longer a field of Edit Pathway; New Pathway's Notes box becomes the first note.
    - `NoteDeletionRequestDialog` (`src/components/pathways/`): a member of staff's request to delete a note, for an admin to decide (`noteDeletionRequestQuery`, `useDecideNoteDeletion`; reading it is recorded as a view). It shows the patient as `PatientBanner` does, the pathway's title, the note (`RichText`, with its author, time and when it was edited, and a warning when that was after the request: `editedSinceRequest`), and who asked, when and why, then **Delete note** (with a reason and detail, `NoteDeletionReasonFields`, that start as the requester's and can be changed, sending the shown note's `version` as `expectedVersion`) or **Keep note**. A request it can't decide (decided already, a restricted record, a deleted pathway) shows its outcome or why instead of the buttons; a 409 shows the API's words and reads the request again. Its loading spinner is silent (`aria-hidden`, with its words beside it), as an announcing one leaves its words in a hidden status region. The pathway page opens it from `?deletionRequest=<id>` for admins (`parsePathwaySearch`; closing it takes it out of the address), and `PathwayNotes` from a note's Review Request. It shows only over its own pathway's page (`pathwayId`): a request about another pathway's note goes to that page instead (`onWrongPathway`, the route's `onDeletionRequestElsewhere`), or just closes. Deleting the wrong note is a clinical hazard (`docs/clinical-safety/hazard-log.md`), so keep everything it shows.
    - `StageSkipDialogs` (`src/components/pathways/`): pathways that branch (`docs/centre-phases-3-5-plan.md`, decisions 113 to 117). `SkipStageDialog` skips an optional current stage (`canSkip`): the patient as `PatientBanner` shows them (compact; hazard H-51), the stage, and a required reason from `STAGE_SKIP_REASONS` (`src/api/stageSkips.ts`: Not needed, Patient declined, Other; none chosen) with a detail (500 characters, required for Other). `ReinstateStageDialog` (`canReinstate`, holders of OverrideStages) asks why (required, 500 characters). `BranchChoice` is the branch question in both finish dialogs for a stage with `needsBranchChoice`: **the clinician chooses, MedApp never does**, so the branches are a radio group in the template's order, none chosen, each with its stages' names, Finish disabled until one is chosen, then which stages it skips; the finish sends `branch`. A 400 shows on the dialog's fields, anything else in the API's words. Skipped stages are struck through (`Text`'s `hasStrikethrough`) with "Skipped: <reason>" (`skipReasonLabel`; `BranchNotChosen` is "Another branch was chosen"), and who, when and the detail inside the stage; optional stages, branch points and branches have tokens. Progress counts skipped stages as done ("3 of 5, 1 skipped"). The template editor gives each stage Optional and Branch point boxes and, after a branch point, a Branch name, indenting the stages in a branch; it sends `stageOptions` only when a stage has one, and says on the stage what the API would refuse (`src/pages/setup/templateBranches.ts`, in the API's words).
    - `TriageDialog` (`src/components/referrals/`): the frame of every triage decision on the referral page (`AcceptReferralDialog`, `RejectReferralDialog`, `RedirectReferralDialog`, each mounted only while open, so its choices start empty): a form step, then **Check and Confirm**, which shows the patient as `PatientBanner` does (compact), the specialty, the date received and every choice before anything is sent, with Back to change them (hazard H-41). **The clinician decides; the app records:** nothing is prefilled or suggested. Accept lists only the referral's specialty's templates (`templatesFor`: not archived, with stages, by name, never ranked), an empty priority with "The referrer asked for: High" as its description, an empty target date, an optional title, an assignee for holders of AssignPathways only (people with WorkPathways) and a first note; it opens the new pathway. Reject takes a reason from `REFERRAL_REJECTION_REASONS` (none chosen) and a detail (required for Other); Redirect, another specialty here (not archived, not its own) or elsewhere, with why. A 400 goes back to the form with its errors on the fields; a 403 or 409 stays in the dialog in the API's words, and the referral is read again (`useAcceptReferral`, `useRejectReferral`, `useRedirectReferral` in `src/api/referrals.ts`). The page shows Accept, Reject and Redirect in its Triage section only while `canTriage`, and `whyCantTriage` otherwise; under it, **This patient's other referrals** (`PatientReferrals` with `exceptReferralId`, the same specialty's marked), so a duplicate is seen before deciding (hazard H-44). A pathway accepted from a referral links back to it on its page ("From a referral received …", `pathway.referral`, which only the pathway's own read fills: `cachePathway` keeps it when a change's response leaves it out). The Specialties page warns, in the row and above the list, about any specialty in use that nobody can triage for (`triagerCount` 0: hazard H-40).
    - Letters (`src/components/letters/`, decisions 100 to 108; `src/api/letters.ts`): `LettersAbout` is a pathway's or referral's Letters part (its letters, each linking to `/letters/$id`, and Write Letter for holders of WriteLetters, which opens `WriteLetterDialog`: a template of the specialty or every specialty, from a referral only replies and requests for more information, nothing chosen to begin with, then the new draft's page). The letter page (`src/pages/letters/LetterPage.tsx`) edits its author's draft (letterhead, Markdown body with the template's headings, closing, large print and `RecipientsEditor`, saved together from the version the draft started from) and offers only what the response's `can...` flags allow, each from a dialog in `LetterDialogs.tsx` that shows the patient as `PatientBanner` does; Approve also lists every recipient with their address (hazard H-48). `RecipientList` shows each recipient's dispatch once it's approved, with Send by Secure Email or Record as Sent. The Letters list (`/letters`) has its views as tabs, `view` in the URL.
    - The notepad (`src/components/notepad/`): each person's own jottings, kept on the server (`notepadQuery`, `useSaveNotepad` in `src/api/notepad.ts`), never in the browser. `NotepadProvider` (in `AppLayout`) holds whether it's open (remembered in `medapp.notepadOpen`, read after mounting) and the pathway pages open (`useOfferToNotepad(pathway)`, which the pathway page calls, with its half view's side). The side nav's **Notepad** item (in the account footer, so in a phone's drawer too) opens and closes it. On a window 1024 px wide or more it's docked on the right of every page (`NotepadPane` in a column of `AppLayout`, `data-notepad-docked`, a labelled region rather than a landmark, as it's inside `main`), and pages beside it take their narrow layout only when the room left is narrow (`NARROW_BESIDE_NOTEPAD_QUERY`, in `useIsNarrow`). The page always sits in the same wrappers (`display: contents` while the notepad is closed), so opening or closing it never rebuilds the page; narrower, it's a full-screen sheet (`NotepadSheet`, an Astryx `Drawer`). `NotepadPane` saves by itself 1.5 s after typing stops (`AUTOSAVE_MS`), on Ctrl+S (`useSaveShortcut`), before closing (`registerCloser`: it stays open if that save fails), before signing out (`onFlushSettings`) and as it unmounts (crossing between docked and sheet), one save at a time; with nothing typed, it reads the notepad afresh when the tab is shown again. Opened from the side nav (a toggle, `aria-pressed`), it takes the focus, and gives it back on closing; it shows "Saving...", "Saved 10:32", or what went wrong with Retry, or with Reload after a 409. **Add Note to Pathway** adds the selection (as Markdown, from `RichTextField`'s `selection()`) or everything as a note through `useAddPathwayNote`, after `AddToPathwayDialog` (the patient as `PatientBanner` shows them, the title and the text; which pathway, with two open; "Remove it from the notepad" ticked when the text can be taken out exactly, by its position, and off with a reason otherwise): hazard H-37. The box has no prompt or explanation text (the product owner removed them; the staff privacy notice says what it's for).
      - **In a half view:** the Notepad row's menu (`RowMenu` with `isRightOnly`: only on the right, keyed `data-nav-row="/notepad"` as the row has no link) opens `/notepad` (`src/routes/notepad.tsx`, `NotepadPage`, outside `_app` behind `requireSignedIn`) in the half view's router. There it's a region (no main landmark or tab title of its own) inside the signed-in layout's `NotepadProvider`, with a provider of its own (`NotepadProvider onCloseHalf`): always open, nothing kept in `medapp.notepadOpen`, the focus in its box as it opens, Close saves then closes the half, and Add Note to Pathway offers the layout's pathway pages (the page beside it), with the same dialog. It closes the docked notepad as it opens, and the side nav's Notepad toggle closes the half view showing it before docking it (`HalfViews.close`), so the notepad is never twice side by side. Closing the left half while the notepad is on the right docks the notepad (`AppLayout`). **There's no separate window** (the product owner's decision, after a review found the pop-out outlived signing out): `/notepad` opened on its own (typed, or an old pop-out reopened) stores the notepad as open and goes to `/` in an effect, so the docked notepad opens there; the server renders only a spinner for it, and doesn't read the notepad.
    - `StageVisit` and `StageVisitTokens`: a stage's visit (a stage that involves one): the Visit part of the current stage's work (`StageWork`'s `visit`: where it stands, and Book Visit, Reschedule, Attended or Did Not Attend, Book Another, and while nothing is booked Record Past Visit), and the tokens beside a stage's title (`StageTitle`'s `extra`, `StageList`'s `renderVisit`). `stageVisit` works out where a stage's visit stands from the pathway's appointments (Cancelled and Entered in error ones never count), and `finishesWithoutVisit` whether finishing it needs the without-a-visit confirmation.
    - `AppointmentList`: a few of one patient's or pathway's appointments (status, when and with whom, what for), each opening on the Calendar.
    - `CalendarGrid` (`src/components/calendar/`): time as a grid of columns, 08:00 to 18:00 in 15-minute rows (or 5-minute ones, `rowMinutes`, as tall, so the day scrolls inside the grid, with smaller quarter-hour times down the side, never fainter: they must pass 4.5:1; dragging a selection, Shift and the arrows go a row at a time, but a click or Enter alone selects 15 minutes; switching keeps the same time at the top, and the keyboard's place on the same time), with appointments, blocked time and meetings placed by time (generic items: `calendarItems.ts` makes them from a calendar, a meeting with its icon and "N attending", or, on the calendar of someone who declined it, faded (`isFaded`: plain, a dashed edge, behind the rest, words at full contrast, in the last 40% of its share of the column's width) and saying "Declined"; a faded item's rows aren't taken, so the free slots beside it select by pointer and keyboard, as the server sees that time, and the card still opens with a click or Enter; blocks are movable only with its `movableBlocks`, the Calendar page's Edit blocks, and a template block only within its own day, `movesWithinDay`). Each column is `{key, label?, date, day, items, freeTime?}`: `dayColumns(days, items)` makes one person's day or week (unlabelled, named as days), and the Calendar page's team view gives a labelled column per person ("k.ashford, Tuesday 17 November") after an "Everyone free" column whose `freeTime` is the only time it lets you select (the rest is shaded, each free stretch labelled "Free, 10:00 to 11:00"). On a closed day "Everyone free" is greyed and labelled "Closed: …" like the person columns, with nothing to select: the team response's own `day` doesn't know the day is closed, so the page takes `closedDayName` from the members' days. Selections and moves say their column (`CalendarSelection.column`; `onItemOpen(item, column)`), and `keepsItemsInColumn` stops an item being dragged to another person. A dragged item moves a row at a time from where it is and keeps its exact length (10:05 to 10:25 a row down is 10:20 to 10:40); a press whose pointer moves less than 5 px (`DRAG_START_PX`), or never leaves the row and column it pressed, is a click, and opens it, even on an item that has started (which can go nowhere); a movable item's words can't be selected (`user-select: none`), as Astryx's `ClickableCard` ignores a click while its text is selected. The free slots are a memoised component with stable handlers, so a drag doesn't redraw them. More columns than fit scroll sideways inside the card, each keeping a minimum width, with the hour gutter sticky. A selection made with the pointer reaches `onSelectRange` just after the press ends, so a menu opened from it (the Calendar page's Book or Block, or New meeting in "Everyone free") isn't closed by that same press as one outside it. A held selection is a button (`selectionRef`, not a tab stop, letting presses through to the slots), because Astryx's `Popover` only anchors to a button: anchored to anything else, it opens in the window's corner. Both are from PR #96, and hold in every column. Selecting free time (click, drag, or the keyboard: one tab stop, arrows, Shift to extend, Enter), opening items and dragging movable ones are callbacks, so leaving them out makes it read-only. `isCompact` squeezes a week into a narrow card (the Calendar page's compact week, with `dayColumns(..., {weekdaysOnly: true})` leaving out the always-empty weekend): a narrower gutter and columns, each headed by its weekday over its date (naming its full date to screen readers), and items whose words wrap to the lines their height allows, in full in a tooltip; a card under 4.5rem wide (a phone) shows its start time instead, with its name under it when it's two rows or more tall, as do selections and dragged items (time only; CSS container queries). "Not a working day" ("Closed: Christmas Day" on a closed day, `notWorkingWords`) sits at the top of its column, sticky, so 5-minute rows' taller day never hides it. A closed weekday (the day's `closedDayName`: a bank holiday, `isWorkingDay` false) is greyed like a weekend, with nothing to select or drop on, but keeps its full width, its heading (which opens the day) and its place in a compact week, as it may hold what was put there before it closed: the grid flags those items itself, as an overlapping block is flagged, their name and tooltip ending ", on a closed day". A meeting an appointment overlaps (`overlapsAppointment`: one recorded after the event may) is flagged the same way (`meetingItem`). A grid with nothing the keyboard can reach inside its scrolling area (a read-only day, Home's) makes that area a tab stop of its own, named "<label>, scrollable". It opens on the time now when today is shown and the working day is under way, otherwise at the day's start. Past time is dimmed and today tinted, with the line for now (behind items, so it never strikes through their text) added after mount, so server and browser renders match. Items list their name, then what they're for, then their time; one under 10 minutes shows its words only in a tooltip. Astryx has no time grid: its cells are plain elements on theme tokens, its items Astryx cards.

  - Pins in the side nav are a setting too (`medapp.pins`), so they follow the account rather than staying in the browser. Their labels come from the labels lookups (`patientLabelsQuery`, `pathwayLabelsQuery`), which record nothing in the activity log; never label a pin from a record's own endpoint, which records a view.
  - **Signing out first saves any setting still waiting to be saved** (`flushSettings`, which `SettingsSync` registers a flusher for), then signs out and clears the browser, so a pin made just before isn't lost.
- **Accessibility:** the aim is WCAG 2.2 AA (`docs/todo.md` lists what's left; the statement is `/accessibility`).
  - The settings in `src/app/accessibility.tsx` work through CSS that `AccessibilityProvider` adds: theme tokens on every theme root, and a few rules, outside Astryx's cascade layers so they win. A new component that uses Astryx tokens and components follows them without more work. Don't hard-code durations, focus rings, font families or control heights.
  - Pages name themselves: `Page` sets the browser tab's title and announces the page to screen readers (`usePageTitle`). Announce other changes people see but a screen reader wouldn't mention with `useAnnounce()`. `DataTable` already announces a list's results, every form page announces its save ("Patient saved", "Stage added", and so on, said before it navigates away, so the next page's name follows it), and the pathway page announces a finished stage and the next one, and a deleted pathway. A new form or action that saves and moves on does the same.
  - Statuses and priorities go through `StatusToken`, `PriorityToken` and `OverdueToken`, which add icons when "Icons on statuses" is on.
  - Custom colours (Account Settings, Colours) are checked as they're picked: a page, card (with its header bars) or side nav colour that leaves the main or the secondary text under 4.5:1 gets a warning on its field (`textContrast` in `src/app/colours.tsx`, with the WCAG maths in `src/utils/contrast.ts`). If the theme's text colours change, change `TEXT_COLOURS` too; a test compares them. Three bundled themes are just under on secondary text (`docs/todo.md`).
  - Sessions time out (WCAG 2.2.1): `SessionTimeout` in `AppLayout` warns five minutes before, with the time left and Stay signed in, and on timing out goes to the login page, which says why (`/login?expired=true`).
  - Keyboard shortcuts are in `KeyboardShortcuts` (`?` lists them). They start off, and never fire while typing in a field or a dialog; keep both true for new single-key ones.
    - The one exception is save, Ctrl+S (⌘S on a Mac; `SaveShortcut.tsx`). It has a modifier, so it can't fire by accident while typing (WCAG 2.1.4 is about single keys): it's always on, whatever the shortcuts switch says, and works from inside a field. It saves the form holding the focus, or the page's only form; never the page behind a dialog, and nothing when it can't tell which of two forms (a half view) was meant. While any form is open it always stops the browser's Save page dialog, and when it then saves nothing (no form chosen, or nothing changed) a brief toast says so, which screen readers hear too. A `save` that has nothing to do returns `false`.
    - `FormCard` joins by itself. Anything else that saves joins with `useSaveShortcut(ref, save)`: the stage notes (`StageWork`) do, and a `ConfirmDialog` that is a form passes `hasSaveShortcut` (Add or Edit Stage). Dialogs that only ask "are you sure?" don't.
  - Run the axe audit (`npm run a11y` in `tools/ui-parity`, with the AppHost running) on the screens every visible change touches (`-- -g "<screen>"`). The run of every screen takes about ten minutes, so it's only for when the user asks. Add new screens to `screens.ts` so it covers them.
- **Server-side rendering:** every page is rendered on the server first (`src/entry-server.tsx`, `server/server.mjs`; see `README.md`), then hydrated, so:
  - **Rendering must work without a browser.** Don't touch `window`, `document`, `localStorage` or `matchMedia` while rendering: do it in effects, or behind `typeof window`. Read settings with `useAppSetting`, which uses the account's saved settings on the server.
  - **A page with data gets a loader.** Its route's `loader` preloads the same query the page reads: `preload(context.queryClient, query)` (`src/api/preload.ts`). Put the query in an exported function that the page and the loader both call (`patientsListQuery`, `pathwaysListQuery`), so their keys match. List settings outside React come from `listSettingsFor(queryClient)`. On the server the loader waits; in the browser it only starts the fetch. A feed fetched a page at a time (`infiniteQueryOptions`, e.g. `patientTimelineQuery`) preloads its first page the same way.
  - **The first render must match the server's.** Nothing random or time-based in render output that isn't the same on both. Anything that depends on this browser shows after mount.
  - `src/entry-server.test.tsx` renders whole pages as the server does (in Node). Extend it for anything server-specific.
- **List pages** fill the window: `Page` with `fill`, and `DataTable` stretches to the bottom with its page controls pinned there. Their search is a `ListFilterBar` above the table (no Search button or dialog); a list that starts filtered (My Worklist on Not started, Stages and Templates on Active) shows that filter as a token and keeps an "all" value in the URL for when it's removed. They keep page, sort and filters in the URL: the route parses them with `validateSearch` (`src/pages/listSearch.ts`), then passes `search` and `onSearchChange` to the page as props, so pages are testable without the real router. Lists come from the API's paged search endpoints (`src/api/search.ts`).
- **Colours:** people choose the page, card and side nav colours for each mode (Account Settings, Colours: a colour theme, or Custom). `ColoursProvider` (`src/app/colours.tsx`) applies them through the theme's own background tokens (`--color-background-body`, `-surface`, `-card`, `-muted`, `-popover`). The side nav is always dark (a nested dark `Theme` in `AppLayout`).
  - **Every new component, page and surface must follow the chosen colours.** Use those tokens (or Astryx components, which do), never fixed colours or a theme's own defaults. Header bars use `-muted`, cards `-card`, menus and popovers `-popover`.
  - Scrollbars follow too: `src/app/scrollbars.css` (loaded by `entry-client.tsx`, after Astryx) sets `scrollbar-color` on every element from the theme's emphasised border token on a clear track, so each takes its own theme's colour (the side nav's dark one) and the surface shows through. Their width stays the browser's.
  - A surface that needs a chosen colour the theme doesn't route through a token: add the token to `ColoursProvider`, from the chosen colours, rather than hard-coding it.
  - Inside the side nav, the dark `Theme` sets its own tokens, so a surface there that should follow the app (a row's menu) uses `--medapp-card-background` and takes the app's mode (see `RowMenu` in `AppSideNav.tsx`).
  - Check a new component in light and dark mode, and with a colour theme other than Standard (Account Settings, Colours), before calling it done.
- **Data:** TanStack Query. Reads are queries keyed by resource (`['patients']`, `['patients', id]`); writes are mutations that invalidate them. Call the API through `api` + `unwrap` from `src/api/client.ts`.
  - **Times from the API** (`...AtUtc`, `createdAt`, `lastUpdated`) are UTC: show them with `formatDateTime` or `timeAgo` (an appointment's time with `formatAppointmentTime`: "Mon 23 Nov 2026, 10:00 to 10:30"), and turn one into a `Date` with `parseUtc` (`src/utils/dates.ts`), never `new Date(value)`, which reads a time without a `Z` as the browser's local time. Dates (`yyyy-mm-dd`: target dates, dates of birth) are whole UK days: `formatDate` and `formatShortDate`. `dueDateUtc` is a moment (the end of the due day, UK time), for comparing with now; show `dueDate`. Tests run in New York time (`vite.config.ts`), so a time misread as local fails them.
- **Forms:** fields in `useState`; on a 400, show `fieldStatus(errors, field)` on each field. The server's FluentValidation is the source of truth, so don't duplicate its rules here. The one exception is the NHS number's check digit (`NhsNumberField`), checked as it's typed so a mistyped number is caught before a lookup or a save; the server checks it too.
  - Fields side by side line up: Astryx puts a description between the label and the input, so when one field in a row has a description, give the others `BLANK_DESCRIPTION` (`src/components/forms/fieldSpace.ts`). Do the same for a description that comes and goes, so the input doesn't jump.
  - Nothing moves when an error shows: the theme gives every field a reserved, empty line under its input that its error message fills. A field that never shows an error can drop it with `containerStyle={NO_STATUS_LINE}`.
- **Tests:** every component and page gets a Vitest test next to it (`X.test.tsx`). Use `renderWithApp` / `renderApp` and `mockFetch` from `src/test/render.tsx`. Synthetic data only, and NHS numbers only from the 999 range, which is never issued to real people.
  - **Effects must survive running twice.** In development the app starts inside `<StrictMode>` (`entry-client.tsx`), which runs every effect, cleans it up and runs it again at once. An effect that reads and clears something (the address's fragment), or cleans up a cache, must keep the first result and not lose or fetch it again. Test such an effect with `renderWithApp(..., {strict: true})`; the production build, which CI's E2E tests, runs effects once and won't catch it (review of #109).
- **Before calling a change done,** check only what you changed, as CI runs everything (root `AGENTS.md`, Testing a change):
  - the changed files' tests (`npx vitest run <files>`)
  - `npm run typecheck`
  - ESLint on the changed files (`npx eslint <files>`)
  - for a visible change, with the AppHost running (start it if it isn't): the UI parity screenshots of just the screens you changed (`npm run parity:react -- -g "<screen>"` in `tools/ui-parity`), looked at, and the axe audit of those screens (`npm run a11y -- -g "<screen>"`)
- **Versions:** `@astryxdesign/*` are pinned exactly (plan Q14). Upgrade them only in their own PR, after reading the changelog, then run `npx astryx upgrade` and `npm run theme:build`.
