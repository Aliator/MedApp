# Review: PR #157, the Roles and Permissions page

**PR:** [#157](https://github.com/Aliator/MedApp/pull/157), branch `feature/roles-page`, security review at `da8175b` on 18 November 2026, fix and `main` (#155, #156) merged in the commit after. No critical or high findings; one low, fixed in the PR.

Admins manage roles at `/admin/roles` (`api/roles`, `api/permissions`): make, change, archive, restore and delete roles and choose their permissions. The built-in Admin role refuses every change (409); the Administrator-only permissions are refused on any other role (400); a role someone holds is archived, not deleted (409). Each change carries the role's version (`ConcurrencyStamp`), is recorded as `RoleCreated`/`RoleChanged = 44`/`RoleDeleted` through `ISecurityEventLog` in the change's transaction (permission names only), and is emailed to the other admins. The Users page's picker reads `api/roles` (roles not archived, with descriptions). `ManageClinics` (#156) shows in its group (Appointments and calendars) with no change, as the page groups from the catalogue.

**Finding (low, fixed): deleting a role could silently take it from someone being given it.** `RoleRepository.DeleteIfUnheldAsync` (`MedApp.Infrastructure/Data/Repositories/RoleRepository.cs:132`) checked `NOT EXISTS` on `AspNetUserRoles` with a plain read. The database uses read committed snapshot, so the check read the last committed rows and missed another admin's grant (`PUT api/auth/users/{username}/roles`) saved but not yet committed; the role's delete then cascaded through `AspNetUserRoles`, waited for that grant, and removed it, with the grant's admin told it succeeded. **Fix:** the delete is one raw SQL statement whose check reads `AspNetUserRoles WITH (UPDLOCK, HOLDLOCK)` (`RoleRepository.cs:140`), inside the handler's transaction (`DeleteRoleHandler.cs:34`): it waits for the uncommitted grant, sees it and refuses (409), and holds the role's key range until it commits, so a grant made after the check fails on the missing role instead of being cascaded away. No migration. `RoleManagementTests.DeletingARole_WhileAnotherAdminIsGivingItToSomeone_WaitsForThem_AndKeepsTheirGrant` (`MedApp.IntegrationTests/Auth/RoleManagementTests.cs:149`) holds a grant uncommitted on its own connection while the delete runs; it fails on the old code (204, grant gone) and passes now (409, grant kept).

**Remaining risk:**
- No step-up (the admin's password again) before a role change, as for other admin actions (ASVS 7.5.3; `docs/todo.md`).
- The confirmation's "This changes what N people can do" counts everyone holding the role, including people another of their roles already gives the same permission (`holderCount`; an exact preview is a to-do).
- A grant racing a delete now ends in an error for the grant (the role is gone) rather than a silent loss; the admin reloads and sees the role has been deleted.
