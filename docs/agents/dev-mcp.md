# Dev MCP server (`medapp-dev`)

The `medapp-dev` tool and the demo data: read before using it beyond its tool descriptions, or changing it or the seed.

`.mcp.json` registers `medapp-dev` (`tools/MedApp.DevMcp`) and the Astryx docs MCP (`astryx`).

**Use `medapp-dev` for local account and app-state chores,** not hand-written SQL or one-off programs: dev accounts (create, reset, unlock, roles, sign out), synthetic patients, migrations and row counts, snapshots of the whole local database, the demo data (`reset_demo_data`), and running a scheduled job now (`run_job`). It only runs against a local database (by default the AppHost's SQL container, with the password from the AppHost's user secrets, so the AppHost must have run once). It protects `admin`; destructive tools need `confirm: true`. **Roles:** `ensure_test_admin` gives `admin` Admin alone, read only (and adds any missing standard role); `ensure_test_staff` makes the test staff for clinical work, `<prefix>-clinician` (Dermatology's clinic admin) and `<prefix>-lab` (the lab's pathologist), with their roles, team and a returned password (run it again after `reset_demo_data`); `create_user` and `set_roles` take any role's name; `list_roles` shows each role's description, flags and permissions; `reset_demo_data` gives the demo staff the starting role for their job and puts the standard roles' permissions back as they start (`StandardRoleSetup`).
- **Before a destructive experiment:** take a `save_snapshot`.
- **Build it first:** `dotnet build tools/MedApp.DevMcp` (`.mcp.json` runs it with `--no-build`).
- **While it runs, `dotnet build MedApp.sln` fails** ("file is locked by: MedApp.DevMcp"): the test projects reference the tool, which isn't in the solution, so a solution build rebuilds it as Debug into the running tool's folder. Build and test in Release (`dotnet build MedApp.UnitTests -c Release`). After a change to the app's rules or the seed, stop it in `/mcp`, run `dotnet build tools/MedApp.DevMcp`, and start it again.
- **Demo data comes from one script, never by hand:** `tools/seed-demo-data.sh --confirm --keep-users dev-parity` (or `.ps1`) builds the seeder, checks the database is local, applies pending migrations, then runs `dotnet run --project tools/MedApp.DevMcp -c Release -- seed-demo` (the same code as `reset_demo_data`, `DemoDataReset`, under the same guard; `--help` lists its options, such as `--out` for the summary and `--save-snapshot` for kind). Never add demo or dummy records with SQL, `HasData`, a test or through the app: change the seeder and run the script. `seed_patients` and `create_patient` make a throwaway record while trying a screen; they aren't demo data.
- **`reset_demo_data`** (`tools/MedApp.DevMcp/DemoData`) wipes the data and loads **the light demo's clinic** (`MedApp.Web/src/demo`): Dermatology, the Eye clinic and the lab, the same people (with the same usernames, roles and teams; `admin` holds Admin alone, read only), Dermatology's reviewed templates and the tour's relay (`DemoDermatology`) and the Eye clinic's draft ones (`DemoOphthalmology`, `docs/pathways/ophthalmology.yaml`), mapped by the same code (`DemoTemplates`), the Eye clinic's story in `DemoEyeClinic`, and the same patients and pathways at the same points, with their referrals, visits, consent, samples, lab cases, hospital requests, results, letters, MDTs, a consult, calendars and clinic sessions. Dates are relative to the day it runs. It refuses a database with pending migrations (the script applies them). It returns the generated passwords and the tour's record IDs. Locally, pass `keepUsers: ["dev-parity"]`. What's in it, and what the full app can't hold as the light demo does: `docs/demo-data.md`.
  - **Everything goes through the app's handlers** (`DemoReplay`, `DemoStory`, `DemoLab`, `DemoClinic`), sent as the person who did the work, with their permissions and team walls (`DemoPerson.Actor`), at a moment the seed's clock moves to: so the handlers' gates, walls, audit entries, notifications and grants are the app's. Clinical work is done by staff in their teams, never the admin (read only) or the system. Only the stage library and templates are written directly (as the admin set them up), and the relay's Triage gates (no command changes a pathway stage's gates).
  - **A change to the light demo's data changes this seed in the same PR, as near as the model allows.** When the app's rules change, the seed may be refused: run it (the script, or against a throwaway LocalDB database made with `EnsureCreated`) and fix the story. The seed writes its sign-in, search and referral view activity entries itself: `DemoActivityParityTests` (unit) fails if the real commands write something else, so change the seed's copy with them.
  - **Its tests:** `DemoDataSeedTests` (integration) runs the seed at awkward fixed moments (a weekend, after a clock change, twice in a row) and checks it obeys the app's rules (visits before finishing, no calendar clashes, no clinical work by the admin, nothing in the future) and that the pathways are at the light demo's points; `DemoDermatologyTests`, `DemoOphthalmologyTests`, `DemoTimelineTests` and `DemoReferenceDataTests` (unit) check the templates, people, patients and moments.
- **Host services** the app's layers need are registered in `DevMcpServices` (activity log actor `medapp-dev`, no live notifications). `DevMcpServicesTests` builds them with validation on, so a newly needed service fails there, not at start.
- **Docs:** `tools/MedApp.DevMcp/README.md`.
