## Accessibility

The axe audit (`npm run a11y` in `tools/ui-parity`: every screen in dark, light and a colour theme, WCAG 2.2 A and AA) passes, and the Accessibility card has the text size, the hover delay and the switches in `src/app/accessibility.tsx`. The statement is at `/accessibility`. Still to do:

- **Three colour themes just under 4.5:1 on secondary text.** Measured against the secondary text colour (subtitles, Back, descriptions), Y2K's light page is 4.19:1, and the header bars of Chocolate's light cards and Butter's dark cards 4.41:1. The custom colour check (`textContrast`) now counts secondary text; these themes were left as they are so they don't change how they look. Decide whether to adjust them (a test lists them in `src/app/colours.test.tsx`).
- **Insights at high zoom.** At 400% zoom (320 x 256 CSS pixels, WCAG 1.4.10's test), the header and filters fill the window, the area under them is 0 px high and the document doesn't scroll, so no chart can be reached. At 200%, each 30rem chart card is taller than the area it scrolls in. Let the whole page scroll when the window is that short, and check the other `fill` pages for the same (review of #94).
- **A list's sort button in its card layout names itself differently from what it shows** (axe `label-content-name-mismatch`, WCAG 2.5.3): `RowCards` shows "Sort: When" but is named "Sort by When, descending", so a voice user saying what they see doesn't match it. Start its name with the visible text ("Sort: When, descending"). Found by the Apply Template branch's audit, on the Audit Log in a half view (`procedure-restricted-half`); it's on every list shown as cards.
- **Escape after Tab in a dialog takes two presses.** Tab from a dialog's title lands on its Close button, whose tooltip shows on keyboard focus; the tooltip is a layer of its own in Astryx's dismissal stack (`useLayerDismissal`), above the dialog, so the first Escape dismisses the tooltip (as WCAG 1.4.13 asks) and only the second closes the dialog. Every dialog (`DialogFrame`'s `DialogHeader`), on `main` too; found in #110's browser check (Log Out, 1366 px). Not MedApp's code: ask Astryx for a dialog Close button whose tooltip doesn't take an Escape of its own (or whose Escape closes both), rather than dropping the tooltip.
- **Screen reader pass by hand.** NVDA and VoiceOver through the main tasks (find a patient, work a stage, finish a procedure), and keyboard-only use of every dialog: focus trapped, and returned on close.

  - **More kinds of booking:** recurring appointments, rooms and resources, and booking several staff for one appointment.
  - **Walk-ins:** recording an appointment after the event. Booking is only in the future today.
  - **Patients:** reminders by email or SMS, and booking for themselves.
  - **Requested appointments left waiting:** flag or notify ones requested long ago and still not booked.
  - **Printing a day list.**
  - **Meetings, after `feature/team-calendar`** (`docs/calendar-plan.md`, decisions 50 to 60): recurring meetings; staff answering an invitation (accept or decline); a meeting's own history (who changed what), as appointments have; notifying attendees when only a meeting's title or notes change (today only a move, an invitation or a cancellation tells them); and letting staff arrange meetings among themselves, not only admins.
  - **Demo data for personal templates and meetings:** `medapp-dev`'s `reset_demo_data` still seeds organisation-wide templates and no meetings. It's being rebuilt on `feature/demo-data`; once that's on `main`, merge it into this work and seed each person's own templates and a few meetings. Until then `reset_demo_data` doesn't clear meetings either.
  - **Sharing or copying calendar templates:** templates are each person's own (`docs/calendar-plan.md`, decisions 50 and 51), and there's no way to give one to someone else. That has costs (review of #99, finding 5):
    - **A change for a team:** twelve nurses who shared "Clinic week" before the migration each have their own copy; moving everyone's lunch to 12:30 is now twelve edits, one person at a time on each person's templates page, where it was one.
    - **A new starter:** an admin can't give them an existing pattern (setting their default week to someone else's template is a 404), so has to rebuild the day templates and the week template by hand in the newcomer's set.
    - **Unused templates** went to one admin, who can't apply them to anyone else either.
    - **The fix:** a "Copy to..." action for admins: copy a day template, or a week template with its day templates, into chosen people's sets (new rows from today, names kept). Keeping copies in step afterwards would need a shared template or a link back to the original, which personal templates deliberately don't have.
  - **Tidy up templates with accounts:** deleting an account (or taking every staff role away) leaves its day and week templates, and its default week rows, where no list shows them (`docs/governance/retention-schedule.md`). Delete the ones nothing refers to, and give the rest (archived) to an admin, or delete them with the rows.
  - **The team view for many people:** it loads every calendar shown in one set of queries and draws a column for each person. Who, when chosen, is at most 100 people, but the default (everyone, which sends no IDs) has no limit: with 400 staff, one page load reads 400 calendars, draws 400 columns and records `PatientListed` for every patient booked with any of them that day (review of #99, finding 7). Cap everyone at the first 100 by name, saying "Showing 100 of 400: choose who in Who", or ask for a choice above 100; a large organisation will want teams or groups to choose from instead of the whole staff list.
  - **Template edits that undo a day's changes.** Editing a day template's block gives it a new row, and a day's exception (the block removed or moved for one day) points at the old row, so the block comes back on that day, possibly over an appointment booked in its place. Keep a block's identity across versions (a lineage ID the exceptions key on), or at least list the future days' changes an edit will drop before saving (review of #93, finding 2).

  - **More choices for each person** (Account Settings), once there are more kinds staff receive (the three appointment kinds, booked, rescheduled and cancelled, can't be switched off yet); and rules an admin sets for someone else (for example a team lead's), kept apart from that person's own choices so they can't undo them.

## Privacy (the rest of roadmap step 7)

The first part is built: the activity log and access report, the subject access export, restricted and disputed flags, anonymisation, the retention review, and clearing browser storage at sign-out (`AGENTS.md`, Activity log and patient privacy). Still to do, roughly in order of need (`docs/governance/README.md` has the full list):

- **Automatic purging of operational data:** sessions and sign-in events at 12 months, notifications at 6 months, as a job that runs once across the API copies, logging counts. The activity log's own retention: its sign-in entries at 12 months, its patient entries with the patient's record.
- **Note versions for stage and appointment notes**, as procedure notes now have (`PatientProcedureNoteVersion`), with the audit and the appointment history pointing at them instead of copying the text into `Details` (DPIA risk 4), and the old values of patient edits.
- **A tamper-evident activity log:** ledger tables, and streaming the log to the log workspace (step 5).
- **Access reviews and alerts:** a periodic review of who can sign in, an alert when one account opens an unusual number of records, a "what has this person seen" report, and an `Auditor` role.
- **The browser's address for pages rendered on the server:** requests from the browser already record its address (the chart turns on forwarded headers for the ingress), but a page rendered on the server calls the API from Node, so its reads record the loopback address. Pass the browser's address through server rendering, trusted only with the page server's key.
- **Age a notepad's text by when it was written** (DPIA risk 26). Today the whole notepad is cleared only once it has gone `Notepad:KeepDays` (30) without any change, so a notepad used every day is never cleared, and a patient's details jotted in January are still there in June. Record when each part was written (by line or block, or at least when the notepad last went from empty to holding text), and after the 30 days show "Your notepad has held text since 3 November: add it to a record or clear it", or clear that part after a warning. Update the DPIA's risk 26 (residual low) and the retention schedule.
- **A scheduled job for operational data:** purge sign-in events (including refused sign-ins) and sessions at 12 months, notifications at 6 months, and notepads untouched for 30 days (today they're cleared only when next opened or saved, so one never opened again waits for its account to be deleted: DPIA risk 26; a notepad in use isn't reached by this, see the entry above), once across the API copies (a lease or a Kubernetes CronJob), logging counts; the activity log's patient entries go with the patient's record. There is no scheduled job in MedApp yet.
- **Restriction hiding patients from lists** except for named roles; a second person approving an anonymisation.
- **A clinician review step in the export,** to hold back what meets the serious harm test, and a PDF.
- **Count appointments in the retention review:** the conclusion of treatment should be the latest of the last closed procedure, the last appointment attended, not attended or cancelled, and the last change to the record, and wait while any appointment is Requested or Booked (`docs/governance/retention-schedule.md`, section 2). Today appointments don't move it.
- **Retention classes per template** and per customer, the conclusion of treatment on the patient's page, destruction with a destruction log, and legal hold.
- **Saved searches that name a patient,** removed on anonymisation or destruction: their terms can be a name or an NHS number (the patient list's NHS number filter), kept in the account's settings and the browser. Anonymisation removes the number from the record but not from saved searches (DPIA risk 21).
- **Archiving in place of deleting patients,** if the product owner decides to (kept as it is for now).
- **Contact preferences** and a National Data Opt-out flag.
- **Always Encrypted for the NHS number** (deterministic, so lookups by exact value still work), which step 7 planned once the number existed. It exists now (branch `feature/nhs-integrations`), protected only by TDE like the rest. Its partial-match search (the list's NHS number filter, which matches numbers containing the digits typed) would have to become an exact match.

- **An emailed link pasted into a tab that's already on its page isn't read.** The browser changes only the fragment and doesn't reload, so `useEmailLink` keeps saying "This link isn't complete" and the token stays in the address bar and history. Listen for `hashchange` and reload when a whole link arrives (review of #109, finding 2).

## Security (roadmap step 2, after `feature/security-baseline`)

## Testing

- **Reloading with a half view open re-renders the page.** The half view's page is kept in the browser tab (`sessionStorage`), which the server can't read, so its render has no half view, the browser's first render has one, and every reload logs "Hydration failed" and rebuilds the page in the browser (`AppLayout`, `useState(() => storedPath())`). Start without the half view and open it after mounting, or keep the half view's page somewhere the server can read (the address), so the first renders match (review of #95).
- **Run the patient timeline's query on SQL Server,** once `MedApp.IntegrationTests` has a database (#65): page through entries that share a time (SQL Server orders `uniqueidentifier`s its own way, and the cursor must agree), and filter by kind (its `LIKE` markers ignore case there). Today it's only proven to translate (`PatientTimelineTranslationTests`) and run in memory (PR #64 review, finding 6).

- **Run more of the web tests under StrictMode.** Only the tests that pass `strict` to `renderWithApp` run effects twice as development does, and `renderApp` has no such option. Use Testing Library's own `reactStrictMode` option, give `renderApp` it too, then try `configure({reactStrictMode: true})` across the suite to find other effects that break when run twice (review of #109, finding 3).
