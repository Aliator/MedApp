# MedApp on a local kind cluster

Step 1 of the Kubernetes plan (`docs/todo.md`): MedApp running in a local cluster made by [kind](https://kind.sigs.k8s.io/) (Kubernetes in Docker), as close to production as one machine allows. The API runs from its production image (`MedApp.API/Dockerfile`: the API, the built React app and Node to render its pages), with SQL Server beside it.

This is a way to try MedApp in Kubernetes, not a replacement for the AppHost: day-to-day development still runs through `dotnet run --project MedApp.AppHost`. The two can run at the same time; their databases are separate.

## What you need

- Docker Desktop, running.
- kind, kubectl and the `dotnet-ef` tool. On Windows: `winget install Kubernetes.kind` (Docker Desktop includes kubectl). Open a new terminal afterwards so kind is on the PATH, although the scripts find it anyway.
- Bash: Git Bash on Windows.
- About 3 GB of memory for SQL Server, plus disk space for the images (SQL Server's alone is 1.5 GB).

## Running it

From the repo root:

```bash
deploy/kind/up.sh --demo-data kind-demo   # first save a kind-demo snapshot with medapp-dev (below)
deploy/kind/up.sh                         # or an empty database
```

Then open **http://localhost:8080** and sign in as `admin` / `admin` (with the demo data).

`up.sh` creates the cluster if it's missing, builds the API's image and loads it in, deploys SQL Server and the API, restores the demo data if you ask for it, and applies the EF migrations. Run it again after a code change to rebuild and redeploy; the database is kept unless you pass `--demo-data`, which replaces it.

`deploy/kind/down.sh` deletes the cluster and its database. The AppHost's dev database isn't affected.

## The demo data

The app seeds no accounts, so an empty database has no way to sign in. `--demo-data <name>` restores a `medapp-dev` snapshot into the cluster's database, then migrates it. Save one from the dev database (which `reset_demo_data` fills with the standard synthetic data and the `admin` login) by asking for medapp-dev's `save_snapshot` with the name `kind-demo`. It lands in `tools/MedApp.DevMcp/.backups/kind-demo.bak`, which is git-ignored. A path to any other `.bak` file works too.

## What's in it

| File | What it is |
|---|---|
| `cluster.yaml` | The one-node cluster, with its ports mapped to this machine only: 8080 to the API, 14331 to SQL Server (for `dotnet ef`; the AppHost's is 14330). |
| `kustomization.yaml` | Everything below, in the `medapp` namespace (`kubectl apply -k deploy/kind`). |
| `sql.yaml` | SQL Server 2022 as a StatefulSet, with its data on a volume. |
| `api.yaml` | The API as a Deployment, from the image `up.sh` builds (`medapp-api:local`, never pulled). |
| `up.sh`, `down.sh` | Start or redeploy, and delete. |

- **The password** for SQL Server is generated by `up.sh` into the `medapp-sql` secret (with the API's connection string), so none is in git. It lasts as long as the cluster.
- **Every `kubectl` call** in the scripts names the `kind-medapp` context, so they can't touch another cluster. To look around yourself: `kubectl --context kind-medapp -n medapp get pods`, and `logs deploy/medapp-api`.
- **Sign-in works over plain http** here because browsers treat `localhost` as secure, so they keep the session cookie even though it's `Secure`. Anywhere else needs TLS in front (the Helm step's ingress).

## Not yet (later steps in `docs/todo.md`)

- The probes only check that the ports are open, because the API maps `/health` and `/alive` only in Development.
- The API keeps its ASP.NET data-protection keys in memory, so they're lost when its pod restarts. Nothing the app does depends on them yet (sessions are database rows), but they need a home before running more than one copy.
- Migrations run from this machine through `dotnet ef`. In the Helm chart they become a Job in the cluster.
- No ingress, TLS, network policies or read-only filesystems yet.
