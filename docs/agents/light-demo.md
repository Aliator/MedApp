# The light demo (GitHub Pages)

The React app as a static site with no server, for recruiters to try: https://aliator.github.io/MedApp/. Read before changing anything in `MedApp.Web/src/demo/`, the demo build, or a page or endpoint its tour uses, and **before any PR that adds or changes an endpoint, a page or a rule** (below).

## Keeping it up to date (the rule)

**Every change to the full app is made to the light demo in the same PR** (the owner, 18 November 2026: "any changes that are made to the local deployment are also made to the light version as well").
- **A new or changed endpoint, page or rule** updates the demo's handlers (`src/demo/handlers/`) and seed (`seed.ts`, `slices/`) in the same PR. Simplified rules are fine; the demo's copy of a rule should refuse what the API refuses, in short.
- **What the demo can't do** (files, PDFs, email, post, background jobs, real sign-in, downloads) is listed in `src/demo/notInLightDemo.ts` with a one-line reason, and said in the Read Me's "What doesn't work" list (`NOT_IN_THE_LIGHT_VERSION` in `tour.ts`) when a visitor would notice.
- **Enforced by `src/demo/parity.test.ts`:** it reads every path and method in `src/api/schema.d.ts` and fails unless each one has a handler or is in `notInLightDemo` (and fails on a listed one that's gone from the API, or handled as well, or a path handled twice). So a new endpoint fails the web tests until its PR classifies it. `npm run typecheck` checks the handlers' shapes against the DTOs.
- **A new page in the side nav** renders with data for every account (no 501s): check it with `npm run dev:demo`.

## How it works

- **A separate build.** `npm run build:demo` is Vite's `demo` mode (`vite.config.ts`): client only (`index.html`'s `#root` is created, never hydrated), under `/MedApp/` (Vite's `base` and the router's `basepath`), into `dist-demo/`, with `index.html` copied to `404.html` so a deep link loads the app (GitHub Pages serves `404.html` for any unknown path; no redirect script). `npm run dev:demo` runs it locally with Vite on port 5174, needing no API.
- **Kept out of production.** Everything demo is behind the build-time constant `__LIGHT_DEMO__` (`define` in `vite.config.ts`, declared in `src/lightDemo.d.ts`), true only in the demo build, and loaded by dynamic `import()`. Other builds and the tests have it false, so the bundler drops the demo's code. Proven by grepping `npm run build`'s client output (`dist/`, not `dist/ssr`) for `Not available in the light demo`, `medapp-light-demo` and `installLightDemo`: none is there. What production keeps: a `/read-me` route that answers not found, and a doc comment in the server bundle.
- **The hooks into the app** (each one line, behind `__LIGHT_DEMO__`): `entry-client.tsx` starts the stand-in before rendering; `router.tsx` sets the base path; `routes/login.tsx` shows the account picker (`DemoLoginPage`); `routes/_app/read-me.tsx` is the Read Me; `AppLayout` opens the Read Me on the first visit (`DemoFirstVisit`) and doesn't start `LiveNotifications`; the banner (`DemoBanner`: synthetic data, who's signed in, Reset) sits at the top of the Read Me only (the owner's choice, 18 November 2026); `AppSideNav` adds the Read Me item (`readMeNavEntry`).
- **A stand-in API in the browser** (`src/demo/install.ts`): `window.fetch` sends every request for this origin's `/api/...` to a table of handlers (`src/demo/api/http.ts`, `src/demo/handlers/`) instead of the network. Each handler is registered with `on(method, path, handler)` for a path in `src/api/schema.d.ts`, and its return type is that endpoint's DTO, so `npm run typecheck` guards the shapes. A path with no handler answers a 501 ProblemDetails, "Not available in the light demo" (logged with `console.info`), and the page shows its usual error state.
- **State** is one record in IndexedDB (`medapp-light-demo`, `src/demo/store.ts`): read once at start, written after every change that succeeded. Without IndexedDB it runs in memory. **Reset** (the Read Me's banner and its Reset button) clears it, seeds again (keeping who's signed in) and reloads. Records are kept close to the DTOs (`src/demo/state.ts`); what depends on the viewer (`can...` flags, overdue, the current stage) is worked out per answer, and a patient's timeline is read from their pathways, appointments and referrals (`handlers/patients.ts`).
- **The seed** (`src/demo/seed.ts`) is a small TypeScript copy of part of the demo clinic (`tools/MedApp.DevMcp/DemoData`): 14 synthetic patients (NHS numbers only from the 999 range, valid check digits), the five teams, the stage library (with its gates: a letter, consent, results), five templates (one with branches and an optional stage), fourteen pathways (one on hold, one overdue, one discharged, one at a stage needing consent, one at a branch point, Gynaecology's and Diabetes's beside Dermatology ones, for the team walls, and one back from the lab), five referrals (four awaiting triage), appointments, this week's and next week's calendar blocks, a meeting and notifications.
- **Slices:** each area's records and seed are in their own file under `src/demo/slices/` (`lab.ts`: specimens, types, labs, results; `clinical.ts`: letters, letter templates, the MDT list, consent; `setup.ts`: practices, sites and rooms, hours, clinics, roles, monitoring, jobs and the rest of setup), with their handlers in `handlers/lab.ts`, `handlers/clinical.ts` and `handlers/setup.ts`. `DemoState` is the base and every slice; each slice's seed runs after the base's, reading it. Fixed IDs come from `id(kind, n)` (`ids.ts`), one `kind` per group.
- **The stage gates** (`StageGates`, without an override) refuse finishing a stage in the demo as in the API, simplified: the lab's (`labGate`: the last stage while a specimen is open; a stage that waits for results, or the last, while a result awaits sign-off), the letter's and consent's (`clinicalGate`). Every finish calls them (`handlers/pathways.ts`). Fixed IDs in `src/demo/ids.ts`; dates relative to the day it's seeded. **The C# seed can't be exported for it:** it runs the API's commands against SQL Server, and Pages builds in CI with neither. Bump `SEED_VERSION` when the seed's shape changes, so visitors' older copies are seeded again.
- **Tree pathways** (MC8, `handlers/pathways.ts`, `src/api/pathwayRoutes.ts`): a pathway's stages follow `links` (copied from the template's, by stage order; a list template's are `chainLinks`). Current = to do with nothing before it to do (`currentStages`); a branch point's branches are its successors' routes up to their join. Seeded fork: `PATHWAYS.forkedTests` (template `lesionWithBloods`). A template with routes side by side is read-only in the editor until MC9.
- **The relay** (MC7, `handlers/pathways.ts`, `canWorkStage` in `teamWalls.ts`): a stage's `ownerTeamId` (the lab's Histology and Lab tests) is worked only by that team; finishing or skipping into another team's stage hands over (each current stage of a fork on its own) (`reachNext`: grant, `PathwayHandedOver` notification, `StageHandedOver` in the audit log); Pick Up (`StagePickedUp`); the `View` search (`OurTurn`, `NewForUs`, `AwaitingLab`, `BackFromLab`) behind My Worklist's team views.
- **The team walls** (MC4, `handlers/teamWalls.ts`): the one place the demo's copy of `TeamScope`/`TeamAccess` lives. Pathways are seen in full through `pathwayAccess` grants (`Owner`; `StageOwner` for the lab once a specimen is recorded, kept); their records (appointments, letters, results, consent, specimens, MDT items, each with a `teamId`) follow them; other teams' pathways are summary lines (`otherTeamPathways`); across a wall is a 404 with `TeamBoundaryRefused`. Use `findPathway` (sees) or `pathwayToChange` (own team only) and `seeRecord`/`canSeeRecord`, never `db().pathways.find` in a handler. MC5: referrals (`findReferral`), counts and Insights (`insightsTeams`) too; other teams' appointments on a calendar are `otherTeamsBusy` (`busyTimeOf`); appointments and referrals change only by their own team (`ensureCanChangeRecord`). MC11 (`handlers/calendar.ts`): anyone sees any team's calendar (`TeamId`); other teams' meetings are `otherTeamsBusy` "Meeting" (`canSeeMeeting`, a 404 when opened); meetings only with your own team except an MDT (`ensureMeetingWithOwnTeam`). MC6: the grids' clinic picker (`TeamId`) through `pickedTeam`/`isPickedTeam` (another team, for staff, is a 400).
- **Three accounts, no real sign-in** (`src/demo/accounts.ts`, MC3): `admin` (Admin alone: read only, no team, `ADMIN_PERMISSIONS`), `n.thornbury` (Nadia Thornbury: Clinician, Dermatology's clinic admin) and `r.aldous` (Ravi Aldous: Lab, staff in the lab team). The login page is a picker that signs in through the stand-in (`POST api/auth/login`); the Read Me's Three accounts card and the tour's buttons switch account (a full reload, so every cached answer is read again); the Read Me's banner says the data is synthetic and kept only in this browser.
- **The Read Me** (`src/demo/ReadMePage.tsx`, `/read-me`, first in the side nav) opens on the first visit (`localStorage` `medappLightDemo.readMeSeen`, outside the app's `medapp.` keys so signing out keeps it). Its guided tour (`src/demo/tour.ts`) is a list of steps, each a button that switches account if the step needs it and opens the exact page by fixed ID **on the left, keeping the Read Me on the right** to follow (a half view: from the Read Me on its own as Ctrl-click does, `halfViews.openOnLeft`; from the right half in the main view, `halfViews.showOnLeft`; after an account switch's reload the same, through the tab's kept half view; on a phone, in its place). Start Using MedApp does the same. The first step (`staysOnReadMe`) keeps them on the Read Me on its own, closing any half view, as its numbered steps (`isNumbered`) start there; the notepad's opens it docked; the pin step's `whyNot` reads this browser's pins (`isPatientPinned`). When a button makes the Read Me start again (moving it to the right half, an account switch's reload, or back to it on its own), it keeps the reader's place first (`readMePlace.ts`: the step's `data-read-me-place` part and its offset, in `sessionStorage` `medapp.readMePlace`), and the Read Me showing where it was going scrolls back to it once laid out, then forgets it (a stale one is dropped after 30 seconds). A step whose record is gone explains instead of opening; one already done (`whyNot`) opens and says what's different. `tour.test.ts` checks every link resolves to a route in the route tree and every record ID is in the seed.
- **Deploying:** `.github/workflows/pages.yml` builds it on every push to `main` touching `MedApp.Web/**` (or itself), and by hand, and deploys with `actions/deploy-pages`. Pages must be set to "GitHub Actions" in the repository's settings.

## Adding a handler

1. Run `npx vitest run src/demo/parity.test.ts`: it lists the endpoints with neither a handler nor a reason. Find the request the page makes (`npm run dev:demo`, the console's `[light demo] Not available` line, or `src/api/*.ts`).
2. In the area's file in `src/demo/handlers/` (or a slice's), `on('get', '/api/...', ({params, query, body}) => ...)`, returning the DTO. Call `me()` first (a 401 when signed out, as the API), and `requirePermission(...)` where the API needs one. Refuse with `refuse(problem(409, '...'))`, `notFound('The ...')` or `invalid({field: ['...']})`.
3. Keep rules simple, and say in the Read Me's "What doesn't work" list what the full version does that this doesn't.
4. A test in the area's test file in `src/demo/handlers/` (`startLightDemo`, `call` from `src/test/lightDemo.ts`).
5. Or, when the demo can't do it, list it in `src/demo/notInLightDemo.ts` with a reason.

## What's simplified or left out

**Covered:** every page in the side nav, for both accounts, with data, and the actions behind them: sign in, pathways and stages (optional stages, branches, unlocking, reinstating), notes and their deletion, status, assignments, referrals (register, edit, triage, withdraw, information requests, the clock's pauses), the lab (specimens through their statuses, types and labs), results (seen, sign-off, reassign, entered in error), letters (write, approve, return, withdraw, correct, record as sent), letter templates, the MDT list (list, defer, withdraw, outcomes), consent forms and records, calendars, templates, closed days, clinics, meetings, appointments, booking and Did not attend, the notepad, settings, notifications, Insights, the setup pages (teams, the stage library, pathway templates, sites and rooms with hours, practices, activity types, roles, monitoring rules including service alerts), the audit and activity logs, privacy (restriction, dispute, the retention review, the export page) and data requests.

**Simplified:** few concurrency checks beyond `expectedVersion`; no locks; the audit log is worked out from the records, and the activity log from seeded entries and the demo's own sign-ins, views and changes; Insights' history (last week's figures, stage times, throughput) is made up; roles held by someone, and users, can't be changed; monitoring rules are kept but nothing fires them; the scheduled jobs are listed with made-up runs. Data requests (`handlers/dataRequests.ts`): kept as an optional list on the state; the review lists pathway notes only.

**Not there** (`notInLightDemo.ts` lists each endpoint with its reason): files (attachments, a specimen's report, an external result, a consent scan), PDFs (letter and template previews, the data-request pack's download), sending letters (`send` refuses: record it as sent instead), email and two-factor, real sign-in and passwords, creating and deleting users, running a job, FHIR and the demographics lookup, live notifications, server rendering. The patient timeline doesn't show specimens, results, letters, the MDT or consent yet.

## Decisions (taken on the owner's behalf, 18 November 2026)

- **Fetch is patched in the page, not a service worker** (no Mock Service Worker): no extra file to serve under `/MedApp/`, nothing that outlives the tab, and no dependency. Plain IndexedDB (a few lines) rather than a library.
- **The whole state is one IndexedDB record**, rewritten after each change: simple, and small at this size.
- **A 501 for a path with no handler,** so it can't be mistaken for a real 404 or 409.
- **The timeline is derived** from the records rather than stored, so no handler has to remember to add to it.
- **Switching account and Reset reload the page,** rather than clearing caches by hand, and close any half view.
- **`src/demo/**` is excluded from the coverage thresholds** (`vite.config.ts`): it's never in the production build, and has its own tests (the tour, the handlers, the store, the seed and each page).
- **The notepad's "never in browser storage" rule doesn't apply here** (`notepad.md`): the demo's data is synthetic and there's no server.
- **The production route tree keeps `/read-me`**, answering not found: the router plugin builds routes from files, and making one conditional would need a second route tree.
