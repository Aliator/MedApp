# Pathways

Pathways, templates and stages, pathway notes and note deletion: read before changing any of them.

Concept and decisions: `docs/pathways-ui-plan.md`. Admins build **templates**, ordered lists of **stage definitions** (a stage may repeat). Staff create a patient's **pathway** from one, copying its stages (name, description, instructions). Stages are worked strictly in order: notes, then finish, which locks the stage until an admin unlocks it.
- **The rules live in `MedApp.Application/Pathways/Common`:** `PathwayWorkflow` (statuses, current stage, what's editable, overdue) and `PathwayChange` (applies a change, moves the status, writes the audit entries). Use them; don't set `Status` or stage flags by hand.
- **Every change is audited** (`PatientPathwayAuditEntry`, no foreign keys so history outlives deletes). New pathway commands must go through `PathwayChange`.
- **Target dates are whole days,** due by the end of the day UK time, stored as that moment in UTC (`DueDates`); the API takes and returns `DueDate` as a date.
- **A pathway accepted from a referral takes its target date from the waiting-time clock** while the clock runs (its target) or is paused (the review date); `PATCH` refuses a different one then (400, `WaitingClock.TargetFromClockMessage`), and staff edit it again once the clock has stopped. The clock stops when the stage marked `StopsClock` (copied from the template's clock-stop stage) is finished, or the pathway is discharged or cancelled; a new priority re-reads its target. All through `PathwayChange` (`FollowClock`, `PriorityChanged`, `PauseClock`, `ResumeClock`), which loads the referral with the pathway: see [Referrals](referrals.md), the waiting-time clock.
- **Every template belongs to a specialty,** and a pathway copies its template's when it's created: see [Specialties](specialties.md).
- **A pathway can come from a referral:** accepting one creates it through `PathwayCreation` like any new pathway, with `referralId` in its Created audit entry, saved with the referral's change: see [Referrals](referrals.md). Its page links back (`PatientPathwayResponse.Referral`).
- **List filters** (`PathwaySearch`, `GET api/pathways/patient-pathways/search`; the Pathways list and My Worklist): besides the rest, `SpecialtyIds` (any of the pathways' own specialties) and **the stage reached**, `StageDefinitionIds` (`PathwaySearch.AtStage`): pathways whose current stage, the first neither finished nor skipped by `StageOrder` as `PathwayWorkflow.CurrentStage` has it, comes from any of those definitions. Closed pathways (discharged, cancelled, archived) never match, whatever else is asked; on hold ones do. At most 100 IDs each. `BreachedOnly` keeps pathways whose referral's clock is past its target, and `sort=daysWaited` orders by the clock's days waited (pathways without one last, either way; `DateOnly.DayNumber`, which EF turns into `DATEDIFF`: `WaitingClockSqlTests`). The web app keeps them in the URL as `specialty` and `stage` (comma lists of IDs, "is" or "is any of", never "not any of": `parseIdChoice`). `PathwaySearchSqlTests` checks the SQL's shape; `PathwayFiltersTests` runs it on SQL Server.
- **Optional stages and branches** (`docs/centre-phases-3-5-plan.md`, decisions 113 to 117; PR 20). Stages stay one ordered list; the current stage is the first **neither finished nor skipped** (`PathwayWorkflow.CurrentStage`, `IsToDo`), and a skipped stage counts as done for the status (`AllStagesFinished`). Existing templates and pathways have none, so behave as before.
  - **On the template** (`PathwayTemplateMap.IsOptional`, `ChoosesBranch`, `Branch`, 50 characters), copied onto each pathway's stage by `PathwayCreation`. The API takes them as `stageOptions` beside `stageDefinitionIdsInOrder` (one each, same order). Left out with the same stage list (definitions in the same order), the stored options stay, so a page from before them can't strip a template's branches; with a new list, every stage is plain. `TemplateBranchRules` (both validators, 400): a branch point needs two branch names (ignoring case) before the next branch point or the end; a branch name only after a branch point; a branch point is never optional or in a branch; the last stage is never optional, a branch point or in a branch.
  - **Skip** (`POST .../stages/{sid}/skip` `{reason, detail?}`, `WorkPathways`): an optional stage while it's current; one whose visit is **Required** only by a holder of `OverrideStages` (409 otherwise, and `canSkip` says so) with a detail (400), as finishing it without its visit needs, and its `StageSkipped` records `visitRequirement` (a branch not chosen still skips one: the clinician chose the other branch); `StageSkipReason` by name, `NotNeeded`, `PatientDeclined` or `Other` (detail required, 500). Audit `StageSkipped` (`skipReason`, `detail`). An unstarted pathway goes InProgress.
  - **Branch choice:** finishing a branch point for the first time needs `branch` in the finish body (400 without, naming the branches); the other branches' to-do stages up to the next branch point are skipped with `BranchNotChosen` in the same save, and one `BranchChosen` entry (`branch`, `skippedStageIds`, `skippedStages`) follows the `StageFinished`. **Never chosen or pre-selected by MedApp**: the response lists a branch point's `branches` (template order, with stage names) and `needsBranchChoice`. Finishing it again after an unlock refuses a branch: a branch changes only by reinstating.
  - **Reinstate** (`POST .../stages/{sid}/reinstate` `{reason}`, `OverrideStages` until PR 24 makes it `UnlockStages`): a skipped stage, while the pathway is open or discharged (as unlocking); it's to do again in its place (before the current stage, it becomes current; its visit is asked for then). Audit `StageReinstated` (`reason`, the old `skipReason`). InReview or Completed goes back to InProgress.
  - **Visits:** a skipped stage has none. Skipping cancels its Requested appointments (`PathwayChange.StageSkippedReason`), and choosing a branch those of the stages it skips (`StageFinishing.StagesTouchedByFinish` loads them); Booked ones stay, as when a stage is finished.
  - **Elsewhere:** the stage filter's stage reached and Insights' stage times read `SkippedAtUtc` (below and [Insights](insights.md)); the timeline's Stages kind has the three actions ([Timeline](timeline.md)); the monitor is told of each command, though no rule watches skips ([Monitoring](monitoring.md)). **The waiting-time clock:** skipping the clock-stop stage (by hand or by a branch not chosen) stops nothing; the clock runs on and stops at discharge or cancellation, as with no clock-stop stage; reinstating never restarts a stopped clock, and a reinstated clock-stop stage stops a running one when it's finished (`PathwayChangeClockTests`).
  - **Stored:** `PatientPathwayAuditAction` `StageSkipped = 35`, `BranchChosen = 36`, `StageReinstated = 37` (16 to 34 kept for Phase 3); `StageSkipReason` `BranchNotChosen = 0`, `NotNeeded = 1`, `PatientDeclined = 2`, `Other = 3`. Never renumber them.
- **Definitions and templates in use are archived, not deleted** (deleting one is a 409). Patients with pathways or appointments can't be deleted (409).
- **A stage can involve a visit** (`VisitRequirement`, copied onto the stage): see [Calendar and appointments](calendar.md).
- **Stage gates without an override** live in `StageGates` (`Pathways/Common`), called by every finish path (`FinishPathwayStageHandler`, the demo's `PathwayReplay`): today the last stage (the one whose finish leaves none unfinished) waits while any of the pathway's specimens is open ([Specimens](specimens.md)). A stage's `CanRecordSpecimen` says whether the viewer can record one there.
- **A pathway with specimens can't be deleted** (409).
- **A pathway has several notes** (`PatientPathwayNote`, Markdown, 4,000 characters), newest first, each with author, written and last edited times. `PATCH` refuses notes (400, `UpdatePatientPathwayValidator.NotesMovedMessage`, so an old page is told, not silently ignored), and the Edit Pathway page has none. A new pathway's notes become its first note, by its creator (`PathwayCreation.Record`).
  - **Endpoints, for staff:** `POST .../patient-pathways/{id}/notes` `{text}` (201, `Location` the pathway) and `PUT .../notes/{noteId}` `{text, expectedVersion}`. Notes come only in the pathway's response (`NoteList`, each with `CanEdit`, plus `CanAddNotes`), so reading them is its `PathwayViewed`. **`Notes` stays a string** (deprecated: the first note's or the old column's text); never change an existing response field's type.
  - **When:** whenever details can be edited (`PathwayWorkflow.CanChangeNotes`), so Blocked and **Completed** too; not Cancelled or Archived (409). Restricted or anonymised records: the usual `GetForUpdateOrThrowAsync` 409.
  - **Who:** staff add; **only the author edits** (403 otherwise, admins included: what someone wrote stays theirs). **Only admins delete;** staff ask. A note migrated with no known creator has no author ("Unknown") and can't be edited.
  - **Versions:** every add and edit writes a `PatientPathwayNoteVersion` (text, who, when; no foreign keys, patient and pathway copied in). An edit from a stale `expectedVersion` is a 409 (`PathwayNotes.ChangedMeanwhileMessage`); the row version catches simultaneous saves.
  - **Audit:** `NoteAdded = 13` and `NoteEdited = 14`, through `PathwayChange.AddNote`/`EditNote` (moving `LastUpdated`; the monitor is told, though no rule watches them). **Details hold the note's ID and version, never its text** (DPIA risk 4).
  - **Deleting is soft, by admins, with a reason** (`POST .../notes/{noteId}/delete` `{reason, detail?, expectedVersion}`, 204; `PathwayChange.DeleteNote`), in any pathway status (it's a correction), never while restricted or anonymised.
    - **Reason:** `NoteDeletionReason`, stored by number, so never renumber it: `WrongPatient = 0`, `WrittenInError = 1`, `Duplicate = 2`, `Other = 3` (words in `NoteDeletionReasons`). Detail: up to 500 characters, required for Other.
    - **Effect:** sets `DeletedAtUtc`, `DeletedByUserId`, `DeletionReason`, `DeletionDetail`; hidden from the pathway page (`PathwayNoteMapper.ToResponses`, and the `Notes` string), but the row and versions stay for history, the timeline and the export. Editing or deleting it again is a 409 (`PathwayNotes.DeletedMessage`).
    - **The version read:** every delete carries `expectedVersion`; a note edited since is a 409 (`PathwayNotes.EditedSinceOpenedMessage`). Keeping a note needs none.
    - **The author is told** (`AuthorsNoteDeleted`, see [Notifications](notifications.md)), so they can add it to the right record.
    - **The old field:** deleting a pathway's oldest note (the one #110's migration copied `PatientPathways.Notes` into) also clears that column (audit `oldNotesFieldCleared`).
    - **Audit:** `NoteDeleted = 15`: note ID, latest version, `deletionReason` by name, detail, `requestId` if any; **never the text**. Anonymising replaces the detail (`detail` is a `PatientAnonymiser` free-text key).
    - **Per-note flags:** `CanDelete` (admins, while the record can change), `CanRequestDeletion` (others, while it can change and nothing is waiting) and `DeletionRequestId` (the waiting request). `PathwayActor.Permissions` (from the session) carries the viewer's permissions; `CanDelete` needs `CorrectRecords`, and `CanEdit` and `CanRequestDeletion` need `WorkPathways`. The pathway's own `Can...` flags follow the viewer's permissions too ([Auth](auth.md), Roles and permissions).
  - **Staff request a deletion** (`POST .../notes/{noteId}/deletion-requests` `{reason, detail?}`, 201 with the note; `RequestNoteDeletionHandler`): any note, any status, not while restricted or anonymised.
    - **The request:** `PathwayNoteDeletionRequest` (`MedApp.Application/Pathways/NoteDeletionRequests`; no foreign keys): note, pathway, patient, requester (ID and username then), reason, detail, status, timestamps and decider. `NoteDeletionRequestStatus` is stored by number, so never renumber it: `Pending = 0`, `Approved = 1`, `Declined = 2`, `Closed = 3` (no decision).
    - **One waiting per note:** `PendingDeletionRequestId` on the note; asking again is a 409 (`PathwayNotes.AlreadyRequestedMessage`). The note's row version and the filtered unique index `IX_PathwayNoteDeletionRequests_NoteId_Pending` stop races (`NoteDeletionRequestRepository` makes either the same 409).
    - **Saved together:** request and note share the DbContext (`INoteDeletionRequestRepository`), one `SaveChangesAsync`.
    - Every admin but the requester is told (`NoteDeletionNotifications`).
  - **An admin decides** (`GET api/pathways/note-deletion-requests/{id}`, `POST .../{id}/decision` `{deleteNote, expectedVersion?, reason?, detail?}`, admins). The GET gives the note's text, the patient (as `PatientBanner`), the pathway's title, request and outcome, `CanDecide` and `WhyCantDecide`, and records `PathwayViewed` (`PatientViewed` once the pathway is deleted). **Delete note** needs `expectedVersion` and uses the admin's reason and detail or else the requester's; **Keep note** declines. The requester is told. Already decided (`PathwayNotes.AlreadyDecidedMessage`), or a restricted or anonymised record, is a 409; the row version catches two admins.
    - **A direct delete approves** a waiting request (telling its requester).
    - **Deleting a pathway closes** its waiting requests (`Closed`, same save, `DeletePatientPathwayHandler`), untold.
    - **Anonymising** replaces request and deletion details and closes waiting requests; an older API copy doesn't (the chart's README, `docs/todo.md`).
    - **Privacy:** the export lists deleted notes and every request (`ExportedNoteDeletionRequestResponse`, loaded in `PatientRecordRepository`); `WrongPatient` deletions are flagged `IsAboutAnotherPatient`. Hazard H-38.
  - **The old `Notes` column** stays (`PatientPathway.LegacyNotes`, for the deprecated string) so older API copies work during a rollout (the chart's two-release rule). Migration `AddedProcedureNotes` copied it into a first note, by the creator, or "Unknown" if anyone else had edited it (`DetailsUpdated` with `changes.notes`). Anonymising clears it. Dropping it is a to-do, after copying text only it holds (`docs/todo.md`).
- Status numbers are stored, so never renumber `PatientPathwayStatus`, `PatientPathwayAuditAction`, `StageSkipReason` or `NoteDeletionRequestStatus`.
- **Three statuses are shown by another name than the code's** (`docs/glossary.md`): `InReview` is "Awaiting review", `Blocked` is "On hold" and `Completed` is "Discharged"; a `DueDate` is a "Target date". The enum members, DTO fields and audit details keep the code's names (Insights and the timeline read them: `"to":"Blocked"`). Put a status into words with `PathwayWorkflow.Describe` in the API and `statusWords` or `statusLabel` in the web app (`src/utils/statusWords.ts`), never by splitting its name.
