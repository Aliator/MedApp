# The full app in the browser (replacing the light demo)

Status: **in progress** · 22 November 2026 · the owner's decisions below

**In one line:** the real MedApp backend (the Application layer's handlers, Infrastructure's repositories and the API's controllers) compiled to WebAssembly and run in the visitor's browser on SQLite, behind the React app, on GitHub Pages: every feature with a real rule, not the light demo's simplified TypeScript copies.

## The owner's decisions (22 November 2026)

1. **Option A:** everything runs in the browser, on GitHub Pages; no server.
2. **Single user:** assume one person at a time, so whatever exists for concurrency (locks, row versions, lock hints, lease checks) is simplified away in the browser build rather than reproduced.
3. **It replaces the light demo** once it's done and tested: built at `/MedApp/full/` first, then moved to `/MedApp/` and the light demo (`MedApp.Web/src/demo`) retired, with its parity rule (`docs/agents/light-demo.md`), after the owner agrees.
4. **The login page** lists the accounts to sign in as (like the light demo's), and **downloads and caches the backend and the database before sign-in is allowed**, with progress shown; later visits load from the cache, and a newer published database is fetched first.

## Feasibility (checked 22 November 2026)

- .NET 10 for the browser (`Microsoft.NET.Sdk.WebAssembly`, the `wasm-tools` workload for native linking) runs **EF Core with SQLite** (`Microsoft.EntityFrameworkCore.Sqlite`, SQLite linked natively from `SQLitePCLRaw`'s `browser-wasm` build) in Chromium: a database created, written and read in 0.7 s.
- **Trimming must be off** (`PublishTrimmed=false`): EF Core makes objects by reflection; trimmed, it fails at runtime.
- **`MedApp.Application` compiles for the browser unchanged** and its 291 handlers load.
- Size: the runtime and EF Core alone are about 11 MB compressed; the whole backend is expected at 15 to 25 MB.

## Design

### The backend: `MedApp.Browser`

A new project (`Microsoft.NET.Sdk.WebAssembly`, `PublishTrimmed=false`, `WasmBuildNative=true`, `InvariantGlobalization` unless the app needs cultures), referencing `MedApp.Application`, `MedApp.Domain` and `MedApp.Contracts` as they are.

- **Infrastructure by source:** `MedApp.Infrastructure` can't be referenced (it needs the ASP.NET Core shared framework, Azure, MailKit, SkiaSharp's Linux build), so its portable source files are compiled into `MedApp.Browser` (`<Compile Include="../MedApp.Infrastructure/**/*.cs" Exclude="…">`), and the few that aren't are replaced by single-user stand-ins in `MedApp.Browser`:
  - **Locks:** `ICalendarLock` and the last-admin guard do nothing (one user).
  - **Concurrency:** row versions (`IsRowVersion`) aren't mapped; `expectedVersion` checks in handlers stay (they compare numbers the app keeps itself).
  - **Sample numbers:** the SQL Server sequence becomes a counter row.
  - **Raw SQL and lock hints** (roles, scheduled jobs): plain LINQ.
  - **Files:** bytes in a SQLite table instead of Azure Blob storage; no virus scan (files are marked clean); no thumbnails (SkiaSharp).
  - **Email, SMS, secure email:** not sent (recorded as not sent, as with no email configured).
  - **Live notifications (SignalR):** none; notifications are read when the page asks.
  - **Data Protection, sessions:** one in-memory session for the account picked.
  - **PDFs (PDFsharp):** kept if it runs in the browser; otherwise "not available here".
  - **Outside services (PDS, FHIR, hospital):** "not available here".
- **Changes to shared code** only where a seam is cleaner than a copy (an interface for the sample number, say), each small and covered by the existing tests.

### The HTTP layer

The 38 controllers (356 actions) compile **unchanged** into `MedApp.Browser` against a small stand-in for the parts of ASP.NET Core MVC they use: `ControllerBase` and its results (`Ok`, `Created`, `NoContent`, `File`, problem results), the routing and binding attributes, `User`, and `[RequirePermission]`. A reflection router matches `METHOD /api/...` to an action by its route template (with constraints like `{id:guid}`), binds route values, query strings (into request objects) and the JSON body as ASP.NET Core does, checks the permission, calls the action and serialises the result with the API's JSON options. Exceptions become the same responses as `ExceptionHandling.cs` (400 `ValidationProblemDetails`, 401, 403, 404, 409 ProblemDetails). One `[JSExport]` entry point takes a request (method, URL, headers, body) and returns the response (status, headers, body).

### The database

- **SQLite, built from the model** (`EnsureCreated`), not the 110 SQL Server migrations. `MedAppDbContext` gets small provider switches where SQL Server-only mapping is used (row versions, the sequence, `datetime2` and other column types, filtered index SQL in brackets).
- **Case:** SQL Server compares text without case; SQLite doesn't. Searches that rely on it are made case-insensitive for SQLite (the `NOCASE` collation on searched text columns, or lower-casing in the query).
- **Kept in the browser:** after any request that changed data, the SQLite file is saved to IndexedDB; on start it's restored from there.

### The demo data

- **Made at build time** by the full app's own seeder (`tools/MedApp.DevMcp/DemoData`) against SQLite (a native run in CI), so the browser never seeds: the same clinic as the full app's demo data (three teams, nine people, every record), dated from the build day. Passwords aren't needed (the account picker).
- **Published** as `medapp.db` (compressed) with a version file (`db-version.json`: the build's date and a hash).
- **A nightly GitHub Action** rebuilds and redeploys, so dates stay current. A visitor whose cached database is older than the published one gets the new one at the login page (their changes go, as the light demo's daily reseed does).

### The web app

- **A new build mode** (`npm run build:full-demo`), like the light demo's, behind a build-time constant (`__FULL_DEMO__`), loaded by dynamic import, never in the production build: `window.fetch` for `/api/...` goes to the .NET backend's entry point instead of the network (the light demo's `install.ts` pattern).
- **The login page:** the accounts (from the seeded database's demo people, or a fixed list matching the seed), each with its description, the sign-in buttons disabled with a progress bar ("Getting MedApp ready: 12 of 20 MB") until the backend and the database are downloaded and cached; then signing in starts the in-memory session as that person.
- **The walkthrough** (`src/demo/coach`) comes along, its targets found by name (the records' IDs come from the seeded database's `tour` IDs).
- **Not started in this mode:** `LiveNotifications`, server rendering.

### Hosting

The same Pages workflow builds both sites: the light demo at `/MedApp/`, this at `/MedApp/full/`, until the switch (decision 3).

## Phases

1. **The backend answers:** `MedApp.Browser` builds; the MVC stand-in and router; SQLite from the model; a handful of endpoints (sign-in, whoami, patients search, a pathway) working in Chromium against an empty database; the size measured.
2. **The demo database:** the seeder runs against SQLite at build time; the browser loads `medapp.db` and serves the seeded data.
3. **Every endpoint:** all 356 actions routed; a test that every path in `src/api/schema.d.ts` reaches an action; the stand-ins (files, email, PDFs) in place.
4. **The web app:** the build mode, the login page with download, cache and progress, the walkthrough.
5. **Deploying:** the Pages workflow builds both, the nightly rebuild; then, once tested and the owner agrees, the switch.

### Phase 1: done (22 November 2026)

- **`MedApp.Browser`** builds in the solution (no native linking on a build, so CI needs no workload); `dotnet publish` links SQLite natively and needs wasm-tools. Cultures stay on (letters and data requests use en-GB), so `InvariantGlobalization` is off.
- **Infrastructure by source**, left out and replaced: `ServiceExtensions.cs` (its portable part, the repositories, jobs' settings and demographics, is now `ServiceExtensions.Portable.cs`, compiled by both), `CalendarLock` (a transaction, no lock), Blob storage (`SqliteFileStore`, a `BrowserFiles` table), SkiaSharp (no thumbnails), SMTP and its dispatcher (nothing sent), secure email letters and GOV.UK Notify (not available), data protection (Identity's own token providers under the same names). `LastAdminGuard` runs as it is (no lock: not SQL Server).
- **SQL Server's dialect** is translated by an EF Core command interceptor (`SqlServerDialect`), so the repositories run unchanged: `NEXT VALUE FOR` becomes a counter row, lock hints go, and SQLite's constraint failures are raised as `SqlException` numbers 2601, 2627 and 547 naming the index or keys, as the catch clauses read them.
- **The model** is fitted to SQLite after it's built (`SqliteModelCustomizer`): no row versions or sequence, no SQL Server column types, `NOCASE` text, `DateTimeOffset` as numbers, SQLite's functions for the insights. The API's model and migrations are unchanged.
- **The HTTP layer:** 37 of the 38 controller files (353 of 356 actions) compile unchanged against `Mvc/` (MVC's attributes, results, `ControllerBase`, `ProblemDetails`); `ExceptionHandling.cs` runs unchanged. `FhirController` is left out (its filters and `FhirResult`): Phase 3.
- **Sessions:** the API's own (`SessionService`, a `UserSessions` row); the cookie is held in memory; any password signs in (the account picker), but the password must be non-empty as the API's validator requires; holds never apply.
- **Proved in Chromium** (`MedApp.Browser/harness`): sign-in, whoami, users and roles, a patient created, searched and read, a pathway search, the activity log, and the API's 400, 401, 403, 404 and 409 bodies.
- **Size:** 244 files, 42.9 MB, 15.8 MB gzipped, 12.4 MB with Brotli (every assembly loads at start). **Start:** about 0.6 s for the runtime, then 5.7 to 6.4 s for the backend, of which 3.5 to 4 s is building EF Core's model; first answer about 6.3 s after the page starts (served locally).

**For Phase 2:** a compiled model (`dotnet ef dbcontext optimize` for the SQLite model) is the biggest saving at start. The seeded database must be made by the same `SqliteModelCustomizer` and `SqlServerDialect` (and the `__BrowserSequences` and `BrowserFiles` tables). Requests are served one at a time (one SQLite file, one thread); saving to IndexedDB can follow each request that changed data.

### Phase 2: done (22 November 2026)

- **The database is built natively** by `tools/MedApp.BrowserDb` (net10.0, in the solution): `dotnet run --project tools/MedApp.BrowserDb -c Release -- --out <folder>`. It compiles what `MedApp.Browser` compiles (`MedApp.Browser/BrowserSources.props`, imported by both: Infrastructure's portable files, the API's controllers, the browser's own files but `Program.cs`), and the full app's seeder (`tools/MedApp.DevMcp/DemoData`) but its SQL Server parts. It makes a new SQLite file from the model (`BrowserBackend.CreateAsync`: `EnsureCreated`, `__BrowserSequences`, `BrowserFiles`, rollback journal mode), then runs `DemoDataSeeder.SeedAsync` on `SeedServices` built with the browser's services (`AddBrowserBackend`, the same stand-ins: files in `BrowserFiles`, no email sent), then `VACUUM`. The same clinic as SQL Server's, **row for row in every table** (checked against the container's run: 85 tables, about 1,560 rows), with the GP's report and the letters' PDFs stored (Azurite isn't needed).
- **The seeder's seams** (nothing changes against SQL Server, whose run still loads the same counts): `DemoDataSeeder.RunAsync` (the guard, Azurite, the wipe) is now in `DemoDataSeeder.SqlServer.cs` and calls `SeedAsync(services, options, wipe, filesSkipped)`; `SeedServices` takes the app's services as a delegate, and its SQL Server constructor (`AddDevMcpCore`) is in `SeedServices.SqlServer.cs`. `Guards`, `DevMcpOptions`, `DevToolActivityContext` and `TestStaffTools.RoleChanges` moved to files of their own, so the build can compile them without SQL Server or the MCP server (it references `ModelContextProtocol.Core` for `McpException`, and SkiaSharp for the seeder's synthetic files).
- **Output:** `medapp.db` (2.4 MB), `medapp.db.gz` (0.30 MB, gzip at its smallest) and `db-version.json`: `builtOn` (the UK date), `seedVersion` (`DemoDatabaseBuild.SeedVersion`, 1: raise it when an older saved copy can't be used), `sha256` (of `medapp.db`), `bytes`, `compressedBytes`, `tour` (the seed's IDs) and `accounts` (the nine people: `username`, `fullName`, `jobTitle`, `roles`, `teams`), with no passwords. About 25 s to build (the seed about 21 s).
- **The browser starts on it:** the page hands the file's bytes to `StartAsync(bytes)`, which writes them to the runtime's file system first; given none, it makes an empty database with the first admin, as before (the harness's Phase 1 run). After each request, `FetchAsync`'s answer says whether the database changed (`changed`, from SQLite's `PRAGMA data_version` on a connection of its own: reads change it too, as they're logged), and `ExportDatabase()` returns the file's bytes (refused while a request is being served).
- **`MedApp.Browser/wwwroot/backend.js`**, for the React app in Phase 4: `startBackend({ onProgress, database = true, base })` downloads the backend (`onDownloadResourceProgress`, by file count) and the database (by bytes) side by side, and returns `{ version, source, timings }`; `fetchApi(method, url, headers, body)` returns `{ status, headers, body | bodyBase64 }`, one request at a time, in order; `flush()` waits for saving; `forgetSavedDatabase()`. The saved copy (IndexedDB `medapp-full-demo`) is used while its `sha256`, `builtOn` and `seedVersion` match the published `db-version.json` (or when that can't be fetched: offline); otherwise `medapp.db.gz` is downloaded (`DecompressionStream`; a server that sends it already decompressed is handled), its hash checked, and saved. After a request that changed the database, its bytes are saved (coalesced, between requests: about 40 to 55 ms for 2.4 MB).
- **A compiled model** (`MedApp.Browser/Data/CompiledModel`, made by `tools/MedApp.BrowserDb/optimize-model.sh` with `dotnet ef dbcontext optimize`; EF Core finds it itself). It needed: `SecondsBetween` translated by a plugin (`SqliteInsightsTranslations`) rather than `HasTranslation`, which a compiled model can't hold; `JsonColumn`'s `Read` and `Write` internal rather than private (the compiled converters call them); and the `Microsoft.EntityFrameworkCore.Issue31751` switch in the browser, so the model is initialised on the page's one thread. **It must be remade after any model change** (`AGENTS.md`): a removed or renamed member breaks the solution's build, and the database's build checks the compiled model against the model as the app builds it (`CompiledModelCheck`: tables, columns, keys, indexes, foreign keys, properties and what their converters store) and refuses a stale one. `EnsureCreated` builds the full model (about 5 s in the browser), so only the empty-database start pays for it.
- **Start, served locally, before and after the compiled model** (the model, then the backend's start, then ready from the page's start): downloading the database 3.8 s, 4.7 s, 5.4 s before; 0.3 s, 1.5 s, 2.2 to 2.5 s after. From the saved copy 3.2 s, 4.0 s, 4.4 s before; 0.3 s, 1.3 to 1.5 s, 1.8 to 1.9 s after. The rest of the start: 0.4 to 0.8 s for the runtime, 0.3 to 0.5 s for the services and routes, and 0.5 to 0.8 s for the first query (the first admin check).
- **Proved in Chromium** (`MedApp.Browser/harness`, `node harness/check.cjs <wwwroot> <database folder>`): Phase 1's run on an empty database; then the published database downloaded, and as each of `admin`, `n.thornbury`, `r.aldous` and `s.varma` (any password): whoami, the patients search finds Leah Corrin, the Home page's counts (Needs your attention: 6, 5, 7 and 1; the lab cases' count is a 403 but for the lab, the data requests' but for the admin), and today's calendar (blocks for each); the insights (SQLite's `unixepoch` for the stage times); a note added to Leah Corrin's pathway, still there after a reload (from IndexedDB), and gone once a newer `db-version.json` is published (the saved copy replaced).

**For Phase 3:** routing every endpoint runs on this database, so each new stand-in can be checked against seeded data (`db-version.json`'s `tour` names the records). `FhirController` is still left out. Requests must reach the backend through `fetchApi` (or another single queue): `ExportDatabase` refuses to read the file mid-request. Every request that changes the database (nearly all: reads are logged) saves the whole file, which is fine at 2.4 MB; if the database grows a lot, save less often. A seeder change runs in both builds (the solution builds `MedApp.BrowserDb`), so keep SQL Server out of `DemoData/` but its `*.SqlServer.cs` files. The runtime's files are cached only by the browser's HTTP cache so far (Phase 4's "downloaded before sign-in" may want them in Cache Storage). The published `wwwroot` doesn't include the database: Phase 5's workflow runs `MedApp.BrowserDb` and copies `medapp.db.gz` and `db-version.json` beside `backend.js`.

### Phase 4: done (23 November 2026)

- **The build mode:** `npm run dev:full-demo` (Vite on :5175) and `npm run build:full-demo` (into `MedApp.Web/dist-full-demo/`, with `404.html`), Vite's `full-demo` mode: base and router base path `/MedApp/full/`, client only, the build-time constant `__FULL_DEMO__` (`src/fullDemo.d.ts`). Everything for it is in `MedApp.Web/src/fullDemo/`, loaded by dynamic `import()` behind `__FULL_DEMO__` from the same hooks as the light demo's (`entry-client`, `router`, `routes/login`, `AppLayout`, `AppSideNav`) and Account Settings. **Not in the production build:** `npm run build`'s client output (`dist/`, not `dist/ssr`) has none of `installFullDemo`, `medappFullDemo`, `medapp-full-demo`, `Getting MedApp ready`, `backend.js` or `runtime-size.json`; the server bundle keeps a doc comment and a `null`. The light demo's build has none of it either, and the full demo's has none of the light demo's store.
- **The backend's files** come from `vite.fullDemo.ts`: the published `wwwroot` (`FULL_DEMO_BACKEND`, default `MedApp.Browser/bin/Release/net10.0/publish/wwwroot`) and the database folder (`FULL_DEMO_DATABASE`, default `MedApp.Browser/bin/demo-db`). The dev server serves them under the base; the build copies `_framework/` (without the `.br` and `.gz` copies), `backend.js`, `medapp.db.gz` and `db-version.json` in, writes `runtime-size.json` (the runtime's files as read and compressed, for the progress), and fails, saying how, if any is missing. `MedApp.Web/README.md` has the commands.
- **Requests:** `window.fetch` for this site's `/api/...` goes to `fetchApi` (`install.ts`); uploads through **XMLHttpRequest** go there too (`xhr.ts`: a subclass that answers `/api` requests from the backend, encoding any body as fetch would, multipart forms included, with simple progress, and anything else as the real one); a **download link** to `/api/...` is answered by the backend and saved under its `Content-Disposition` name (`downloads.ts`). Until the backend has started, whoami answers "signed out" at once and anything else waits for it.
- **The login page** (`FullDemoLoginPage`) shows the accounts from `db-version.json` at once (read by itself, before the backend): `admin`, `n.thornbury`, `r.aldous` and `s.varma` first, each described in a line as the light demo's are, then **Other people at the centre**; the synthetic data banner; an Astryx progress bar with its words ("Getting MedApp ready: 2.0 of 15 MB": the runtime's bytes read, scaled to its compressed size, plus the database's download; "Getting MedApp ready from this browser" from the caches; then "Starting…"); every Sign in button disabled until `startBackend` resolves; a failed start says "MedApp couldn't be downloaded" with Try Again (a reload). Signing in calls the real `POST api/auth/login` with the username and a fixed password.
- **Sessions across reloads:** the backend's one session lives in its memory, so a reload starts signed out. The demo remembers the username for the tab (`sessionStorage`, `medappFullDemo.user`, like a session cookie) and signs in again once the backend is up; meanwhile a start screen (`startScreen.tsx`) shows the progress. Signing out forgets it and goes to the login page with the backend still running (sign-in ready at once).
- **Caching:** `backend.js` (changed: its exports kept, the harness passes) gives the runtime a resource loader (`dotnet.withResourceLoader`) that keeps its files in Cache Storage (`medapp-full-demo-runtime`; their names carry their hash, so a kept copy is good for good, and files an older build used are removed after each start); the three JavaScript modules stay with the browser's HTTP cache. .NET 10's `dotnet.js` has no `cacheBootResources` any more (it fetches with `no-cache`). `forgetSavedDatabase()` now also stops saving from the page (a later request would save the old data back). **Reset the Demo** is on the login page and in Account Settings (`FullDemoResetCard`), and is the walkthrough's: it forgets the saved database and this browser's app storage and reloads, still signed in.
- **The walkthrough** runs on `CoachTour` with a host (`src/demo/coach/tourHost.ts`): the light demo's (`lightTourHost`, its checks moved out of `tour.ts`) or the full demo's (`src/fullDemo/tourHost.ts`). The steps and highlights are the light demo's; their records' IDs are swapped for the database's (`TOUR_RECORDS`): `relay` and `labCaseRelay` from `db-version.json`'s `tour`; Samuel Okafor and Tobias Lund looked up by name (patient search) and Dermatology's team from the relay pathway, as the seed doesn't name them (a `samuelOkafor`, `tobiasLund` or `dermatology` key in the seed's `Tour` would be used first). A test checks every ID in the steps' and highlights' paths has a record. The `whyNot` checks are read from the API (pinned, the relay's Triage and Testing, the lab case's status); the relay's last step no longer checks whether the appointment is booked. Account switches sign out and in through the API, save, and reload on the step's page. Each demo keeps its own place in the tour (they share an origin).
- **Proved in Chromium** against the built site served as Pages serves it (gzip, `max-age=600`, `404.html` for deep links): the accounts listed 0.9 s after navigation with sign-in disabled and the progress showing; for each of `admin`, `n.thornbury`, `r.aldous` and `s.varma`, Home shows Needs your attention and today's calendar; a pathway (Leah Corrin's), her patient page and the calendar open; a seeded file (the GP's report, a PDF) downloads through the backend; Sign Out goes back to the login page; Reset drops a note added and keeps the person signed in; the walkthrough's first four steps open and highlight their targets (Samuel Okafor's page by his ID here, the switch to the lab on Tobias Lund, back to Nadia Thornbury on the relay pathway). **Uploading fails in the backend** (Phase 3): the request reaches it with its body, but `AttachmentIntake`'s temporary file throws `FileNotFoundException` at `FileStream.Length` in the browser's file system, a 500 (the page says "The file couldn't be attached").
- **Timings** (Chromium, served locally): first visit ready 4.2 to 4.7 s unthrottled, 7.3 s at 50 Mbps and 17.6 s at 10 Mbps (15.6 MB of runtime, compressed, and 0.3 MB of database); **a second visit ready in 2.4 to 2.6 s** whatever the connection (3 requests to the network, 239 files from Cache Storage; the runtime's part from 1.1 s to 0.4 s), the rest being the backend's own start (services, model and first admin check, about 2 s); a reload while signed in reaches Home in 5.5 to 6.6 s (the start, signing in again, and Home's first queries, each slow the first time).

**For Phase 5:** the workflow publishes the backend (wasm-tools), builds the database, then runs `FULL_DEMO_BACKEND=<publish>/wwwroot FULL_DEMO_DATABASE=<db> npm run build:full-demo` and puts `dist-full-demo/` at `full/` inside the light demo's artifact. **GitHub Pages uses only the site's top-level `404.html`** (`/MedApp/404.html`, the light demo's), so a deep link under `/MedApp/full/` would load the light demo: the top-level `404.html` must start the full demo's app for paths under `/MedApp/full/` (its scripts are `/MedApp/full/assets/…`). Pages sends `max-age=600`: `dotnet.js` and `backend.js` aren't fingerprinted, so a new build reaches visitors within ten minutes; `db-version.json` is read with `no-cache`, so the nightly database is fetched on the next visit. The site is about 50 MB on disk (242 runtime files). Both demos share an origin, so their `medapp.` browser settings are shared (each account's settings load from its own database on sign-in).

## What's lost against the full app (for the owner, 22 November 2026)

Sharing between people (each browser has its own database), real security (it all runs on the visitor's machine: synthetic data only, never real patients), email and texts, live notifications, server rendering, outside services (PDS, FHIR), virus scanning, thumbnails, scheduled jobs except while the tab is open, and possibly PDFs. A first visit downloads 15 to 25 MB.
