# Monitoring

Admins' monitoring rules: read before changing them or adding a pathway command.

Admins' rules for being told what staff do to pathways (`/admin/monitoring`, `api/monitoring/rules`, admin-only), e.g. "Notify me when **sam** finishes **Bloods** on a **High or Urgent** priority pathway".
- **A rule** (`MonitoringRule`) belongs to one admin, who alone sees and changes it (another's is a 404). It names a person or anyone, an event (`MonitoringEvent`, stored by number: pathway created, stage finished, pathway completed, blocked or cancelled, someone assigned, a stage unlocked, a target date changed, a Required stage finished without its visit) and optional conditions: a minimum priority, a template, and for the three stage events a stage definition. It can be switched off. At most 50 each (`MonitoringRuleInput.MaxRulesPerAdmin`; count then insert, so two adds at 49 can make 51, accepted). No foreign keys: a rule naming something deleted stays, shows it as deleted and matches nothing.
  - **Switching** (`PUT api/monitoring/rules/{id}/enabled`) changes nothing else, so always works. An edit (`PUT .../{id}`) checks only the person, template and stage it newly names (`MonitoringRuleInput.CheckAsync`).
- **The person** is who did it, except for PathwayAssigned: the one assigned. A target date moved by a referral's waiting-time clock (a pause, a resume, a new priority) is a target date change by whoever made that change: pausing and resuming call the monitor too. **For StageUnlocked the person must hold `UnlockStages`** (400 otherwise, `MonitoringRuleInput.UnlockNeedsAdmin`; the page offers only them). StageFinishedWithoutVisit's person can be anyone (only holders of `FinishWithoutVisit` can do it, but a rule naming someone else just never matches).
- **How it fires:** every pathway command calls `IPathwayMonitor.NotifyAsync(change)` after saving its `PathwayChange`. `PathwayMonitor` reads what it did from its audit entries (`MonitoredActivity`, ignoring automatic status changes, notes and starts); loads the switched-on rules for those events (one query, only when a rule could match); matches them (`MonitoringRuleMatcher`: the template after the change, the higher of the priority before and after); leaves out the admin who made the change and, for an assignment, the assignee; skips (doesn't delete) rules of owners who no longer hold `ManageMonitoring` (`GetOwnersWhoCanMonitorAsync`, only when a rule matched); and sends each remaining admin one notification per change however many rules match (`MonitoringNotifications`).
- **Best effort, after the save:** not in the change's transaction (no outbox). A failure is logged and the change stands; only the request's own cancellation is rethrown. A failed insert is detached from the DbContext (`NotificationRepository.AddAsync`) so a later save doesn't retry it. Clinical follow-up must never rely on monitoring (hazard H-29).
- **Privacy:** a patient's export leaves monitoring notifications out (`Notification.IsMonitoring`, in `PatientExportMapper`): they're about staff. Anonymisation leaves monitoring and appointment notifications as they are (`Notification.HasFixedTitle`): fixed titles, no free text or patient details, and new messages must keep it so (the canary in `PatientPrivacyTests` checks).
- **Finishing without the visit** (decision 136 of `docs/centre-phases-3-5-plan.md`): a `StageFinished` entry whose details say `withoutVisit` with `visitRequirement: "Required"` gives two activities, `StageFinishedWithoutVisit` first, then `StageFinished`, so rules for either match, and an admin with both is told once, of the bypass (`MonitoredStageFinishedWithoutVisit = 38`, "Stage finished without visit": who, the stage and the pathway's priority and template, never the reason). A Suggested stage finished without its visit is only `StageFinished` (anyone may, after confirming). `Notification.IsMonitoring` is a set now (10 to 17, and 32 to 38).
- **Service alerts** (decisions 134 to 137 of `docs/centre-phases-3-5-plan.md`, PR 25): six time-based events, `ReferralNotTriaged = 8`, `ResultNotSignedOff = 9`, `VisitNotBooked = 10`, `SpecimenOverdue = 11`, `WaitBreached = 12`, `PauseReviewPassed = 13` (`MonitoringEvents.ServiceAlerts`), found by the **`service-alerts` job** every 15 minutes (`ServiceAlertsJob`, under the lease like every job: `jobs.md`), not by a change.
  - **A rule's days** (`ThresholdDays`, 0 to 90) are required for them and refused (400) for every other event. What each counts is in `ServiceAlertCandidates` (plain LINQ, the same in SQL and tests): Awaiting triage received more than N UK days ago (Information requested isn't counted: it waits on the referrer); a result awaiting sign-off (seen or not) reported more than N days ago; a visit Requested more than N days ago; a specimen open more than N days past taken plus its type's turnaround (0 is the lab's Overdue); a running clock whose target is less than N days away or passed (0: breached); an open pause whose review date passed more than N days ago (reported per pause, so a clock paused again is reported again).
  - **Conditions:** `SpecialtyId` (the referral's, else the pathway's; it applies to every event, changes too, matched by `MonitoringRuleMatcher`), the minimum priority (the pathway's, or a referral's requested priority while it has none), the template (not for `ReferralNotTriaged`: 400), the stage (also for `VisitNotBooked` and `SpecimenOverdue`). The person is refused (400) except for `ResultNotSignedOff`, where it's the responsible clinician. A condition about a pathway leaves out what has none.
  - **Each item once per rule** (`MonitoringAlertsSent`, key rule and item, cascade-deleted with the rule; kept when a rule is edited, so an edit doesn't report everything again). Each run sends **one notification per rule** with the count, saved in the same save as the rows (`IServiceAlertRepository.RecordAsync`), then pushed live (best effort): kinds `MonitoredReferralNotTriaged = 32` to `MonitoredPauseReviewPassed = 37`, fixed titles ("Referrals awaiting triage"), e.g. "3 Dermatology referrals have waited more than 2 days for triage." (`ServiceAlertNotifications`): a count, the days, the specialty's name and, for results, the clinician's username; never a patient or free text. Its `SubjectId` is the rule's specialty, and the bell opens the list it counts (filtered by specialty where the list takes one). Rules of owners who no longer hold `ManageMonitoring` are skipped, and nothing is marked.
  - **A convenience, never the safety net** (hazard H-29): clinical follow-up never relies on an alert; the lists and their counts are what to work from, and a stopped job is caught by Scheduled Jobs (decision 111). Phase 2's decision 38 (breaches shown, never sent) now has an exception an owner chooses: a `WaitBreached` rule.
- **Skipping, choosing a branch and reinstating** call the monitor like every pathway command, but no event watches them (`StageSkipped`, `BranchChosen` and `StageReinstated` give no `MonitoredActivity`); finishing a branch point is still a `StageFinished`.
- **Tests:** `PathwayCommandsMonitoringTests` checks every pathway command calls the monitor after its save, with the request's token; `MonitoringNotificationsTests` checks every event's message.
- **A new event:** add it to `MonitoringEvent` (a new number), `MonitoredActivity` (or, for a time-based one, `MonitoringEvents.ServiceAlerts`, `ServiceAlertCandidates` and `ServiceAlertNotifications`), `MonitoringNotifications` (its own `NotificationKind`, inside `Notification.IsMonitoring`'s range), the web app's `MONITORING_EVENTS` and `ruleText`, and the governance documents listing the events (`dpia.md` risk 24, the staff privacy notice, hazard H-29).
- **`medapp-dev`'s `reset_demo_data`** deletes every rule, notification choice and notification.
