# Auth

Sign-in, sessions, throttling, passwords, security headers, roles and permissions: read before changing authentication, authorisation or headers.

- On login a `UserSession` row is created and its ID goes into an HttpOnly cookie. `SessionAuthenticationHandler` checks it on every request and builds claims, including roles and the session ID (`SessionIdClaim`, read with `User.GetSessionId()`).
- **Sessions last 8 hours** from sign-in (`UserSession.Lifetime`), extendable to 24 at most (`MaxLifetime`; over 20 hours, so WCAG 2.2.1 allows the hard limit). Only asking extends one, never using the app:
  - `GET api/auth/session` returns `SessionResponse` (`expiresAtUtc`, `expiresInSeconds` by the server's clock, `canExtend`) and never extends it. `POST api/auth/session/extend` ("Stay signed in") moves the expiry to 8 hours from now, never past 24 from sign-in nor earlier than it was, and resends the cookie with that expiry.
  - Both use the cookie's session, are `[Authorize]` with no role, `no-store`, and a 401 once it's ended. `SessionTimeout` in `MedApp.Web` uses them to warn.
  - **The forced password change page has no timeout warning,** deliberately: `/change-password` is outside the signed-in layout and `PasswordChangeRequired` doesn't allow the session endpoints, so it ends at normal expiry and its user signs in again.
  - A lockout doesn't end a session yet (risk S5).
- The UI is always on the API's origin (`wwwroot` in production, Vite's proxy in development), so there's no CORS and the cookie is `SameSite=Lax`.
- **The cookie's name:** outside Development `__Host-medapp.session` (`Secure`, `Path=/`, no `Domain`, so only this host over https can set it); in Development `medapp.session`, not `Secure` (Vite is plain http). Only `ISessionCookieService` knows the name (`CookieName`, `TryGetSessionCookie`); read the cookie through it.
- **Sessions end when the password changes:** handlers call `ISessionService.RevokeUserSessionsAsync` (through `UserSessions.EndSessionsAsync`) inside `IIdentityTransactions.RunAsync` with the change, so both are kept or neither.
  - Your own change ends your other sessions; an admin's reset ends all the user's. **A role change ends none:** roles are read on every request.
  - An admin can sign a user out everywhere: `POST api/auth/users/{username}/sign-out-everywhere` (204, 404 for unknown), the Users page's confirmed "Sign out everywhere".
  - A new account action that changes how someone signs in should end their sessions the same way, in the same transaction. An open live-notifications connection isn't closed when its session ends (`docs/todo.md`).
- **Sign-in throttling** (`MedApp.API/Common/RateLimiting`), in front of Identity's lockout, which stays: `POST api/auth/login` allows 30 attempts a minute per client address (IPv6 by /64; the `login` rate limiting policy) and 5 a minute per username from anywhere (the `[ThrottleLoginByUsername]` action filter, since the username is in the body), right or wrong. Over either: a 429 `ProblemDetails` ("Too many sign-in attempts. Try again in N seconds.") with `Retry-After`, before the password is checked. Behind Traefik the address comes from forwarded headers. Counts are per API copy, in memory. Settings: `LoginThrottling` (`LoginThrottlingOptions`).
  - **Only a name that could be an account's is counted or looked up** (`UsernameRules.CouldExist`: at most 256 characters of `User.AllowedUserNameCharacters`, trailing spaces ignored). Any other is the usual 401 with no lookup (`IdentityAuthenticationService`), as SQL Server's collation would match some (a leading byte order mark, a trailing NUL, full-width letters) to real accounts. Over 256 characters is a 400 (`LoginValidator`); a body over 16 KB a 413 (`[RequestSizeLimit]`). The per-username key is trimmed, NFKC-normalised and upper-cased (`LoginUsernameLimiter.Key`).
  - **Each refusal is logged** at Warning with the limit and the client's key, never the username (`LoginThrottling.LogRefusal`).
  - **Sizing:** a site behind one NAT address (an HSCN gateway) shares the per-address allowance; if staff are refused at a shift change, raise `LoginThrottling:PerClientPermitLimit` for that deployment (per API copy), keeping the per-username limit at the lockout count. `MedAppApiFactory` sets both out of reach; `LoginThrottlingTests` restores them.
- **Common passwords are refused** when a password is set (creating, changing, resetting), never at sign-in: `CommonPasswordValidator` (`MedApp.Infrastructure/Common/Identity`), the NCSC's 10,000 most used, from `Passwords/common-passwords.txt` (licence in `Passwords/NOTICE.txt`), ignoring case. Generated passwords never match (a test makes 500).
- **Security headers** (`MedApp.API/Middleware/SecurityHeaders.cs`, first in the pipeline) on every response: `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, a `Permissions-Policy` turning off device features. Every `/api` response: `Cache-Control: no-store` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
  - **Pages, outside Development, get a CSP with a new nonce per response:** scripts only from the origin or with the nonce, styles from the origin and inline, `connect-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`. The nonce goes `SsrPages` → `X-MedApp-Csp-Nonce` → `server.mjs` (if base64) → `createSsrRouter` (`ssr.nonce`), onto every script and a `csp-nonce` meta tag. The fallback `index.html` has no inline scripts.
  - **Never add an inline script or `eval`:** the policy refuses them. A new external origin (fonts, images, an API) needs the policy changed, deliberately.
  - In Development non-API paths get only `frame-ancestors 'none'` (Vite, and Swagger UI's inline scripts). `SecurityHeaders:PageCspReportOnly=true` makes the page policy report-only: an emergency switch, no rebuild.
- A change to authentication, sessions, headers or a data flow should update `docs/security/threat-model.md` and the ASVS 5.0 Level 2 checklist, `docs/security/asvs.md`.
- **Roles and permissions** (`docs/centre-phase2-plan.md`, decisions 51 to 68). **Permissions are fixed in code; roles are data.**
  - **Permissions:** `Permission` with each one's group and description in `Permissions.Catalogue` (`MedApp.Application/Common/Identity/Permissions.cs`). Stored by **name** in `RolePermissions` (`RoleId`, `Permission`), never by number; renaming one needs a migration that renames its rows; a name code doesn't know grants nothing.
  - **Roles:** Identity roles (`ApplicationRole`: `Description`, `IsArchived`, `IsBuiltIn`, `CreatedAt`, `LastUpdated`); membership stays in `AspNetUserRoles`. A person's permissions are all their roles' together. **Every role grants `UseApp`** (own account, settings, notifications, notepad, own calendar; reading calendars, meetings and the setup lists), so "staff" means holding any role (`AppRoles.IncludesStaff`).
  - **`Admin`** is the one built-in role: its permissions are fixed in code (`Permissions.Admin`: every one but the clinical ones in `Permissions.NotForAdmin`: `TriageReferrals`, `RecordSpecimens` and `ProcessSpecimens`), it has no rows, and it can't be deleted (`IdentityErrors.BuiltInRole`, 409). **The Administrator-only permissions** (`ManageUsers`, `ManageRoles`, `ManageSecuritySettings`, `ViewAudit`, `ExportPatientRecords`, `ManagePrivacy`, `CorrectRecords`) grant nothing on any other role, even if a row says so (`Permissions.GrantedBy`).
  - **The standard roles** (`StandardRoles`, written by the migration `AddedRolePermissions` with fixed IDs): Admin; "All staff (before roles)" (`AppRoles.AllStaffBeforeRoles`), the old `User` role renamed, with exactly what staff could do before; and the starting roles Clinician, Nurse, Booking, Lab and Manager. `PermissionCatalogueTests` pins them to decision 68's table.
  - **Read on every request, with no cache:** `SessionService` reads the roles and their permissions in one query (`RolePermissionQueries.ForUserAsync`), and `SessionAuthenticationHandler` adds a `medapp:permission` claim for each (`SessionAuthenticationDefaults.PermissionClaim`). A change to a role, or to who holds it, applies on the next request. `whoami` lists them (`permissions`, sorted).
  - **Endpoints:** every controller action has `[RequirePermission(Permission.X)]` (its own or its controller's; several must all pass), or `[AllowAnonymous]`, or is one of five plain `[Authorize]` ones open to anyone signed in (`GET api/auth/session`, `POST api/auth/session/extend`, `POST api/auth/email/confirm`, the notepad). `PermissionPolicies` makes one policy per permission (`Permission:<name>`). **Never** `[Authorize(Roles = …)]`, a `Staff` policy or `User.IsInRole` in the API: `AuthorisationConventionTests` fails them, and any action without a permission. A new endpoint also needs its row in `AccessBeforeAndAfterPermissionsTests` (who may call it).
  - **A missing permission** is a 403 `ProblemDetails` with `code: "permission_missing"` and `permission` (its name), and the description in `detail` (`ApiAuthorizationResultHandler`); FHIR's stays an OperationOutcome.
  - **Handlers that check something themselves** get the caller's permissions on their actor (`PathwayActor.Permissions`, `CalendarActor.Permissions`, from `User.ToPathwayActor()` and `User.ToCalendarActor()`, `MedApp.API/Common/Authentication/ClaimsPrincipalExtensions.cs`) or a flag the controller sets from one (`User.HasPermission`). Never a role name. Today: someone else's calendar and templates (`ManageAnyCalendar`), anyone's working hours (`ManageClinics` or `ManageAnyCalendar`, `CalendarActor.CanSetHours`), meetings' `CanEdit` (`ArrangeMeetings`), finishing a Required stage without its visit (`OverrideStages`), the timeline's full view (`ViewAudit`), deleting anyone's file, listing deleted files, a note's `CanDelete` and withdrawing anyone's walk-in (`CorrectRecords`).
  - **Who is told or can be given work, by permission** (`IPermissionHolders`): note deletion requests go to holders of `CorrectRecords`; a stage left without its required visit to holders of `OverrideStages`; monitoring rules count while their owner holds `ManageMonitoring`; a "Stage unlocked" rule's person must hold `OverrideStages`.
  - **Only holders of `WorkPathways` can be assigned a pathway** (decision 68): anyone else is a 400 on `UserId` (`AssignPatientPathwayHandler.CantWorkOnPathways`: "{username} can't be assigned: their roles don't allow working on pathways."). Roles are read at the time, so someone already assigned stays assigned if they lose it.
  - **The staff list by permission:** `GET api/calendar/staff?permission=<name>` (`UseApp`) lists only the holders of that permission (exact name; an unknown one is a 400 on `Permission`). It's the people list for whoever can't read the users list (`ManageUsers`): a Manager picking assignees (`WorkPathways`) or a "Stage unlocked" rule's person (`OverrideStages`).
  - **Response flags follow the viewer's permissions,** as the endpoints do, so the page offers only what will work. A pathway's (`PathwayMapper`, from the actor's or the session's permissions): `CanWorkOnStages`, `CanEditDetails`, `CanAddNotes`, each stage's `CanEdit` and `AllowedStatusChanges` (empty without it) need `WorkPathways`; `CanChangeAssignments` `AssignPathways`; a stage's `CanUnlock` `OverrideStages`; `CanBeDeleted` `DeletePathways`. A note's (`PathwayNoteMapper`): `CanEdit` (its author) and `CanRequestDeletion` (not a holder of `CorrectRecords`) need `WorkPathways`; `CanDelete` needs `CorrectRecords`. A file's `CanDelete` (`AttachmentMapper`) needs `AttachFiles`, and `CorrectRecords` for someone else's. Null permissions in the mappers mean no viewer is known: only the record's state counts, and nothing needing `CorrectRecords` is offered; every response to a request passes the caller's.
  - **The web app follows permissions** (`MedApp.Web`): `whoami`'s `permissions` become `CurrentUser.permissions`, and `useCan(permission)` (or `can(user, permission)`, `src/auth/permissions.ts`) shows or hides each action, never a role name. Its copy of the catalogue (`PERMISSIONS`, `PERMISSION_CATALOGUE`) must match the API's: `permissionCatalogue.test.ts` reads `Permissions.cs` and fails when they differ. A page that needs a permission has `beforeLoad: requirePermission(...)`, which sends anyone without it to `/no-permission?permission=…`, saying what it needs. A `permission_missing` 403 becomes an `ApiError` whose `title` is the API's `detail` (so dialogs show what's missing where they show any refusal), and `PermissionMissingWatcher` shows it in a toast and reads whoami again, once no dialog is open, so typed text stays to be copied out (decision 61). The server stays the authority.
  - **Who may call what, in short:** `ViewPatients` reads patients, pathways, appointments, files, the timeline and the GP practice directory; `EditPatients` adds and edits them (and the demographics lookup, and keeps the practice directory); `DeletePatients`; `CreatePathways`; `WorkPathways` (stages, notes, details, status, asking for a note's deletion); `AssignPathways`; `OverrideStages` (unlock); `DeletePathways`; `BookAppointments`; `ArrangeMeetings` (meetings, team view, suggested times); `ManageClinics` (staff working hours; clinic patterns and sessions to come); `AttachFiles`; `RecordSpecimens` (record specimens taken and sent, edit them before they're sent; Clinician, Nurse, Lab) and `ProcessSpecimens` (receive, reject and report them; Lab), either marking one lost; `ViewInsights`; `ManageMonitoring`; `ManageSetup` (stage library, templates, specialties, activity types, closed days, sites and rooms, sites' opening hours, letter templates and their preview); `ManageUsers` (accounts, giving roles, specialty memberships, anyone's full name and job title, resets, sign-out everywhere, removing an email, the role list); `ManageRoles` (the Roles and Permissions page: the catalogue, a role's page, making, changing, archiving and deleting roles); `ManageSecuritySettings`; `ViewAudit` (audit and activity logs); `ExportPatientRecords`; `ManagePrivacy` (restriction, dispute, anonymisation, retention); `CorrectRecords` (note deletion, its requests). The controllers are the source of truth.
  - **The Roles and Permissions page** (`/admin/roles`, decision 62; `RolesController`, `MedApp.Application/Authentication/Roles`): `GET api/permissions` (the catalogue, `ManageRoles`), `GET api/roles` (every role, archived ones too, Admin first, with its permissions and `holderCount`; `ManageUsers`, as the Users page's picker reads it, which only Admin holds as it does `ManageRoles`), `GET api/roles/{id}` (with `holders`), `POST api/roles`, `PUT api/roles/{id}` (`{name, description, permissions, expectedVersion}`), `POST …/{id}/archive` and `…/restore` (`{expectedVersion}`), `DELETE …/{id}`, all `ManageRoles`.
    - **The rules** (`RoleRules`, `RoleValidation`): the built-in Admin role refuses every change (409, `BuiltInMessage`); an Administrator-only or unknown permission is a 400 on `Permissions`; `UseApp` is never stored (every role has it) and is dropped if sent; names are unique ignoring case (409) and at most 50 characters, descriptions 200. A role anyone holds is a 409 on delete (archive it); the delete is one `DELETE … WHERE NOT EXISTS` holder, so it can't take a role from someone given it at that moment.
    - **Two admins at once:** a role's `version` is Identity's `ConcurrencyStamp`; every change sends it as `expectedVersion` and gets a new one. The save is one `UPDATE … WHERE ConcurrencyStamp = @expected` inside the change's transaction, so of two saves at once one waits for the other, then finds the version changed: a 409 (`RoleRules.ChangedMeanwhileMessage`). The web page reads the role again and shows the API's words.
    - **Logged and told** (decision 60): each change and its activity log entry are saved in one transaction (`IIdentityTransactions.RunAsync`), through `ISecurityEventLog` (`SecurityEventKind.RoleCreated`, `RoleChanged`, `RoleDeleted` → `ActivityAction.RoleCreated = 22`, `RoleChanged = 44`, `RoleDeleted = 23`), by the admin. Details (`RoleChange.Details`): `roleId`, `role`, and only what changed: `renamedFrom`, `descriptionChanged` (never the words), `added` and `removed` (permission names), `archived`. A save that changes nothing records nothing. Then `ISecurityNotices.SendRoleChangeToOtherAdminsAsync` emails every other admin with a confirmed address ("An administrator changed a MedApp role": who, and `RoleChange.Summary()`). Role changes are kept by the operational purge with the other account changes.
    - **The page** (`MedApp.Web/src/pages/roles`): the list (`RolesPage`: name and description, people, permissions, status; Archive, Restore, Delete), and a role's page (`RoleEditorPage`, `/admin/roles/$id` and `/admin/roles/new`): ticks grouped as the catalogue (`rolePermissions.ts`), a search box, the Administrator-only group read only, who holds it (linking to the Users page), and a save that first shows what's added and removed and how many people hold the role. The built-in Admin role is shown read only. Both need `ManageRoles` (`requirePermission`).
    - **The Users page's picker** reads `GET api/roles`: roles that aren't archived, with their descriptions, plus an archived one the person already holds, marked so. `PUT api/auth/users/{username}/roles` still takes role names (not IDs, as the plan first said: names are unique, and pages loaded before the change keep working during a rollout).
    - **Gone:** `POST api/auth/roles`, `roles/assign`, `roles/revoke` and `DELETE api/auth/roles/{roleName}`. `GET api/auth/roles` (names only) stays one release for pages loaded before (`docs/todo.md`). `AssignRoleCommand` and `RevokeRoleCommand` stay for `medapp-dev` and the demo data.
  - **Nobody locks everyone out** (`ILastAdminGuard`, `LastAdminGuard`): taking Admin from the last active admin (holding Admin and not locked out), or deleting them, is a 409 (`IdentityErrors.LastAdmin`), checked under a SQL Server application lock in the change's transaction. Nobody changes their own roles (`OwnRoles`). An archived role can't be given to anyone new (400 `RoleArchived`); its holders keep it.
  - **Recovery when every admin is locked out:** `dotnet MedApp.API.dll grant-admin <username>` (`AdminGrant`), run by whoever deploys, gives an existing account Admin, logged as a security event (`AdminGrantedByCommand`, the activity log's `RolesChanged`, by nobody, the account as target) and at Warning.
  - **The holds are unchanged:** the forced password change and the two-factor setup hold run before authorisation. The admin two-factor requirement applies to holders of `Admin`.
  - There may be several admins; never assume one. `SelfUserOnly` limits a user to their own `{username}` route (beside `UseApp` on the password change).
- The app seeds no users (its only `HasData` is a default stage definition). **Locally, sign in as `admin` / `admin`:** `medapp-dev` makes it (`ensure_test_admin`, every `reset_demo_data`), bypassing the password rules, in local databases only.
- **A deployed database gets its first admin deliberately:** `dotnet MedApp.API.dll create-first-admin` (`FirstAdminSetup`) makes the built-in Admin role if it's missing (the migration makes it) and an admin with Admin alone (its permissions include `UseApp`, so they can change their own password) from `FirstAdmin:Username` and `FirstAdmin:Password`, only while there are no accounts, then exits. The chart's migrations Job runs it, with credentials from a Secret.
- **The server generates every new account's first password;** there's no default. `POST api/auth/users` takes only a username and returns the password once in `CreateUserResponse` (`IIdentityUserService.CreateUserAsync`, the reset's generator). The Users page shows it once (`OneTimePassword`, with copy) and forgets it when the dialog closes.
  - **It must be changed at first sign-in:** `IdentityUserService` sets `ApplicationUser.MustChangePassword` in the same save as a created or reset password; `UpdateUserPasswordAsync` clears it in the same update. A new password must differ from the current one (`UpdateUserValidator`).
  - **Enforcement:** `SessionService` reads the flag every request, `SessionAuthenticationHandler` makes it a claim (`SessionAuthenticationDefaults.MustChangePasswordClaim`), and `whoami` reports `mustChangePassword`. While set, `PasswordChangeRequired` (`MedApp.API/Common/Authentication`, between authentication and authorization) refuses every `/api` request, the hub included, with a 403 `ProblemDetails` (`code: "password_change_required"`), except every `AccountHold`'s allowlist (`GET api/auth/whoami`, `me/settings`, `features`; `POST api/auth/login`, `login/two-factor`, `logout`; the anonymous `password/forgot`, `password/reset`, `email/confirm`) and their own `PUT api/auth/users/{username}/update-password` (`AuthPolicies.IsOwnUsername`). Pages pass; the `_app` guard sends them to `/change-password`, and the API client sends any 403 with that `code` there with a full page load.
  - **Exempt:** the first admin, whose password is from the secret store (on kind, generated by `up.sh`), and every account `medapp-dev` makes or sets a password on (`create_user`, `set_password`, `ensure_test_admin`, `reset_demo_data`'s staff but its new starter).
  - **`CreateUserResult`** carries a password exactly when created (`Created(password)` or `Failed(result)`). It and the password responses never print the password in `ToString()`, and are sent `no-store`.
  - **Accounts created before #53** got the published `DefaultPassword1` and may still have it: an admin should reset them. Finding them is a to-do (`docs/todo.md`).
- Identity password and lockout rules are in `appsettings.json`'s `Identity` section.
