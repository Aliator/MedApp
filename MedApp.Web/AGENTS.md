# AGENTS

Guidance for AI coding agents working in `MedApp.Web`, the React app replacing the Blazor client. The repo-wide rules are in the root `AGENTS.md`; the migration plan is `docs/react-migration-plan.md`. `README.md` describes the layout and scripts.

## MedApp conventions

- **Only Astryx for UI.** Components map 1:1 to an Astryx component, or are composites built only from Astryx primitives (plan section 4). No other UI library and no hand-rolled widgets; keep `style` overrides to layout values the components have no prop for, using tokens.
- **Icons:** `AppIcon` from `src/components/shared/icons.ts`, never `@remixicon/react` directly. Add new icons there.
- **Routes** are thin files in `src/routes/` that point at a page component in `src/pages/`. Signed-in pages go under `src/routes/_app/`; admin-only routes use `beforeLoad: requireAdmin` (`src/auth/auth.ts`), which sends anyone else home.
- **Pages share one layout:** `Page` gives every page the same content width (`PAGE_MAX_WIDTH`), so titles and cards line up; don't pass `maxWidth` without a reason. A Back button (`backHref`/`onBack`) sits under the title, with `backLabel` as its tooltip.
- **Every page about one patient shows `PatientBanner`** under its header, through `Page`'s `banner` prop: the patient's page, Edit Patient, the export page, the patient's procedures, the procedure page, Edit Procedure and New Procedure so far, and any new page that shows or changes one patient's record. It's a clinical safety control (wrong patient), so don't put it inside something that folds or scrolls away: a page with a form taller than the window is a `fill` page whose form scrolls in its card under the banner (Edit Patient, Edit Procedure, New Procedure). The export page, a long printable document, is the one exception, and its banner heads the page. `src/app/patientBanners.test.tsx` renders every route under `/patients/$id` and `/procedures/` and checks each has the banner; a new route there must be added to it. Procedure responses carry the patient (`patient`: `ProcedurePatientResponse`), so a procedure page needs no extra patient read for it.
- **Fit the window; scroll the cards, not the page.** Pages that show more than a short form use `Page` with `fill`, and their cards fill the space. A card's open parts scroll inside it; the page never does.
  - The few pages that do scroll as a whole (Account Settings, the accessibility statement) line up with the rest: the main area always keeps room for a scrollbar on both sides (`STABLE_SCROLLBAR` in `AppLayout`), as each half of a half view does. Where scrollbars take up space (Windows), a page would otherwise move sideways as soon as it scrolls.
- **Build reusable patterns, not one-off page wiring.** When a page needs a layout or behaviour that another page could plausibly use, make it a composite in `src/components/` with its own test and a doc comment saying when to use it, then use it from the page. Look for an existing one first, and extend it rather than writing a near-copy. Signs a piece should be shared: you're reaching for flex or measuring code in a page, a second page wants the same thing, or the user describes it as a rule ("headers should look like…").
  - The shared building blocks so far:
    - `Page` and `PageHeader`: the frame, title and Back, and a `banner` under the header (the `PatientBanner`). A page's own messages (load and save errors) go in its `message`, a rounded banner in the middle of the header, so they never push the content down. On a form, `ValidationAlert` takes the form's `fields` and lists only the messages that aren't already on a field.
    - `TwoColumns`: two equal cards side by side.
    - `PanelCard` and `PanelHeader`: a header bar, a scrolling body and a pinned footer. With `isBodyKeyboardScrollable`, a body that's scrolling is a Tab stop named by the title (`useOverflows` tells it when), for a body with nothing the keyboard could scroll it by, such as a chart or a table of numbers. Leave it off for bodies of fields, buttons or links.
    - `FoldingCard`: sections under header bars that fold, scrolling together as one (not each on its own).
    - `CardSection`: titled sections in `ViewCard` and `FormCard`, whose titles become header bars.
    - `FormCard` with `fill`: a long form whose sections scroll inside the card, its footer pinned.
    - `DataTable`: a filling, paged table.
    - `ProcedureCells`: status, priority, due and progress cells.
    - `TextCell`: plain text in a table cell, kept to its lines.
    - `PageControls`: a list's page buttons (DataTable uses it); each "…" opens a box to type a page number.
    - `ListFilterBar`: a list's search as an Astryx PowerSearch, above its table (`DataTable`'s `search`): a token per filter, kept in the URL; choices take "is any of" and "is not any of". Every list with a search uses it, with a `list` key for its favourites.
    - `ListFavourites`: the star beside a list's search: the list's quick filters, and the person's saved searches (save, rename, delete, and one to start the list on), with the one showing named beside the star (a quick filter's name only with `ListFilterBar`'s `namesQuickFilters`, which a list turns off when it starts, or can start, on a quick filter its bar already shows as a token: My Tasks, the procedures lists, Stage definitions and Templates, where "All" is the empty bar; a saved search's name always shows, and wins over a quick filter with the same filters).
    - `RowCards`: a table's rows as cards, which `DataTable` switches to by itself when its columns don't fit even at their narrowest.
    - `RichTextField` and `RichText`: formatted text (stage notes and instructions, procedure notes), edited with a toolbar (Astryx's `RichTextEditor`) and shown read-only (Astryx `Markdown`, which never runs HTML). It's stored as Markdown, so plain text written before reads as it was. Tests can't type into it under jsdom: use `setRichText`, `typeRichText` and `richText` from `src/test/richText.ts`.
    - `RuleSentence` and `describeRule` (`src/pages/monitoring`): a monitoring rule as a plain sentence with the choices in bold, used by the Monitoring page's list and its editor's preview, so they always agree. Each row's switch is named by that sentence (a switch's name stays put; its state says on or off), held still with `isLoading` while its own save runs, and handles its own outcome with `mutateAsync` (a mutation runs per-call callbacks only for its latest call).
    - `NotificationBell`: the bell beside the MedApp heading, with the unread count and a list of the newest. `LiveNotifications` (in `AppLayout`) keeps a SignalR connection to the API's notifications hub, so new ones show at once on any page. Tests get a stand-in connection (`src/test/signalr.ts`): `liveHub.push('notification', …)` delivers one.
    - `PatientTimeline`: a patient's history across their procedures and appointments (the patient page): what's due, filter chips by kind and procedure (`ToggleButton`s), and the feed by UK day with "Load more" (an infinite query, `src/api/timeline.ts`). It sits in a card's scrolling body and lays out its own padding; the page holds its filters. The API decides what staff and admins see, so it shows whatever comes back.
    - `StageVisit` and `StageVisitTokens`: a stage's visit (a stage that involves one): the Visit part of the current stage's work (`StageWork`'s `visit`: where it stands, and Book Visit, Reschedule, Attended or Did Not Attend, Book Another), and the tokens beside a stage's title (`StageTitle`'s `extra`, `StageList`'s `renderVisit`). `stageVisit` works out where a stage's visit stands from the procedure's appointments, and `finishesWithoutVisit` whether finishing it needs the without-a-visit confirmation.
    - `AppointmentList`: a few of one patient's or procedure's appointments (status, when and with whom, what for), each opening on the Calendar.
    - `CalendarGrid` (`src/components/calendar/`): time as a grid of columns, 08:00 to 18:00 in 15-minute rows, with appointments, blocked time and meetings placed by time (generic items: `calendarItems.ts` makes them from a calendar, a meeting with its icon and "N attending"). Each column is `{key, label?, date, day, items, freeTime?}`: `dayColumns(days, items)` makes one person's day or week (unlabelled, named as days), and the Calendar page's team view gives a labelled column per person ("k.ashford, Tuesday 17 November") after an "Everyone free" column whose `freeTime` is the only time it lets you select (the rest is shaded, each free stretch labelled "Free, 10:00 to 11:00"). Selections and moves say their column (`CalendarSelection.column`; `onItemOpen(item, column)`), and `keepsItemsInColumn` stops an item being dragged to another person. More columns than fit scroll sideways inside the card, each keeping a minimum width, with the hour gutter sticky. A selection made with the pointer reaches `onSelectRange` just after the press ends, so a menu opened from it (the Calendar page's Book or Block, or New meeting in "Everyone free") isn't closed by that same press as one outside it. A held selection is a button (`selectionRef`, not a tab stop, letting presses through to the slots), because Astryx's `Popover` only anchors to a button: anchored to anything else, it opens in the window's corner. Both are from PR #96, and hold in every column. Selecting free time (click, drag, or the keyboard: one tab stop, arrows, Shift to extend, Enter), opening items and dragging movable ones are callbacks, so leaving them out makes it read-only. Past time is dimmed and today tinted, with the line for now (behind items, so it never strikes through their text) added after mount, so server and browser renders match. Items list their name, then what they're for, then their time; one under 10 minutes shows its words only in a tooltip. Astryx has no time grid: its cells are plain elements on theme tokens, its items Astryx cards.
    - `DayCalendar`: one person's day on a read-only `CalendarGrid` (`isHeadingHidden`, as its card's title dates the day), with Previous day, Today and Next day (Home); an appointment opens its procedure or patient. Meetings show read-only, like blocks.
    - `MeetingDialog`: a meeting's details for everyone (title, time, organiser, attendees, notes), and for admins Change and Cancel Meeting; and New Meeting: title, Who (a multi-select with Everyone and Clear; the organiser goes by default, with a checkbox), length, notes (about staff, never patients), suggested times for the next two weeks from `availabilityQuery` (refreshed as Who and length change, with Later suggestions), or a day and time by hand, saying who's busy then. The server's 409 is the final word, shown in the dialog. Opened from the Calendar page's New menu, a meeting on a calendar, or free time in the team view's "Everyone free" column (with `initial` people and time). Its date and time helpers are `src/utils/meetingTimes.ts`.
    - `StaffPicker`: whose calendar or templates, from the staff list, "My calendar" (or the label given) for yourself, so the URL leaves `staff` out for your own. The Calendar page and the calendar templates page use it.
    - `AppointmentStatusToken`, `ActivityToken` and `VisitRequirementToken` (`CalendarTokens.tsx`): an appointment's status (Needs booking, Booked, Attended, Did not attend, Cancelled), an activity in its colour, and a stage's Visit suggested or required, with icons when "Icons on statuses" is on. Use them wherever these show.
    - `BookAppointmentDialog`: booking, rescheduling, or adding to Needs booking, in one dialog. Whatever is known (patient, procedure, stage, a Requested appointment, a time picked on the calendar) is filled in; the rest have defaults, and the free times come from `src/utils/calendarSlots.ts`. Once a patient is chosen, it shows their name, date of birth and NHS number, as `PatientBanner` does, so staff can check who they're booking (hazard H-34). Booking or moving an existing appointment sends the status the page showed (`expectedStatus`), so the API refuses (409) rather than book over someone else; a 409 keeps the dialog open with the API's message and refreshes the calendars and appointment lists. Use it for every booking (the Calendar page's drag-to-move sends `expectedStatus` too).
    - `AppointmentDialog`: an appointment's details and everything its `can...` flags allow (book, reschedule, outcome, cancel with a reason, notes, book another). `BlockDialog`: adding or changing blocked time, and a template block for one day only.
    - `Attachments` (`src/components/attachments/`): the files attached to a patient, a procedure or a stage: an add area (Astryx `FileInput` as a drop zone, whose real button opens the file picker, so dragging is never the only way), each file's progress as it's sent (one at a time, with Cancel), and the list, newest first, with a thumbnail or type icon, name, type, size, who and when, the scan state as a token, Download and Delete (`ConfirmDialog`). Admins get Show deleted. `canChange` says whether files can change there now (the same rule the server applies: a patient's always, a procedure's unless cancelled or archived, a stage's while its notes can be edited); staff delete only their own files, and only where they can change. `isLocked` (the patient's record is restricted or anonymised: `whyCantChange(patient)`, or a procedure's `readOnlyReason`) hides adding and deleting for everyone, admins too, as the API refuses them; files are still listed and downloaded. Size and type are checked in the browser before sending (`checkAttachmentFile`), with the server's word final. Results are announced. `AttachmentsFold` is the same folded under a "Files" heading, fetched only once opened, for a part of a page that has several (each stage). A page with them holds `useAttachmentsState()` and passes it as `state`, so uploads carry on, and Show deleted stays, when it changes layout.
      - **Never show an uploaded file inline:** no `<img>`, iframe, `<object>` or new tab of a file's `/content`. Download always downloads (an `<a download>`, and the API sends `Content-Disposition: attachment`). The only images are the API's small re-encoded thumbnails (`/thumbnail`, only when `hasThumbnail`), shown decoratively.
      - Uploads go through `uploadAttachment` (`src/api/attachments.ts`), with XMLHttpRequest for its progress; tests answer it with `stubXhr()` (`src/test/xhr.ts`).
    - `ColourField` and `ColourSwatches`: picking a colour (the browser's colour input in an Astryx Field), and small squares showing a few.
    - `PasswordChangeFields` and `usePasswordChangeForm`: changing your own password (current, new, confirm, with the server's messages on the fields), used by Account Settings' Change Password page and by `/change-password`, where someone with a password an admin gave them must choose their own. `NewPasswordFields` is the new password and its confirmation on their own (`/reset-password`, from an emailed link).
    - `StandalonePage`: a page outside the signed-in layout (no side nav): MedApp over one card with the page's heading, centred. `/login`, `/forgot-password`, `/reset-password`, `/confirm-email` and the hold pages (`/change-password`, `/set-up-two-factor`) use it.
    - `OneTimeCodeField`: a two-factor code (`authenticator`: 6 digits, `one-time-code` AutoFill, a number pad; `recovery`; or `either`). Use it wherever a code is asked for.
    - `TwoFactorSetup` (`src/components/account/`): setting up an authenticator app from start to finish: a new key as it opens, shown as a QR code (an inline SVG from the server's path, black on white whatever the theme, the one place fixed colours are right: cameras need dark on light) and as text to copy, the password and a code to turn it on, then the recovery codes. Used by Account Settings' Security page and `/set-up-two-factor`.
    - `RecoveryCodes`: recovery codes shown the only time they can be, with a warning, Copy, and Download (a .txt made in the click handler). It takes the focus and tells screen readers, never reading the codes out.
    - Emailed links (`/reset-password`, `/confirm-email`) carry their token in the address's fragment, never the query: read it with `useEmailLink` (`src/auth/emailLink.ts`), which reads it after mounting (the server never sees it, so the server's render shows "Reading the link") and then takes it off the address. A link that does something on the server waits for a click (link scanners open links). `/confirm-email` needs the link's own account signed in (the API refuses anyone else): signed out, it keeps the link in this tab (`pendingEmailConfirmation`, a `medapp.` key in sessionStorage, cleared once the link is used or refused) and sends them to `/login?redirect=/confirm-email`, which brings them back to confirm it with a click; signed in as another account, it says so and offers Sign out. The login page's `redirect` takes only a path in this app (`safeRedirectPath` in `src/auth/redirect.ts`: one leading `/`, never `//`, no backslashes or control characters), and an account on hold still goes to its hold page first.
    - `PatientBanner`: who the patient is, never foldable, under the page header (`Page`'s `banner`), a region named for the patient ("Patient: Ahmed, Freya", so two in half views are told apart): `SURNAME, Forename` in bold (the surname upper-cased by CSS, its text in its own case, so screen readers read it as a name), the date of birth with the age (`ageDescription`: days under 4 weeks, weeks under 3 months, months under 2 years), and the NHS number as `XXX XXX XXXX` (or "No NHS number"), with small tokens when the record is restricted, disputed or anonymised. It wraps in a narrow window or half view. It's the control for clinical safety hazards H-01 and H-02 (`docs/clinical-safety/hazard-log.md`), so keep everything it shows.
    - `NhsNumberField`: the NHS number input (an Astryx `TextInput` composite, `src/components/forms/`): accepts the number with or without spaces, checks the check digit as it's typed (too few digits only once the field is left), and shows a Look up button when the demographics lookup is available (`demographicsStatusQuery`, `useLookUpDemographics` in `src/api/demographics.ts`; the lookup only fills the form if the number hasn't changed meanwhile). `formatNhsNumber` (`XXX XXX XXXX`), `isValidNhsNumber` and `spokenNhsNumber` (for screen readers) in `src/utils/nhsNumber.ts` format and check one anywhere else.
    - `SnomedConcept` and `SnomedCell` (`src/components/procedures/`): a SNOMED CT code and term written `80146002 | Appendectomy`, as a line or a table cell; `stageDescription` puts it under a stage's description in a list.
    - `PatientFlagBanners`: a patient's restricted, disputed and anonymised banners, for every page about the patient (in `Page`'s `message`): the patient's page, Edit Patient, their procedures, and the procedure page (from `procedure.patientFlags`). `PatientFlagDialog` (restricting counts the procedures under way and open appointments, and asks the admin to confirm their work stops), `AnonymiseDialog` (a typed confirmation) and `KeepRecordDialog` are the admin's privacy actions, and `PatientAccessReport` is a patient's latest activity log entries (admins).
    - `PasswordChangeFields` and `usePasswordChangeForm`: changing your own password (current, new, confirm, with the server's messages on the fields), used by Account Settings' Change Password page and by `/change-password`, where someone with a password an admin gave them must choose their own.
    - Charts, in `src/components/charts/`: `ChartCard` (a chart's card: its title, a summary in words, and a button to show it as a table; one height in both views, `CHART_CARD_HEIGHT` (30rem, so it grows with the text size), so a long chart or table scrolls inside the card, a Tab stop while it does, and never lengthens the page. Insights is the exception to "the page never scrolls": four charts and the tiles don't fit one window, so the area under its filters scrolls, a column of these fixed-height cards), `BarChart` (bars or columns, one series or several, side by side or stacked, with a tooltip and a legend), `ChartTable` (a chart's numbers as a table, rows linking where bars go) and `StatTile` (a headline number against an earlier one, as a link, or a plain card when nothing lists what it counts). Each `ChartCard`'s button names its card ("Show Table of Overdue by assignee"), so a list of buttons can tell them apart. Astryx has no charts, so `BarChart` wraps Recharts (the library Astryx's dashboard templates use); use Recharts only inside these composites. Every chart goes in a `ChartCard`, so it has a summary and a table (WCAG 1.1.1); the chart itself is one image to screen readers. Colour series from `SERIES_COLOURS` in order (theme tokens, checked for colour blindness), never fixed colours. A page with charts keeps its query in a module of its own (`insightsPageQuery.ts`), so its route's loader doesn't pull the chart library into the main bundle.
  - Clickable things shade under the pointer: list rows do already, and `PanelHeader` (with `onClick`) and `ColourField` do the same. Keep it up for new clickable surfaces.
    - `SetupCells`: the Active/Archived token and name cells of the setup lists (stages, templates, activity types, calendar templates); the name cell takes a `token` to show beside the name (a stage's Visit required).
  - **Half views** (`src/components/pages/halfView.tsx`, `AppLayout`): every side nav item has a button (shown on hover, like the pin) that opens its page beside the current one, each in its narrow layout, with the nav folded away. With a half view open, each item has a left and a right button instead (both greyed out while either side shows its page), and clicking the item itself opens its page on its own, closing the half view (or, by a setting in Account Settings, on the left). A page with a narrow layout asks `useIsNarrow()` (narrow window or half view), never the window query directly. The second page runs in a router of its own, so its links and Back stay in its half.
  - Keep state that should survive a layout change (what's open or folded) in the page and pass it in, as the procedure page does, rather than inside each collapsible.
- **Holds:** an account can be held to one task before anything else; the API refuses every other `/api` call with a 403 whose `code` names it. The signed-in layout's guard (`requireSignedIn` in `src/auth/auth.ts`, from whoami) sends them to its page, outside the layout, and `src/api/client.ts` sends an open page there with a full load on that 403. In order: `password_change_required` → `/change-password` (`mustChangePassword`), then `two_factor_setup_required` → `/set-up-two-factor` (`mustSetUpTwoFactor`: an admin, while Admin Settings requires two-factor for admins). A hold page's route lets in only those held (`requirePasswordChange`, `requireTwoFactorSetup`) and loads only what the API still allows them (their settings).
- **Email:** `featuresQuery` (`src/api/account.ts`) says whether the server can send email. When it can't, nothing offers what needs it: no "Forgot your password?", no email field on Add User, and the Email Address page says email isn't available.
- **Password re-checks:** a session alone can't change how an account signs in or where its reset links go. Changing or removing the email address, turning two-factor on (`TwoFactorSetup`) or off, and getting new recovery codes each ask for the password, with the signed-in user's name in a hidden `autoComplete="username"` field beside it for password managers (inside a dialog only while it's open). A 400 shows on its field (`password`, `code`, `email`); a 409, 423 (locked) or 429 (too many tries) shows in the API's words (`refusalMessage` in `src/api/errors.ts`).
- **Notification choices** (Account Settings' Notifications card, `NotificationSettings`) are the exception to the next point: the server checks them before sending, so they're kept only on the server (`notificationPreferencesQuery`), not in `settingsStore`.
- **Settings** (Account Settings) live in `src/app/settingsStore.ts`: declare a key with `defineSetting`, read and write it with `useAppSetting`. They're kept in this browser and with the account (`SettingsSync` loads them on sign-in and saves changes), so they follow people between browsers. A provider per area turns them into values: `colorMode`, `colours`, `textSize`, `navSettings`, `listSettings` (rows per page, where procedure lists start), `accessibility`, and `favourites` for saved searches.
  - **Signing out clears this browser** (`clearStorageAtSignOut`, from `useLogout`): every `medapp.` key in localStorage and sessionStorage, except settings declared with `defineSetting(key, {keepOnSignOut: true})`, which is only for purely visual ones (`colorMode`, `colours`, `textSize`, `accessibility`). Signing in loads the account's settings before opening the start page (`useEnterApp`), so nothing is lost. Anything new kept in the browser goes under a `medapp.` key, so sign-out clears it; never keep patient details there.
  - Pins in the side nav are a setting too (`medapp.pins`), so they follow the account rather than staying in the browser. Their labels come from the labels lookups (`patientLabelsQuery`, `procedureLabelsQuery`), which record nothing in the activity log; never label a pin from a record's own endpoint, which records a view.
  - **Signing out first saves any setting still waiting to be saved** (`flushSettings`, which `SettingsSync` registers a flusher for), then signs out and clears the browser, so a pin made just before isn't lost.
- **Accessibility:** the aim is WCAG 2.2 AA (`docs/todo.md` lists what's left; the statement is `/accessibility`).
  - The settings in `src/app/accessibility.tsx` work through CSS that `AccessibilityProvider` adds: theme tokens on every theme root, and a few rules, outside Astryx's cascade layers so they win. A new component that uses Astryx tokens and components follows them without more work. Don't hard-code durations, focus rings, font families or control heights.
  - Pages name themselves: `Page` sets the browser tab's title and announces the page to screen readers (`usePageTitle`). Announce other changes people see but a screen reader wouldn't mention with `useAnnounce()`. `DataTable` already announces a list's results, every form page announces its save ("Patient saved", "Stage added", and so on, said before it navigates away, so the next page's name follows it), and the procedure page announces a finished stage and the next one, and a deleted procedure. A new form or action that saves and moves on does the same.
  - Statuses and priorities go through `StatusToken`, `PriorityToken` and `OverdueToken`, which add icons when "Icons on statuses" is on.
  - Custom colours (Account Settings, Colours) are checked as they're picked: a page, card (with its header bars) or side nav colour that leaves the main or the secondary text under 4.5:1 gets a warning on its field (`textContrast` in `src/app/colours.tsx`, with the WCAG maths in `src/utils/contrast.ts`). If the theme's text colours change, change `TEXT_COLOURS` too; a test compares them. Three bundled themes are just under on secondary text (`docs/todo.md`).
  - Sessions time out (WCAG 2.2.1): `SessionTimeout` in `AppLayout` warns five minutes before, with the time left and Stay signed in, and on timing out goes to the login page, which says why (`/login?expired=true`).
  - Keyboard shortcuts are in `KeyboardShortcuts` (`?` lists them). They start off, and never fire while typing in a field or a dialog; keep both true for new single-key ones.
    - The one exception is save, Ctrl+S (⌘S on a Mac; `SaveShortcut.tsx`). It has a modifier, so it can't fire by accident while typing (WCAG 2.1.4 is about single keys): it's always on, whatever the shortcuts switch says, and works from inside a field. It saves the form holding the focus, or the page's only form; never the page behind a dialog, and nothing when it can't tell which of two forms (a half view) was meant. While any form is open it always stops the browser's Save page dialog, and when it then saves nothing (no form chosen, or nothing changed) a brief toast says so, which screen readers hear too. A `save` that has nothing to do returns `false`.
    - `FormCard` joins by itself. Anything else that saves joins with `useSaveShortcut(ref, save)`: the stage notes (`StageWork`) do, and a `ConfirmDialog` that is a form passes `hasSaveShortcut` (Add or Edit Stage). Dialogs that only ask "are you sure?" don't.
  - Run the axe audit (`npm run a11y` in `tools/ui-parity`, with the AppHost running) on the screens every visible change touches (`-- -g "<screen>"`). The run of every screen takes about ten minutes, so it's only for when the user asks. Add new screens to `screens.ts` so it covers them.
- **Server-side rendering:** every page is rendered on the server first (`src/entry-server.tsx`, `server/server.mjs`; see `README.md`), then hydrated, so:
  - **Rendering must work without a browser.** Don't touch `window`, `document`, `localStorage` or `matchMedia` while rendering: do it in effects, or behind `typeof window`. Read settings with `useAppSetting`, which uses the account's saved settings on the server.
  - **A page with data gets a loader.** Its route's `loader` preloads the same query the page reads: `preload(context.queryClient, query)` (`src/api/preload.ts`). Put the query in an exported function that the page and the loader both call (`patientsListQuery`, `proceduresListQuery`), so their keys match. List settings outside React come from `listSettingsFor(queryClient)`. On the server the loader waits; in the browser it only starts the fetch. A feed fetched a page at a time (`infiniteQueryOptions`, e.g. `patientTimelineQuery`) preloads its first page the same way.
  - **The first render must match the server's.** Nothing random or time-based in render output that isn't the same on both. Anything that depends on this browser shows after mount.
  - `src/entry-server.test.tsx` renders whole pages as the server does (in Node). Extend it for anything server-specific.
- **List pages** fill the window: `Page` with `fill`, and `DataTable` stretches to the bottom with its page controls pinned there. Their search is a `ListFilterBar` above the table (no Search button or dialog); a list that starts filtered (My Tasks on Not started, Stages and Templates on Active) shows that filter as a token and keeps an "all" value in the URL for when it's removed. They keep page, sort and filters in the URL: the route parses them with `validateSearch` (`src/pages/listSearch.ts`), then passes `search` and `onSearchChange` to the page as props, so pages are testable without the real router. Lists come from the API's paged search endpoints (`src/api/search.ts`).
- **Colours:** people choose the page, card and side nav colours for each mode (Account Settings, Colours: a colour theme, or Custom). `ColoursProvider` (`src/app/colours.tsx`) applies them through the theme's own background tokens (`--color-background-body`, `-surface`, `-card`, `-muted`, `-popover`). The side nav is always dark (a nested dark `Theme` in `AppLayout`).
  - **Every new component, page and surface must follow the chosen colours.** Use those tokens (or Astryx components, which do), never fixed colours or a theme's own defaults. Header bars use `-muted`, cards `-card`, menus and popovers `-popover`.
  - A surface that needs a chosen colour the theme doesn't route through a token: add the token to `ColoursProvider`, from the chosen colours, rather than hard-coding it.
  - Inside the side nav, the dark `Theme` sets its own tokens, so a surface there that should follow the app (a row's menu) uses `--medapp-card-background` and takes the app's mode (see `RowMenu` in `AppSideNav.tsx`).
  - Check a new component in light and dark mode, and with a colour theme other than Standard (Account Settings, Colours), before calling it done.
- **Data:** TanStack Query. Reads are queries keyed by resource (`['patients']`, `['patients', id]`); writes are mutations that invalidate them. Call the API through `api` + `unwrap` from `src/api/client.ts`.
  - **Times from the API** (`...AtUtc`, `createdAt`, `lastUpdated`) are UTC: show them with `formatDateTime` or `timeAgo` (an appointment's time with `formatAppointmentTime`: "Mon 23 Nov 2026, 10:00 to 10:30"), and turn one into a `Date` with `parseUtc` (`src/utils/dates.ts`), never `new Date(value)`, which reads a time without a `Z` as the browser's local time. Dates (`yyyy-mm-dd`: due dates, dates of birth) are whole UK days: `formatDate` and `formatShortDate`. `dueDateUtc` is a moment (the end of the due day, UK time), for comparing with now; show `dueDate`. Tests run in New York time (`vite.config.ts`), so a time misread as local fails them.
- **Forms:** fields in `useState`; on a 400, show `fieldStatus(errors, field)` on each field. The server's FluentValidation is the source of truth, so don't duplicate its rules here. The one exception is the NHS number's check digit (`NhsNumberField`), checked as it's typed so a mistyped number is caught before a lookup or a save; the server checks it too.
  - Fields side by side line up: Astryx puts a description between the label and the input, so when one field in a row has a description, give the others `BLANK_DESCRIPTION` (`src/components/forms/fieldSpace.ts`). Do the same for a description that comes and goes, so the input doesn't jump.
  - Nothing moves when an error shows: the theme gives every field a reserved, empty line under its input that its error message fills. A field that never shows an error can drop it with `containerStyle={NO_STATUS_LINE}`.
- **Tests:** every component and page gets a Vitest test next to it (`X.test.tsx`). Use `renderWithApp` / `renderApp` and `mockFetch` from `src/test/render.tsx`. Synthetic data only, and NHS numbers only from the 999 range, which is never issued to real people.
  - **Effects must survive running twice.** In development the app starts inside `<StrictMode>` (`entry-client.tsx`), which runs every effect, cleans it up and runs it again at once. An effect that reads and clears something (the address's fragment), or cleans up a cache, must keep the first result and not lose or fetch it again. Test such an effect with `renderWithApp(..., {strict: true})`; the production build, which CI's E2E tests, runs effects once and won't catch it (review of #109).
- **Before calling a change done,** check only what you changed, as CI runs everything (root `AGENTS.md`, Testing a change):
  - the changed files' tests (`npx vitest run <files>`)
  - `npm run typecheck`
  - ESLint on the changed files (`npx eslint <files>`)
  - for a visible change, with the AppHost running (start it if it isn't): the UI parity screenshots of just the screens you changed (`npm run parity:react -- -g "<screen>"` in `tools/ui-parity`), looked at, and the axe audit of those screens (`npm run a11y -- -g "<screen>"`)
- **Versions:** `@astryxdesign/*` are pinned exactly (plan Q14). Upgrade them only in their own PR, after reading the changelog, then run `npx astryx upgrade` and `npm run theme:build`.
