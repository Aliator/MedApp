# AGENTS.md

Guidance for AI coding agents working in this repository.

## Overview

MedApp is a patient and procedure management app. It has a .NET 10 Web API backend built with Clean Architecture, CQRS and MediatR, and a React frontend (`MedApp.Web`: React 19, TypeScript, Vite and Astryx). The original Blazor WebAssembly frontend is kept, deprecated, as `MedApp.Client.Deprecated`. Data is stored in SQL Server through EF Core, and ASP.NET Core Identity handles users. Authentication is a custom cookie-based session scheme.

## Commands

Run everything from the repo root. `global.json` pins the SDK to 10.0.x, and every project targets `net10.0`.

```bash
dotnet build MedApp.sln                     # build everything
dotnet test MedApp.UnitTests -c Release     # unit tests (CI's unit-tests job; Release, as medapp-dev locks Debug)
dotnet test MedApp.UnitTests -c Release --filter "FullyQualifiedName~UpdatePatient"   # run a subset
dotnet test MedApp.IntegrationTests         # the API against SQL Server in Docker (needs Docker running; about 1.5 min)

# End-to-end tests (Playwright) against the running AppHost, signed in as the local dev admin. They make their own
# synthetic data and delete what the app can delete (MedApp.E2ETests/README.md lists what stays). Install Chromium once: pwsh MedApp.E2ETests/bin/Debug/net10.0/playwright.ps1 install chromium
E2E_USERNAME=admin E2E_PASSWORD=admin dotnet test MedApp.E2ETests

dotnet run --project MedApp.AppHost         # everything (needs Docker running): SQL Server container, API, React app, Aspire dashboard
#   React app:      http://localhost:5173   (MedApp.Web; its commands are in MedApp.Web/README.md)
#   API + Swagger:  https://localhost:7038/swagger
#   Dashboard:      the login URL the command prints

# EF Core migrations (dotnet-ef 10.x is installed as a global tool)
dotnet ef migrations add <Name> --project MedApp.Infrastructure --startup-project MedApp.API
dotnet ef migrations has-pending-model-changes --project MedApp.Infrastructure --startup-project MedApp.API   # model and snapshot in sync?

# Applying migrations to the dev database (the AppHost's SQL container) needs its connection string.
# The sa password is in the AppHost's user secrets.
PW=$(dotnet user-secrets list --project MedApp.AppHost | sed -n 's/^Parameters:sql-password = //p')
dotnet ef database update --project MedApp.Infrastructure --startup-project MedApp.API --connection "Server=127.0.0.1,14330;Database=MedApp;User ID=sa;Password=$PW;TrustServerCertificate=True"
```

See [Migrations](#migrations) before adding or applying one.

To try the production image in Kubernetes, `deploy/kind/up.sh --demo-data kind-demo` runs MedApp on a local kind cluster at http://localhost:8080 (and https://localhost:8443), beside the AppHost and with a database of its own. It deploys with the Helm chart in `deploy/helm/medapp`, whose migrations Job runs the EF migrations bundle built into the image, then makes the first admin. The chart also runs Azurite (the Azure Storage emulator, port 10000) for attached files, unless `attachments.azurite.enabled` is off. The chart is locked down (network policies, the `restricted` Pod Security Standard, read-only filesystems, secrets from External Secrets), so a new container, port or connection in it needs a matching change there. Each API pod has two containers from the same image: `api`, and `pages`, the Node page server, with none of the API's secrets (see Server-side rendering under Local dev gotchas). `up.sh --argocd` has Argo CD deploy from git instead. Each merge to `main` runs the Publish workflow, which pushes the image to GHCR and records the commit, with the image's tag, on the `env/kind` branch that Argo CD follows (`deploy/argocd/README.md`). Roll back by reverting the change on `main`. Never commit to an `env/*` branch by hand except in an emergency, and know that the next deploy replaces it.

Azure (AKS, Azure SQL, Key Vault, Azure Container Registry, and a storage account for attached files) is in `deploy/azure`. It's written and checked, but **not deployed**. Its Bicep (`main.bicep`) is compiled and linted in CI. Deploying it costs money, so never run `deploy.sh` or `bootstrap.sh` without the user asking. Once it's set up, the Publish workflow's `azure` job deploys each merge through the `env/azure` branch; until then the job is skipped. Chart versions for both clusters are in `deploy/versions.sh`. See the `README.md` in each. CI lints the chart (the `helm` job), so after changing it run `helm lint --strict deploy/helm/medapp --set image.tag=ci`.

**Testing a change: only what it touches.** CI runs every suite on each PR, on GitHub's machines (about 9 minutes), and a PR merges only once it's green. So locally, run only what checks your change, and leave the rest to CI:
- **Use Release locally** (`-c Release`) for builds and tests. A Debug build of either test project rebuilds `medapp-dev` into the folder the running tool has locked (see [Dev MCP server](#dev-mcp-server-medapp-dev)).
- **Build** the projects you changed, with no new warnings (`dotnet build <project> -c Release`). CI's `unit-tests` job builds the whole solution.
- **.NET unit tests:** only the ones for the code you changed, e.g. `dotnet test MedApp.UnitTests -c Release --filter "FullyQualifiedName~UpdatePatient"`.
- **`MedApp.Web`:**
  - the changed files' tests (`npx vitest run <files>`)
  - `npm run typecheck`
  - ESLint on the changed files (`npx eslint <files>`)
- **Integration tests** start SQL Server and Azurite in Docker. Run them only for something unit tests can't reach, such as SQL translation, Identity, a migration, middleware or the demo data seed. Then run only that fixture (`--filter "FullyQualifiedName~<Fixture>"`).
- **A visible change is looked at in a browser.** Nothing in CI does that. Start the AppHost if it isn't running (it's the light setup). Then capture the UI parity screenshots of just the screens it touches and look at them. Run the axe audit on just those screens too (`npm run a11y -- -g "<screen>"` in `tools/ui-parity`). The accessibility statement promises the checks run again whenever screens change.
- **A change to how MedApp is deployed is tried on kind** before it merges. That covers the chart (`deploy/helm`), the Dockerfile or what's in the image, `deploy/kind` or `deploy/argocd`, and a new setting, secret, port, container or connection the API needs outside Development. Start the cluster, run `deploy/kind/up.sh`, and check the app answers. CI lints and renders the chart, but never installs it.
- **Not locally**, unless the user asks, a rule above calls for it, or you're chasing one failing test:
  - the full unit, web or integration suites
  - E2E tests
  - the whole UI parity set, or the axe audit of every screen
  - the kind cluster
- **When CI fails,** run only the failing tests locally.

## Backend conventions

### Feature slices (vertical, one folder per use case)

```
MedApp.Application/<Area>/Commands/<Action><Entity>/
    <Action><Entity>Command.cs     # sealed record : IRequest<TResponse>
    <Action><Entity>Handler.cs     # sealed class, primary-constructor DI, IRequestHandler<,>
    <Action><Entity>Validator.cs   # sealed class : AbstractValidator<TCommand> (when input needs checking)
MedApp.Application/<Area>/Queries/<Get...>/
    <Get...>Query.cs / <Get...>Handler.cs
```

To add a feature end to end:
1. Add or update the entity in `Domain`. Add or update its `IEntityTypeConfiguration` in `Infrastructure/Data/Configurations/<Area>/`, which `ApplyConfigurationsFromAssembly` picks up automatically.
2. Add request/response DTOs in `Contracts/<Area>/{Requests,Responses}/`.
3. Add the command/query, handler and validator in `Application`. MediatR handlers and validators are registered by assembly scanning, so no DI changes are needed for them. A handler that reads or changes patient data records it in the activity log (see [Activity log and patient privacy](#activity-log-and-patient-privacy)).
4. For a new repository, put the interface in `Application/<Area>/Repositories/` and the implementation in `Infrastructure/Data/Repositories/`. Register it in `AddRepositories()` in `MedApp.Infrastructure/Common/Extensions/ServiceExtensions.cs`.
5. In the controller action, map the request into a command, call `mediator.Send(...)` and return the result. Keep business logic out of controllers.
6. If the schema changed, add an EF migration and review it (see [Migrations](#migrations)). Migrations are **not** applied at startup.
7. Add unit tests for the handler and the validator.
8. If the change alters what personal data is held, who can see it, where it goes (a recipient, a sub-processor, a region) or how long it's kept, update `docs/governance/` in the same PR: at least `data-inventory.md` and `dpia.md`, and any other document it makes untrue (see `docs/governance/README.md`).

### Validation and errors

- Validation runs in the MediatR pipeline (`ValidationBehaviour` in `Application/Common/Behaviors`). It throws `FluentValidation.ValidationException`, which `API/Middleware/ExceptionHandling.cs` turns into a 400 `ValidationProblemDetails`.
- **Preferred style for new code:** throw `NotFoundException` (becomes 404) or `ConflictException` (becomes 409) from handlers. The Procedures area follows this. A wrong username or password throws `InvalidCredentialsException` (becomes 401).
- An `/api` path that matches no endpoint is a 404. Every other unknown path gets the React app's `index.html`, so client-side routes work on reload.
- The Patients and Auth slices predate that and return `null`/`bool`/`IdentityResult`, leaving controllers to choose the status code (except that deleting a patient who has procedures or appointments throws `ConflictException`). Keep that existing style when you edit those slices, unless the task is to migrate them.
- Unhandled exceptions are not caught by the middleware, so they surface as 500s.

### Lists

- Lists are filtered, sorted and paged by the API: `GET api/patients/search`, `GET api/auth/users/search`, `GET api/procedures/patient-procedures/search`, `GET api/procedures/audit/search`, `GET api/activity/search`, `GET api/patients/retention-review` and `GET api/appointments/search` return a `PagedResponse<T>` (`items`, `page`, `pageSize`, `totalCount`, `totalPages`). `pageSize` defaults to 10, with a maximum of 100.
- Sort and filter in plain LINQ that EF can translate (see `PatientSearch`), so the same code runs in SQL and in unit tests. Always end the order with a unique key (`ThenBy(x => x.Id)`), or paging can repeat or skip rows.
  - The retention review is an exception too: SQL narrows it to patients last changed long enough ago, then the schedule's rules, which depend on each patient's age, sort and page it in memory (`SearchRetentionReviewHandler`).
- **The exception is a feed:** a patient's timeline (`GET api/patients/{id}/timeline`) pages by cursor (keyset) rather than by page number, so entries added meanwhile don't shift the pages. It orders by `AtUtc` then `Id`, both descending; a page's `NextCursor` encodes its last entry's pair, and the next page starts after it (`PatientTimelineSearch`, `TimelineCursor`).
- `GET api/patients` and `GET api/auth/users` return everything. Only the deprecated Blazor client uses them; prefer the search endpoints.

### Mapping

Domain entities become `Contracts` responses through **hand-written static mappers**, one per area. Don't use a mapping library (no AutoMapper or Mapster).
- **Where they live:** in the area's `Common/` folder, named `<Thing>Mapper`. Each has `ToResponse(entity)`, plus overloads for what a response needs that the entity doesn't have, for example `ToResponse(definition, usage)` or `ToResponseAsync(...)` when it looks up usernames.
- **Mappers so far:**
  - `PatientMapper`, `UserSettingsMapper`, `SessionMapper`, `NotificationMapper` (with notification preferences), `AuditEntryMapper`, `AttachmentMapper`, `MonitoringRuleMapper` (with the names from `MonitoringRuleNames`), `EmailMapper`, `TwoFactorMapper`, `SecuritySettingsMapper`
  - `ProcedureMapper`, `ProcedureNoteMapper`, `NoteDeletionRequestMapper`, `StageDefinitionMapper`, `StageTemplateMapper`, `TimelineMapper`, `ProcedureInsightsMapper` (from totals, not entities)
  - `AppointmentMapper`, `CalendarMapper`, `CalendarSetupMapper` (activity types and day and week templates), `MeetingMapper` (meetings, and free times)
  - `FhirPatientMapper` (a patient as a UK Core Patient) and `DemographicsMapper`
  - `UserMapper`, in Infrastructure, because `ApplicationUser` is an Infrastructure type
- **Paged responses:** `PagedMapper.ToResponse(result, page, pageSize, Mapper.ToResponse)` (`Common/Paging`) turns a repository's `PagedResult` into the `PagedResponse` every search endpoint returns.
- **No inline mapping:** handlers and controllers don't build responses from entities themselves, and queries never return Domain entities to the API. Results that aren't entities (a login's session, a generated password, the signed-in user's claims) may be built where they're made.
- **Tests:** every mapper has its own (`<Thing>MapperTests`), including what it computes (`CanBeDeleted`, an action or kind by name, read or not).

### Data access

- Each repository method calls `SaveChangesAsync` itself, so there is no unit of work.
- Read methods use `AsNoTracking()`, and updates go through `context.X.Update(entity)`.
- **Procedures are the exception:** handlers load a tracked procedure with `GetForUpdateAsync`, change it through `ProcedureChange`, and `SaveAsync(change)` (`IPatientProcedureRepository.SaveAsync(ProcedureChange)`) saves the change, its audit entries, and any appointments it requested or cancelled with their history, in one `SaveChangesAsync`. That way EF works out which stages and assignments changed, and no change can miss the audit log.
- Pass `CancellationToken` all the way through. The tests check that it is passed on.
- IDs are `Guid`s generated in handlers (`Guid.NewGuid()`). Timestamps are UTC (`CreatedAt`, `LastUpdated`), set in handlers.
- **Times are stored and sent as UTC, with a `Z`.** SQL Server's `datetime2` keeps no time zone, so `UtcDateTimeConverter` (every `DateTime` and `DateTime?`, in `MedAppDbContext.ConfigureConventions`) marks what EF reads as UTC; without it the JSON has no `Z` and browsers read the time as their local time, an hour out in British Summer Time. The web app formats times in UK time (`formatDateTime` in `MedApp.Web/src/utils/dates.ts`), and reads one without a `Z` as UTC too. Due dates and dates of birth are dates, not times, and are never shifted. `dueDateUtc` is a moment, the end of the due day (UK time) in UTC, for comparing with now; show `dueDate`.
- Handlers and validators that need "now" take a `TimeProvider` (registered in `AddApplication`); tests pass a `FixedTimeProvider`.

### Procedures

The concept and decisions are in `docs/procedures-ui-plan.md`. In short: admins build **templates**, ordered lists of **stage definitions** in which a stage may repeat. Staff create a patient's **procedure** from a template, which copies its stages (name, description, instructions) onto the procedure. Stages are worked strictly in order: notes, then finish, which locks the stage until an admin unlocks it.
- **The rules live in `MedApp.Application/Procedures/Common`:** `ProcedureWorkflow` (statuses, which stage is current, what can be edited, overdue), and `ProcedureChange` (applies a change, moves the status automatically and writes the audit entries). Use them; don't set `Status` or stage flags in a handler by hand.
- **Every change to a procedure is audited** (`PatientProcedureAuditEntry`, no foreign keys so the history outlives deletes). New procedure commands must go through `ProcedureChange` so they're audited too.
- **Due dates are whole days,** due by the end of the day UK time and stored as that moment in UTC (`DueDates`). The API takes and returns `DueDate` as a date.
- **Definitions and templates in use are archived, not deleted;** deleting one that's in use is a 409. Patients with procedures or appointments can't be deleted (409).
- **A stage can involve a visit** (`VisitRequirement` on the definition, copied onto the stage), which ties it to appointments: see [Calendar and appointments](#calendar-and-appointments).
- **A procedure has several notes** (`PatientProcedureNote`, Markdown, 4,000 characters each), newest first on its page, each with its author, when it was written and when last edited. They're not details: `PATCH` refuses notes (a 400, `UpdatePatientProcedureValidator.NotesMovedMessage`, so a page loaded before the change is told rather than having its change dropped), and the Edit Procedure page has none. A new procedure's notes, if any, become its first note, by whoever creates it (`ProcedureCreation.Record`).
  - **Endpoints, for staff:** `POST .../patient-procedures/{id}/notes` `{text}` (201 with the note) and `PUT .../notes/{noteId}` `{text, expectedVersion}`. Notes come back inside the procedure's response (`NoteList`, each with `CanEdit` for the signed-in user, and the procedure's `CanAddNotes`), so reading them is the procedure's `ProcedureViewed`; there's no GET of their own, and the 201's `Location` is the procedure. **`Notes` stays a string** (deprecated: the first note's text, or the old column's), so pages loaded before the change don't fail on a list; never change an existing response field's type.
  - **When:** whenever the details can be edited (`ProcedureWorkflow.CanChangeNotes`), so also while Blocked or **Completed**, since a note after completion (a result, a follow-up call) is normal; not once it's Cancelled or Archived, when the record is closed (409). A restricted or anonymised record's are refused through `GetForUpdateOrThrowAsync` (409), as for every procedure change.
  - **Who:** staff add notes; **only a note's author edits it** (403 otherwise, admins included: what someone wrote in the clinical record stays theirs). **Only admins delete one** (below); staff ask an admin to. A note moved from the old single field with no known creator has no author ("Unknown"), and nobody can edit it.
  - **Versions:** every add and edit writes a `PatientProcedureNoteVersion` (text, who, when; no foreign keys, with the patient and procedure copied in, so versions outlive a deleted procedure). An edit names the version it started from (`expectedVersion`), so a stale one is a 409 (`ProcedureNotes.ChangedMeanwhileMessage`), and the note's row version catches two saves at once.
  - **Audit:** `NoteAdded = 13` and `NoteEdited = 14` go through `ProcedureChange.AddNote`/`EditNote`, so they're audited and move `LastUpdated` in the same save, and the monitor is told (no rule watches them). **Their details hold the note's ID and version, never its text** (DPIA risk 4): the text lives only in the versions.
  - **Deleting is soft, by admins, with a reason** (`POST .../notes/{noteId}/delete` `{reason, detail?, expectedVersion}`, admins, 204; `ProcedureChange.DeleteNote`). The reason is a fixed choice (`NoteDeletionReason`, by name: `WrongPatient = 0`, `WrittenInError = 1`, `Duplicate = 2`, `Other = 3`; stored as its number, so never renumber it; `NoteDeletionReasons` has the words), with an optional detail (500 characters, required for Other). The note gets `DeletedAtUtc`, `DeletedByUserId`, `DeletionReason` and `DeletionDetail` and is hidden from the procedure page for everyone (`ProcedureNoteMapper.ToResponses` leaves it out, and the deprecated `Notes` string skips it), but its row and versions stay, so the history, the admins' timeline and the patient's export still account for it. A deleted note can't be edited or deleted again (409, `ProcedureNotes.DeletedMessage`).
    - **The version the admin read:** deleting (directly or from a request) carries the note's `expectedVersion`; a note edited since is a 409 (`ProcedureNotes.EditedSinceOpenedMessage`), so nobody deletes words they haven't seen. Keeping a note needs none.
    - **The author is told** (`AuthorsNoteDeleted = 21`), unless they deleted it themselves, asked for it, or aren't known, so someone who knows what it said can add it to the right record.
    - **The old single notes field:** deleting a procedure's oldest note (the one #110's migration copied `PatientProcedures.Notes` into) also clears that column, which would otherwise keep the deleted text (the audit's `oldNotesFieldCleared`).
    - **When:** in any status of the procedure, Cancelled and Archived too: it's a correction (a note on the wrong patient), as an admin can delete a file at any time. Never while the record is restricted or anonymised (the usual guard's 409).
    - **Audit:** `NoteDeleted = 15`, with the note's ID and latest version, the reason by name (`deletionReason`), the detail and the request it approved (`requestId`, if any); **never the text**. The timeline gives the reason and detail to admins only, in words, and anonymising replaces the detail (`detail` is one of `PatientAnonymiser`'s free-text keys; the reason is a fixed choice and stays).
    - Each note in the response carries flags for the signed-in user, like attachments' `CanDelete`: `CanDelete` (an admin, while the record can change), `CanRequestDeletion` (anyone else, while the record can change and no request is waiting) and `DeletionRequestId` (the waiting request, shown as "Deletion requested"). `ProcedureActor.IsAdmin` (from the session's role) carries whether the viewer is an admin into the procedure's response.
  - **Staff ask an admin to delete a note** (`POST .../notes/{noteId}/deletion-requests` `{reason, detail?}`, staff, 201 with the note; `RequestNoteDeletionHandler`). Any note on a procedure they can see, in any status, not while the record is restricted or anonymised: the admin decides, so it widens nothing.
    - **The request** (`ProcedureNoteDeletionRequest`, `MedApp.Application/Procedures/NoteDeletionRequests`): the note, procedure and patient (no foreign keys, like the audit log, so it outlives a deleted procedure), who asked (by ID and the username at the time), the reason (a fixed choice) and its optional detail (free text) and when, its status and who decided when. `NoteDeletionRequestStatus` is stored by number, so never renumber it: `Pending = 0`, `Approved = 1` (the note was deleted), `Declined = 2` (kept), `Closed = 3` (closed without a decision).
    - **One waiting request per note:** the note's `PendingDeletionRequestId` points at it; asking again is a 409 that names who asked and when (`ProcedureNotes.AlreadyRequestedMessage`). Setting it changes the note's row, so its row version stops two requests at once, and the filtered unique index `IX_ProcedureNoteDeletionRequests_NoteId_Pending` is the last word (`NoteDeletionRequestRepository` turns either into the same 409).
    - **Saved together:** the request and its note share the DbContext (`INoteDeletionRequestRepository`), so making or deciding one saves the note's change in the same `SaveChangesAsync`, as appointments loaded with a procedure do.
    - **Every admin but the requester is told** (`NoteDeletionNotifications`, see [Notifications](#notifications)).
  - **An admin decides** (`GET api/procedures/note-deletion-requests/{id}` and `POST .../{id}/decision` `{deleteNote, expectedVersion?, reason?, detail?}`, admins). The GET gives the note's text, the patient (as `PatientBanner` shows them), the procedure's title, who asked, when and why, and the outcome once decided, with `CanDecide` and `WhyCantDecide`; it records `ProcedureViewed` (or `PatientViewed` once the procedure has been deleted). **Delete note** soft-deletes it as above, from the version the admin read (`expectedVersion`, required), with the admin's reason and detail or, left out, the requester's; **Keep note** declines it. Either way the request is closed and the requester told. A request already decided (by another admin) is a 409 naming who and how (`ProcedureNotes.AlreadyDecidedMessage`), and so is a decision on a restricted or anonymised record; the request's row version catches two admins at once.
    - **A direct delete approves a waiting request** for that note, by that admin, and tells its requester (and its author).
    - **Deleting a procedure closes its waiting requests** (`Closed`, by the admin; `DeletePatientProcedureHandler`, in the same save), since its notes go with it. Their requesters aren't told.
    - **Anonymising** replaces every request's detail and every note's deletion detail, and closes waiting requests (`Closed`), as the record can't change any more. **Done by an API copy from before this change** (a rollout or a rollback), it leaves them as they were: see the chart's README and `docs/todo.md`.
    - **Privacy:** the export lists deleted notes (with when, who and why) and every request (`ExportedNoteDeletionRequestResponse`); `PatientRecordRepository` loads them by patient. A note deleted as `WrongPatient` is flagged (`IsAboutAnotherPatient`) for the clinician checking the export: its text is most likely another person's. Hazard H-38 (a note deleted wrongly).
  - **The old `Notes` column** stays (`PatientProcedure.LegacyNotes`, read only for the deprecated string), so API copies from before keep working during a rollout (the chart's two-release rule, and its README's list of what old pods do); the migration `AddedProcedureNotes` copied each procedure's text into its first note, by its creator, or by nobody ("Unknown") when anyone else had edited it (`DetailsUpdated` entries with `changes.notes`), marked edited at the last edit. Anonymising still clears it. Dropping it is a to-do for a later release, after copying any text only it holds (`docs/todo.md`).
- Status numbers are stored, so never renumber `PatientProcedureStatus`, `PatientProcedureAuditAction` or `NoteDeletionRequestStatus`.

### Patient timeline

The patient page shows a **timeline**: everything that happened to the patient's procedures and appointments, in one feed, built from the procedure audit log and the appointment history (`AppointmentEvent`) (`MedApp.Application/Procedures/Timeline`).
- **Endpoints, for staff:** `GET api/patients/{id}/timeline` (a page of entries, newest first, with `Kinds` and `ProcedureIds` filters and a `Before` cursor) and `GET api/patients/{id}/timeline/overview` (the open and blocked procedures, soonest due first and overdue flagged, and the procedures to filter by). Both are 404 for an unknown patient.
- **Kinds** (`PatientTimelineKind`) group the audit actions for filtering: Created, Stages (started, finished, unlocked), Notes (stage notes saved, and procedure notes added, edited or deleted), Assignments, Blocks (to Blocked, or back from it: cancelling a blocked procedure is under Status), Status, DueDates (a details edit that includes the due date), Details, Deleted and Files (a file attached or deleted; downloads are never on the timeline). `PatientTimelineKinds` works them out the same way in memory and in SQL, reading markers in the entry's JSON details. They aren't stored, so they can be regrouped freely; a change to how `ProcedureAudit` writes details must keep its tests passing.
  - **Appointments** is a kind of its own, for every appointment history entry: requested, booked, rescheduled, attended, did not attend, cancelled and notes changed.
- **Two feeds, merged:** audit entries (file entries among them) and appointment history entries are read with the same filters and order, and merged into one page by time, so one cursor pages through both. An appointment entry's `ProcedureId` and `ProcedureTitle` are null when the appointment isn't for a procedure.
- **What each person sees is decided on the server** (`GetPatientTimelineQuery.IsAdmin`, from the caller's role), because the audit log itself is admin-only and keeps old values:
  - **Staff** see entries only for procedures that still exist. Each shows the kind, who, when and the procedure (a link), and structured values, old and new: due dates, priorities and statuses, the template, who was assigned and unassigned (past assignees too), and the username recorded at the time (a deleted account's too, where the procedure page says "Deleted user"). **Never** free text from the log: no notes text (stage or procedure), no old or new titles, no block or cancel reasons; for those they get only which field changed. A procedure note added, edited or deleted shows as that, with who and when (its change's field is `note`, with no values, and a deletion's reason left out).
  - **Files:** staff see that a file was attached or deleted, and where (the patient, a procedure, a stage), but **not its name**, which is free text; admins see the name. A file attached to the patient themselves has no procedure: its entry's procedure ID is `PatientProcedureAuditEntry.NoProcedure` (all zeros) and its title is empty, and staff see it like any other.
  - **Staff, for appointments,** see the structured values (status, time, member of staff, stage), and nothing about appointments of a deleted procedure. **Never** an appointment's notes (old or new) or a cancellation reason. A stage finished without a visit shows that, but not the admin's reason.
  - **Admins** see everything, including entries for deleted procedures (labelled as deleted, each with the title recorded in that entry), file names, appointment notes and cancellation reasons, the reason a stage was finished without a visit, a procedure note's text (and, for an edit, the text before; for a deletion, the text it had and the reason), read from the note versions (`GetPatientTimelineHandler`, `PatientTimelineRow.NoteText`), and the other free-text values.
  - Keep this when adding a field to `PatientTimelineEntryResponse`: free text from the audit details goes to admins only (`TimelineMapper`'s `PublicValueFields` is the allowlist for edited fields). `TimelineStaffCanaryTests` records every action with one string as all its free text (file names and note text too) and checks the whole staff response never holds it; add any new action or free-text field to it. It covers the appointment entries and a stage finished without a visit too.
  - The governance pack (`docs/governance/`) states this rule; change both together.
- An entry carries the procedure's title now, or, once it's deleted, the title recorded in that entry (so a procedure renamed before it was deleted shows under both titles).
- **Order:** newest first by `AtUtc`, then `Id`. The entries one change writes (a stage started, its notes saved, the status change that followed) are each a tick (100 ns) after the one before (`ProcedureChange.Audit`), so they sort in the order they happened; entries written before that share a time and fall back to ID order.

### Notifications

- A handler tells someone about something with `INotificationSender.SendAsync(new Notification { … })` (`MedApp.Application/Notifications/Common`), after its own change is saved. It stores the notification, then pushes it live to every page that user has open.
- **Live delivery is SignalR:** `NotificationsHub` at `/api/notifications/hub`, addressed by user ID (the session's `NameIdentifier`), through `SignalRNotificationPublisher` in the API. Pushing is best effort: a failure is logged, and the stored notification shows on the next load.
- **Several copies of the API share a backplane:** with `ConnectionStrings:SignalRBackplane` set, SignalR passes messages through that Redis-compatible server (`SignalRBackplane`), so a notification reaches a browser on any copy. In Kubernetes it's Valkey; in development it's unset, and there's one copy.
  - Browsers connect by WebSocket only, without negotiating first (`LiveNotifications`), because with several copies the negotiate request and the WebSocket could reach different ones.
- `GET api/notifications` returns the newest and the unread count. `POST api/notifications/read` marks them all read, and `POST api/notifications/{id}/read` marks one.
- **Kinds** (`NotificationKind`) are stored by number, so never renumber them. 0 is being assigned a procedure (not when you assign yourself); 1 to 3 are the appointment kinds, `AppointmentBooked = 1`, `AppointmentRescheduled = 2` and `AppointmentCancelled = 3` (see [Calendar and appointments](#calendar-and-appointments)), 4 to 6 the meeting kinds, `MeetingInvited = 4`, `MeetingChanged = 5` and `MeetingCancelled = 6`, and 7 to 9 are kept for more calendar kinds; the monitoring kinds are 10 to 17, one for each `MonitoringEvent`; 18 to 21 are about deleting notes (`Notification.IsNoteDeletion`). Notifications have no foreign keys, like the audit log; an appointment's carries its `AppointmentId`, a meeting's its day (`CalendarDate`), which links to the Calendar that day, and a note deletion request's its `NoteDeletionRequestId`.
  - **Note deletion kinds** (`NoteDeletionNotifications`): `NoteDeletionRequested = 18` goes to every admin but the requester ("Note deletion requested", "s.nurse asked to delete a note on a procedure."), with `ProcedureId` and `NoteDeletionRequestId`, and opens the request's dialog on the procedure page. `NoteDeletionApproved = 19` ("Note deleted") and `NoteDeletionDeclined = 20` ("Note kept") go to the requester, unless they decided it themselves, linking to the procedure. `AuthorsNoteDeleted = 21` ("Your note was deleted", "admin deleted a note you wrote on a procedure.") goes to the note's author, unless they deleted it themselves, asked for it (they get 19) or aren't known. Titles are fixed phrases and messages hold only usernames: never the note, the reason or the patient. `Notification.HasFixedTitle` covers them, so anonymising leaves them as they are.
- **Each person's choices** (`NotificationPreferences`, Account Settings' Notifications card, `GET`/`PUT api/notifications/preferences`): today only whether to be told of being assigned (the appointment kinds can't be switched off yet). `NotificationSender` checks them before storing an optional kind (`NotificationPreferences.IsOptional`); no row means everything. They're kept on the server, apart from the browser's app settings, because the server reads them.
- **Notification text never carries free text or the patient.** A new kind's title is a fixed phrase, and its message is built from usernames, enums, admin-written names (templates, stages, meeting titles) and dates. (The older assignment notification still uses the procedure's title: DPIA risk 3. Their messages say who did what and when, never the patient's name or the notes.)
  - **A meeting's title counts as an admin-written name:** only admins arrange and change meetings, and the dialog's Title field says not to put patient details in it, as Notes does. Its notifications quote it, and those copies outlive the meeting, out of reach of a patient's export and anonymisation (DPIA risk 25). A meeting's notes are never in a notification.

### Calendar and appointments

The concept and decisions are in `docs/calendar-plan.md`. In short: every member of staff has a **calendar**, on which staff **book appointments** with patients and **block off time** for activities (Lunch, Training, ...). **Day and week templates** fill each week with its usual blocks. A stage definition can say a stage **involves a visit**, and the app then asks for an appointment before the stage is finished.
- **The rules live in two `Common` folders.** Use them; don't set an appointment's `Status`, or work out UK times, slots or clashes, in a handler by hand.
  - `MedApp.Application/Calendar/Common`: `WorkingHours` (the working day, the slot length, and `WhyOutside(startUtc, endUtc)` for validators), `UkTime` (UK dates and clock times to and from UTC, and "Monday 23 November at 10:00" for messages), `TemplateHistory` (replacing a set of dated rows from today), `CalendarProjection` (a person's days, with their template blocks and exceptions, from the rows the repository loads, `CalendarData`), `CalendarClashes` (what a time would overlap), `CalendarMapper` and `CalendarSetupMapper`.
  - `MedApp.Application/Appointments/Common`: `AppointmentWorkflow` (statuses, and what's allowed from each), `AppointmentChange` (applies a change and writes its history) and `AppointmentMapper`.
- **The working day** is 08:00 to 18:00 UK time (Europe/London), Monday to Friday, shown in 15-minute rows, or 5-minute ones by choice (the Calendar page's Rows menu, with **15 minutes** and **5 minutes**: `rows=5` in its URL, and each person's last choice kept as their default). Weekends are shown greyed, and nothing can be booked or blocked on them. An appointment or block must start and end on the same weekday, inside the working day, on a 5-minute boundary, and start before it ends; anything else is a 400. Bank holidays aren't known yet.
- **Times are UTC, with a `Z`,** like every other time ([Data access](#data-access)). Template times are UK clock times (`TimeOnly`), turned into UTC for each date by `UkTime`, so a 12:00 lunch is at 12:00 UK time on both sides of a clock change. The calendar response gives each day's `workStartUtc` and `workEndUtc`, so the browser steps through slots in UTC and never does time zone arithmetic. A UK working day never spans a clock change.
- **Activity types** (`CalendarActivityType`) are the admin-managed list of what time can be blocked for. Each has a name and a colour from a fixed palette of Astryx `Token` colours (`red`, `orange`, `yellow`, `green`, `teal`, `cyan`, `blue`, `purple`, `pink`, `gray`), so contrast comes from the theme. Seeded: Lunch, Admin time, Training, Meeting, Annual leave and Travel. Once a block or template block uses one, it's archived, not deleted; an archived one can't be chosen for new blocks, but existing blocks keep it.
- **Blocks** (`CalendarBlock`): a member of staff, an activity type, a start and end, and an optional note (200 characters). Blocks are about staff, never patients: a block's note must not hold patient details, and the UI says so.
- **No overlaps.** A new or moved appointment, block or meeting may not overlap an appointment (Booked, Attended or Did not attend), a block (stored or from a template) or a meeting on that person's calendar. The server refuses it with a 409 that names the clash ("That time overlaps Lunch, 12:00 to 13:00.", or for a meeting, who and what: "k.ashford has Lunch, 12:00 to 13:00."), and the UI only offers free slots. `CalendarClashes.BusyTimes` is that busy time, and `Availability` (free time several people share, and suggested meeting times) uses it, so a suggestion is always a time the server accepts.
  - **Two requests racing for one slot** are serialised by a database lock per member of staff (`ICalendarLock`, SQL Server's `sp_getapplock`), so one wins and the other gets the 409. Any command that adds or moves something on a calendar takes the lock before it checks for clashes.
  - **The lock protects a person's calendar, not an appointment:** two requests booking one appointment with different people take different locks. So the appointment itself is protected too, below.
  - **A later template change can overlap what's already there** (an admin moves everyone's lunch over a booked appointment). Both still show, the appointment on top, and the block is flagged as overlapping. The app never moves or removes either.
- **Templates are applied when a calendar is read, never generated.** `CalendarProjection` works out each day's template blocks when it's shown, so editing a template changes every day it applies to from then on. Nothing runs in the background.
  - **A day template** (`DayTemplate`) is named, with blocks (`DayTemplateBlock`: activity type, start and end time, optional note). **A week template** (`WeekTemplate`) gives a day template, or none, for each weekday (`WeekTemplateDay`). Each member of staff may have a **default week** (`StaffWeekTemplate`), set by themselves or an admin.
  - **Templates are personal** (`OwnerUserId`): a person's week templates, day overrides and default week use only their own templates (404 for someone else's), and names are unique per owner. Their owner or an admin changes them (`CalendarGuards.EnsureCanChangeTemplatesOf`, 403 otherwise); anyone reads them. The page is each person's own, `/calendar/templates`.
  - **History is kept by dating rows, not by copying them.** A day template's blocks, a week template's days and a person's default week each have `ValidFrom` and `ValidTo` (UK dates). An edit closes the rows that changed on the day before today and adds new ones from today; unchanged rows are kept; a row added today and changed again today is replaced. `TemplateHistory` does this, with its own tests. So a past day shows what applied then, and a change shows from today, including today's blocks that have already passed.
  - **Changing one day's template block** stores an exception for that date (`CalendarBlockException`), so the template block isn't shown that day, plus, for an edit, a stored block with the new values. A later edit to the template keeps exceptions on the blocks it didn't change.
  - **Apply Template** (the Calendar page's button, on any working days of the week shown) stores a day override (`CalendarDayOverride`) for each day: that date uses the chosen day template, or none, instead of the week's. Choosing "The default week's" removes it, going back to the week's (the dialog asks for every ticked day, and takes the API's 404 for a day with nothing of its own as done). Blocks added by hand that day stay.
  - **Past days don't change:** blocks, exceptions and overrides on a day before today (UK) can't be added, edited or removed (409). Appointments in the past can still have their outcome recorded.
  - **Templates in use are archived, not deleted,** like stage definitions: a day template once any week template or day override has referred to it, a week template once anyone has had it as their default. An archived one can't be chosen again, but keeps applying where it already does.
- **Who changes what:**
  - **Any staff member** can see anyone's calendar, and book, reschedule, cancel and record the outcome of any appointment, for any member of staff (as they can work on any procedure).
  - **A calendar's blocks, a day's template and its owner's default week:** the owner, or an admin.
  - **A person's day and week templates:** the owner, or an admin. Staff can read anyone's.
  - **Activity types:** admins. Staff can read them.
  - **Meetings:** admins arrange, change and cancel them; everyone sees them. The team view and suggested times are admins' too.
- **A meeting** (`Meeting`, `MeetingAttendee`) is something an admin arranges for several members of staff: a title, notes about staff (never patients), a time inside one working day, not on a past day, and at least one attendee. It's busy time on each attendee's calendar. Adding or changing one holds every attendee's calendar lock (and, on a change, those of everyone going before), and has a row version. A change carries the `lastUpdated` the caller saw (`expectedLastUpdated`, required): a 409 if anyone has changed the meeting since, so a stale dialog or drag can't undo another admin's change; the web app sends it from both. Only attendees a change newly adds must be staff: anyone already going whose account has gone is dropped on save, untold. Attendees are told (`MeetingNotifications`), never of their own change. Cancelling deletes it. An account that's deleted, or loses every staff role, is taken off its meetings still to come (`IMeetingRepository.RemoveAttendeeFromUpcomingAsync`), and a meeting left with nobody goes.
- **An appointment** (`Appointment`) is for a patient, and optionally for one of their procedures and one of its stages. It has a member of staff, a start and an end (UTC), a status, optional notes (2,000 characters of free text about the patient, treated like procedure notes), who requested or booked it and when, and who recorded the outcome and when.
  - **Statuses** (`AppointmentStatus`): `Requested = 0` (shown as "Requires appointment": no member of staff or time yet; they're listed on the **Requires Appointment** page, `/calendar/requires-appointment`, which has no side nav item and is reached from the Calendar page's "Requires Appointment (N)" link), `Booked = 1`, `Attended = 2`, `DidNotAttend = 3` and `Cancelled = 4`.
  - **Changes** (`AppointmentWorkflow`): Requested to Booked, and Booked to Booked (rescheduling, to another time or member of staff), only in the future and clash-free. Booked to Attended or Did not attend only once its start has passed; those two can be corrected either way. Requested or Booked to Cancelled, with a reason (500 characters). Cancelled is final: a patient who didn't attend gets a new appointment. Booking in the past isn't possible, so a walk-in can't be recorded after the event.
  - **One open appointment per stage:** a stage can have one Requested or Booked appointment at a time. Asking for another is a 409 that points to the one there is (when and with whom it's booked, or that it's in Requires Appointment: `AppointmentWorkflow.StageHasOpenVisit`). Appointments without a stage have no limit. `CreateAppointmentHandler` checks it, and a filtered unique index enforces it (`IX_Appointments_StageId_Open`, on `StageId` where the status is Requested or Booked), so two requests at once can't both add one: the repository turns the index's refusal into `StageHasOpenAppointmentException`, and the handler into the same 409. A procedure change whose automatic visit loses that race is a 409 to try again (`PatientProcedureRepository`).
  - **Two people changing one appointment at once:** appointments have a row version (`Appointment.RowVersion`), so of two saves from the same copy the later is refused with a 409 (`AppointmentWorkflow.ChangedMeanwhileMessage`, or `ProcedureAppointmentChangedMeanwhileMessage` when a procedure change touched it) instead of silently overwriting the earlier. Every appointment save goes through `SaveChangesOrConflictAsync` with that message.
  - **Booking says what it expects:** `POST api/appointments/{id}/book` takes `expectedStatus`, the status the caller saw: `Requested` to book it, `Booked` to move it. If the appointment isn't in that status any more, it's a 409 (`BookedMeanwhileMessage` when someone else booked it first), so a stale "book" can't quietly move someone else's booking. The web app sends the status from its copy (the booking dialog, and a drag on the calendar).
  - **Every change is recorded** in the appointment's history (`AppointmentEvent`, its action an `AppointmentEventAction`): requested, booked, rescheduled (with the old time and member of staff), attended, did not attend, cancelled (with the reason) and notes changed (old and new text). Like the procedure audit log, it has no foreign keys, so it outlives what it's about. New appointment commands must go through `AppointmentChange`, so they're recorded too.
  - Status, action and requirement numbers are stored, so never renumber `AppointmentStatus`, `AppointmentEventAction` or `VisitRequirement`.
- **Stage visits:**
  - **Stage definitions have a `VisitRequirement`:** `None = 0` (the default), `Suggested = 1` or `Required = 2`, set by admins. It's copied onto each procedure stage when the procedure is created, like the name and instructions. Existing definitions and stages are `None`, so they behave exactly as before.
  - **The Requested appointment:** when a stage with a visit becomes the current stage (the procedure is created, or the stage before it is finished), `ProcedureChange.RequestVisit` creates a Requested appointment linked to it, unless it already has one that's Requested, Booked or Attended (one booked ahead counts). Its history records it as requested by the app. None is made while the procedure is blocked or closed.
  - **Required:** finishing the stage needs an Attended appointment linked to it, checked on the server (`ProcedureWorkflow.WhyStageNeedsVisit`). Staff are refused with a 409 that says to book it and mark it Attended, and that an admin can finish it without one.
  - **The admin bypass:** an admin may finish a Required stage without a visit, after a confirmation dialog that asks for a reason (`FinishProcedureStageRequest { withoutVisit: true, reason }`). The stage's `StageFinished` audit entry records `withoutVisit`, the requirement and the reason. With no body, the finish endpoint works as before.
  - **Suggested:** finishing without an Attended appointment asks anyone to confirm, in the UI only. The server doesn't refuse, and the `StageFinished` entry records `withoutVisit` and the requirement.
  - Finishing a stage again after an admin unlocked it doesn't ask for a visit again.
  - **Tidying up:** finishing a stage cancels its Requested appointments, and cancelling a procedure cancels all its Requested ones (`ProcedureChange.CancelRequestedVisit`), each with a reason saying why. The app never cancels a Booked appointment: someone may need to tell the patient, so the procedure page lists them.
  - The appointments and history these make are saved with the procedure change, in one `SaveChangesAsync` ([Data access](#data-access)).
- **Notifications** go to the member of staff, only when someone else made the change: `AppointmentBooked` (an appointment was booked with you, or moved to you), `AppointmentRescheduled` (yours was moved to another time) and `AppointmentCancelled` (yours was cancelled, or moved to someone else). The title is a fixed phrase ("Appointment booked", "Appointment moved", "Appointment cancelled"); the message says who and when, never the patient's name or the notes. `Notification.AppointmentId` opens the appointment on the Calendar page.
- **Deleting:**
  - A patient who has appointments can't be deleted (409), as with procedures.
  - Deleting a procedure (only once it's cancelled or archived) detaches its appointments (procedure and stage set to none) in the same save; their history keeps the procedure.
  - A user account with upcoming Booked appointments can't be deleted until they're moved or cancelled, so no appointment is left with nobody. Nor can it lose every staff role (`SetUserRolesHandler`), since its calendar would go with them. Both ask `WhyCantStopBeingStaffAsync` (`AppointmentRepositoryExtensions`) and refuse with the same `HasUpcomingAppointments` error.
- **Privacy** ([Activity log and patient privacy](#activity-log-and-patient-privacy)):
  - **Restriction:** every change to an appointment loads it through `GetForUpdateOrThrowAsync` (`AppointmentRepositoryExtensions`), which applies `PatientRules.EnsureCanChange` (a 409 for a restricted or anonymised patient), and adding one checks the patient the same way. Cancelling loads it through `GetForCancelOrThrowAsync`, which allows a restricted patient's (`PatientRules.EnsureCanPause`), so care can be paused safely as their procedures can; an anonymised patient's still can't be cancelled.
  - **Reads are logged** like other reads of patient data: opening an appointment records `PatientViewed`, and the calendar and appointment search (Requires Appointment, a patient's or procedure's appointments, the booking dialog's lists) record `PatientListed` for the patients they show. Apply Template reads a week's days without the appointments (`GET api/calendar?withoutAppointments=true`), which names no patients and records nothing. Classify a new GET endpoint in `EndpointCoverageTests`.
  - **The export and anonymisation cover appointments:** `PatientRecordRepository` loads a patient's appointments, their history and the notifications about them. `PatientAnonymiser` replaces appointments' notes and cancellation reasons, and the history's notes, reasons and procedure titles, with placeholders. Notifications about appointments are left as they are: their titles are fixed phrases (`Notification.HasFixedTitle`; see [Monitoring](#monitoring)).
  - **Not monitored:** appointments aren't `MonitoringEvent`s, and neither is the admin bypass yet (`docs/todo.md`).
- **Endpoints** are under `api/calendar` and `api/appointments` (the plan's section 4). The stage finish endpoint takes the optional `{ withoutVisit, reason }`.

### Notepad

Each member of staff has one notepad (`Notepad`, keyed by their account's ID): Markdown jottings beside every page of the web app, for a call or a clinic (`MedApp.Application/Notepads`).
- **Endpoints:** `GET api/me/notepad` and `PUT api/me/notepad` `{text, expectedVersion}`, open to anyone signed in (`[Authorize]`, no role), always the caller's own. The response carries `version` (0 for none) and `keepDays`. A save from a version other than the stored one is a 409 (`NotepadRules.ChangedMeanwhileMessage`: another tab saved first); the row version catches two saves at once, and two first saves at once hit the key (also a 409).
- **Kept on the server, never in the browser,** because it may hold patient details. The web app keeps only whether it's open (`medapp.notepadOpen`).
- **Retention:** cleared (the row deleted) once the whole notepad has gone `Notepad:KeepDays` (30, at least 1: checked at startup) without any change, when it's next read or saved, so a notepad in use is never cleared (ageing its text is a to-do); a save that finds it expired is a 409 saying so (`NotepadRules.ClearedMessage`), so the page's old text isn't saved again. No scheduled job yet (`docs/todo.md`). Deleted with the account (a foreign key's cascade).
- **Not in the activity log:** it's the user's own and not linked to a patient (`EndpointCoverageTests` says so). For the same reason a patient's export and anonymisation can't find what it says: the DPIA accepts that (risk 26), with the 30 days and **Add note to procedure** as the controls.
- **Add note to procedure** (web only) adds its text, or the part selected (as Markdown, from the editor's own selection), as a note on an open procedure through `POST .../notes`, after a confirmation that shows the patient as the banner does (hazard H-37). "Remove it from the notepad" takes out exactly that range, by its position, never by searching for its words; when it can't, it says so.

### Monitoring

Admins' rules for being told what staff do to procedures (`/admin/monitoring`, `api/monitoring/rules`, admin-only): for example "Notify me when **sam** finishes **Bloods** on a **High or Urgent** priority procedure".
- **A rule** (`MonitoringRule`) belongs to one admin, who alone sees and changes it (another admin's is a 404). It names a person or anyone, an event (`MonitoringEvent`, stored by number: procedure created, stage finished, procedure completed, blocked or cancelled, someone assigned, a stage unlocked, a due date changed), and optional conditions: a minimum priority, a template, and for the two stage events a stage definition. It can be switched off. At most 50 each (`MonitoringRuleInput.MaxRulesPerAdmin`; a count, then an insert, so two adds at once at 49 can make 51, which is accepted). No foreign keys: a rule naming something deleted stays, shows it as deleted, and matches nothing.
  - **Switching** has its own endpoint, `PUT api/monitoring/rules/{id}/enabled`, which changes nothing else, so a rule naming something since deleted can always be switched. An edit (`PUT .../{id}`) checks only the person, template and stage it newly names (`MonitoringRuleInput.CheckAsync`): what the rule already names may be deleted and stay.
- **The person** is who did it, except for ProcedureAssigned, where it's the one assigned (only admins assign, so that's how to follow someone's new work). **For StageUnlocked the person must be an admin** (a 400 otherwise), as only admins unlock; the page lists only admins for it.
- **How it fires:** every procedure command calls `IProcedureMonitor.NotifyAsync(change)` after saving its `ProcedureChange` (a unit test checks every handler takes it). `ProcedureMonitor` reads what the change did from its audit entries (`MonitoredActivity`: automatic status changes, notes and starts are ignored), loads the switched-on rules for those events (one query when the change did something a rule can watch, none otherwise), matches them (`MonitoringRuleMatcher`: the template after the change; the higher of the priority before and after, so lowering an Urgent procedure to Low in the same edit as moving its due date still counts as Urgent), leaves out the admin who made the change and, for an assignment, the person assigned (they get the assignment notification), skips (doesn't delete) the rules of an owner who is no longer an admin (one more query, `GetAdminsAsync`, only when a rule matched), and sends each remaining admin one notification per change however many of their rules match (`MonitoringNotifications`: one insert and one push each, in turn).
- **Best effort, after the save:** not in the change's transaction (no outbox). A failure is logged and the change stands; only the request's own cancellation is rethrown. A failed insert is detached from the request's DbContext (`NotificationRepository.AddAsync`), so a later save in the same request doesn't try it again. The assignment handler tells the assignee before the monitor runs. Clinical follow-up must never rely on monitoring (hazard H-29).
- **A patient's export leaves monitoring notifications out** (`Notification.IsMonitoring`, applied in `PatientExportMapper`): they're about the staff, not the patient. Anonymisation still finds them, and leaves them as they are (below).
- **Tests:** `ProcedureCommandsMonitoringTests` runs every procedure command and checks each calls the monitor after its save, with the request's token; `MonitoringNotificationsTests` checks every event's message; the privacy canary checks one end to end.
- **Anonymisation leaves monitoring and appointment notifications as they are** (`Notification.HasFixedTitle`): their titles are fixed phrases and their messages hold no free text or patient details, so there's nothing to replace. A new monitoring or appointment message must stay that way (the canary in `PatientPrivacyTests` checks it).
- **A new event:** add it to `MonitoringEvent` (a new number), `MonitoredActivity`, `MonitoringNotifications` (a `NotificationKind` of its own, inside `Notification.IsMonitoring`'s range), and the web app's `MONITORING_EVENTS` and `ruleText`; and the governance documents that list the events (`dpia.md` risk 24, the staff privacy notice, hazard H-29).
- **`medapp-dev`'s `reset_demo_data`** deletes every rule, notification choice and notification with the rest.

### Attachments

Staff attach files (scans, photos, results, letters) to a **patient**, a **procedure** or a **stage** (`MedApp.Application/Attachments`, `api/attachments`). The bytes are in blob storage behind `IFileStore`; the metadata (`Attachment`: name, sniffed type, size, SHA-256, scan state, who, when, and the patient, procedure or stage) is in SQL.
- **Endpoints, all for staff:** `GET api/attachments?patientId=` (everything attached to the patient, anywhere), `?procedureId=` (the procedure's own, not its stages') or `?stageId=`, exactly one, newest first, at most 200 (`AttachmentLimits.MaxListed`; `TotalCount` says how many in all); `POST api/attachments?…` (upload); `GET api/attachments/{id}/content` (download); `GET api/attachments/{id}/thumbnail`; `DELETE api/attachments/{id}`.
- **Uploading:** the body is the file's raw bytes as `application/octet-stream` (any other request type is a 415, so another site can't send one without CORS, which nothing allows), with its name percent-encoded in `X-File-Name` (headers must be ASCII). Not multipart. At most 20 MB: `[RequestSizeLimit]` on that action only, and the handler counts the bytes too (Kestrel's own limit is untouched).
  - The handler streams the body into a temporary file (`IUploadStaging`: `/tmp`, readable only by the API's user) while hashing it, so it's never all in memory. On Linux its name is deleted as soon as it's opened (the handle keeps the bytes), so a killed process leaves nothing; on Windows it's deleted on close, and `StaleUploadSweeper` clears leftovers at start-up.
  - **What it's attached to is checked twice:** before the body is read, and again after (`CheckTargetAsync`), since a 20 MB upload can take a minute in which the record may be restricted, anonymised or deleted, or the stage finished. Closing the window fully would need the save to re-read the patient's flags in its transaction. Then, in order: its type from its contents (`FileTypeSniffer`), the malware scan, the blob, the thumbnail, then the record and its audit entry in one save. If anything after storing the blob fails, the blob is deleted again.
  - **Types are found from the contents, never the name or the browser's type** (`FileTypeSniffer`, `AttachmentFileTypes`): PDF, PNG, JPEG, HEIC/HEIF, Word `.docx` (a ZIP with Word's parts, read from its central directory without unpacking it; macros refused) and UTF-8 text. **SVG and HTML are refused by name**, and so is any text starting with markup. The name's extension must match the type found. A new type needs its signature there, its tests, and a check that browsers can't run it.
  - **Active content in the allowed types is refused where it's easy to see:** a `.docx` with an external relationship (`TargetMode="External"`: a remote template, a linked object), embedded objects (`word/embeddings/`) or ActiveX (`word/activeX/`); a PDF naming `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile` or `/RichMedia` anywhere in its bytes. The rest (names hidden in a PDF's compressed object streams, say) is left to the malware scanner.
  - File names are cleaned before they're kept (`AttachmentFileName.Clean`: no folders, control characters or Unicode direction controls, at most 255 characters).
- **Serving: files only ever leave through the API,** never as a link to storage, and never inline on the app's origin. `AttachmentResponseHeaders` sends each with `Content-Disposition: attachment` (an ASCII `filename` and an RFC 5987 `filename*`), the sniffed type, `nosniff`, `Cache-Control: no-store`, `Content-Security-Policy: sandbox; default-src 'none'` (replacing the `/api` policy) and `Cross-Origin-Resource-Policy: same-origin`. The web app shows only thumbnails in pages, and offers everything else as a download.
- **Thumbnails** are made at upload for PNG and JPEG (`SkiaThumbnailGenerator`, SkiaSharp, MIT licence; ImageSharp's licence has commercial terms): turned upright from EXIF, at most 320 px, re-encoded, so they carry none of the original's metadata. **A small file can claim a huge image,** and decoding it scaled down doesn't bound the memory (a progressive JPEG holds its full-size coefficients; a PNG decodes at full size). So the header is read first, and an image whose **own** size is over 24 million pixels, or either side over 10,000 px, gets no thumbnail (the file is still attached, without a preview); so does one it can't read. HEIC gets none (the Linux build can't read it). Thumbnail views aren't audited.
- **Expensive work is limited:** at most two uploads at a time in each API copy work out a type or make a thumbnail (`FileWorkLimiter`), since both grow with a hostile file. A Word document's ZIP listing more than 5,000 entries (`FileTypeSniffer.MaxZipEntries`, read from its end record) is refused before it's opened; real ones have tens. A test makes a 1 MB progressive JPEG claiming 24,000 by 24,000 pixels (over 1 GB to decode) and checks it's skipped at once.
- **Malware scanning:** `IMalwareScanner`, today `NoMalwareScanner`, which scans nothing and marks every file `NotScanned`; the web app shows that on each file. An `Infected` result refuses the upload. A real scanner is a to-do (`docs/todo.md`).
- **Who may do what:** staff list, upload and download any patient's files. Files can be added to a patient always, to a procedure unless it's cancelled or archived, and to a stage only while its notes could be edited (`AttachmentTarget.WhyFilesCantChange`; otherwise a 409). Staff delete their own files, under the same rule; admins delete any file at any time (to remove one attached to the wrong patient from a finished stage, say). `CanDelete` in each response says whether the caller may.
- **Deleting is soft:** the record is hidden from staff (`DeletedAtUtc`) and audited; admins can still list it (`includeDeleted=true`), but nobody can download it. The bytes stay until a purge job deletes them after a retention window, which doesn't exist yet (`docs/todo.md`). A patient or procedure with live files can't be deleted (409): attachments have no foreign keys (like the audit log), so their records outlive what they were attached to.
- **Audit:** adding, deleting and downloading a file are entries in the procedure audit log (`AttachmentAudit`; actions `AttachmentAdded`, `AttachmentDeleted` and `AttachmentDownloaded`, whose numbers are stored, so never renumber them), with the file's ID, name, type, size and what it's attached to. They don't go through `ProcedureChange` (a file isn't a change to the procedure), so a procedure's `LastUpdated` doesn't move. Added and deleted files are on the patient timeline (see [Patient timeline](#patient-timeline)).
- **Storage** (`AddAttachmentStorage` in Infrastructure): `ConnectionStrings:Attachments` is an Azure Storage connection string, and `Attachments:Container` the container (default `attachments`, created on first use). In development the AppHost runs Azurite (persistent, volume `medapp-azurite-data`) and passes it in; on kind it's Azurite in the chart; in Azure, a storage account behind a private endpoint, with its connection string in Key Vault. **Without a connection string the API still runs:** uploads and downloads are a 503 (`FileStorageUnavailableException`), and lists still work. CI's `e2e` job runs that way, and so does a Kubernetes deployment whose attachments Secret is missing (the API's reference to it is optional). **A store that fails** is a 503 too (`StorageUnavailableException`, from `BlobFileStore.Guard`), after the client's own retries (`AttachmentStorageOptions.ClientOptions`: 2 retries, 30 seconds a try); a failed upload's clean-up gets 10 seconds.
- **Privacy** (see [Activity log and patient privacy](#activity-log-and-patient-privacy)): file names are free text and the files are special category data. The governance pack lists them (`docs/governance/data-inventory.md`, `dpia.md`); a change to what's kept, who sees it or how long must update it.
  - **A restricted or anonymised record's files can't change:** uploading or deleting one (on the patient, their procedures or stages) is the guard's 409 (`PatientRules.EnsureCanChange` on `AttachmentTarget.Owner`), for admins too. Listing and downloading still work.
  - **Reads are in the activity log:** listing a patient's, procedure's or stage's files records `AttachmentsViewed`, and a download `AttachmentDownloaded`, against the patient (and procedure), deduplicated like other views; the procedure audit log has every download too. Thumbnails record nothing (they come with a list, which does).
  - **The subject access export** lists every file's details (deleted ones too: name, type, size, SHA-256, scan state, what it's attached to, who uploaded and deleted it), not the files themselves (`docs/todo.md`).
  - **Anonymising** renames every file to `Anonymised file` plus its type's extension, removes file names from the audit's details (`fileName` is one of `PatientAnonymiser`'s free-text keys), and deletes every live file, by the admin anonymising, with an `AttachmentDeleted` audit entry each (saved with the record), so its bytes go with the purge of deleted files.
  - **Retention:** downloading is a read, so it doesn't move a record's conclusion of treatment (`RetentionSchedule.ReadOnlyAuditActions`, left out of the retention review's query); attaching and deleting are changes and do.

### Activity log and patient privacy

Roadmap step 7. What it records and why is in `docs/governance/` (the data inventory, the DPIA and the rights procedure).
- **The activity log** (`ActivityEntry`, written through `IActivityLog` in `MedApp.Application/Activity/Common`) is separate from the procedure audit. It records who read or changed patient data, sign-ins (and refused ones, with the account's ID when the username exists, and the two-factor step: see Auth), sign-outs, account and role changes, and the security events of email, password reset and two-factor (`ISecurityEventLog`), with the address the request came from.
  - **Reads:** a handler that returns a patient's data calls `RecordViewsAsync`. `PatientViewed` for the patient's page, for their timeline and its overview, and for a FHIR read; `PatientListed` for each patient in a list's results (patient search, procedure search, retention review, a FHIR search); `ProcedureViewed` for a procedure's page, and for a note deletion request's dialog (`PatientViewed` once its procedure is deleted). A repeat of the same view by the same person within `Activity:ViewWindowMinutes` (5) adds nothing, so the log stays a readable size.
  - **What records nothing, on purpose:** the side nav's pin labels (`GET api/patients/labels`, `GET api/procedures/patient-procedures/labels`: names and titles of records the user already chose, at most 20); the admin-only logs themselves (procedure audit, activity log); insights (counts only); a user's own notifications; a calendar read without its appointments (`withoutAppointments`, Apply Template's days). The deprecated `GET api/patients` records one `PatientsSearched` entry ("all"), not one per patient, so it appears in no patient's access report.
  - **Files:** listing files records `AttachmentsViewed`, and downloading one `AttachmentDownloaded` (see [Attachments](#attachments)).
  - **`EndpointCoverageTests`** (integration tests) lists every GET endpoint with what it records, and fails on any it doesn't know: classify a new one there.
  - **Lookups outside MedApp:** a demographics (PDS) lookup records `DemographicsLookedUp`, with whether anyone was found, never the NHS number.
  - **Changes to a patient:** build the entry with `activityLog.Entry(...)` and pass it to the repository method (`AddAsync`, `UpdateAsync`, `DeleteAsync`, `IPatientRecordRepository.SaveAsync`), which saves both in one `SaveChangesAsync`, so no change can miss the log.
  - **Details never hold a patient's details or clinical text:** the names of the fields changed, never their values; the names of the search filters used, never the terms (an NHS number is a term like any other: `nhsNumber`, never the number). Reasons an admin types for a restriction, dispute or keep are the only free text, and anonymising replaces them; anonymising's own reason is a fixed choice, with an optional note that must hold no patient details.
  - **Who:** the actor (user and address) comes from `IActivityContext` (`HttpActivityContext` in the API, `DevToolActivityContext` in `medapp-dev`), not from the command. Procedure commands still take a `ProcedureActor`.
  - **It fails closed:** a read or sign-in whose entry can't be written fails (500), rather than going unrecorded.
  - Action numbers are stored, so never renumber `ActivityAction`. The log has no foreign keys, like the audit log.
  - `GET api/activity/search` (admins) searches it; a patient's page shows its latest entries about them as the access report.
- **Restricted and disputed records** (Articles 18 and 16): admins set them with a reason (`PUT api/patients/{id}/restriction` and `.../dispute`).
  - A restricted or anonymised record can't be changed, nor can its procedures, appointments or files: `PatientRules.EnsureCanChange` (409), which `GetForUpdateOrThrowAsync` applies to every procedure change, its namesake in `AppointmentRepositoryExtensions` to every appointment change ([Calendar and appointments](#calendar-and-appointments)), and the attachment handlers to every upload and delete ([Attachments](#attachments)).
  - **So that care can be paused safely,** a restricted record's procedures can still be blocked or cancelled with a reason, and its appointments cancelled (`GetForCancelOrThrowAsync`): `ChangePatientProcedureStatusHandler` loads them through `GetForPauseOrThrowAsync` for those two statuses (`PatientRules.PausesWhileRestricted`). Restricting a record with procedures under way or open appointments needs `ConfirmOpenProcedures` (a 400 without it); the dialog shows how many of each, and shows the API's message if it still asks. Hazard H-22.
  - `GetForUpdateAsync` is called only by those two guards; a convention test checks it, and that every procedure command uses one.
  - A procedure's response says why it's read-only in `ReadOnlyReason` (with every `Can...` flag false, and only Blocked and Cancelled allowed while restricted), and carries the patient's flags (`PatientFlags`) for the banners on the procedure, edit and patient-procedures pages. Disputed is a banner only.
- **Patients have a row version** (`Patient.RowVersion`, a concurrency token): a save made from a copy read before someone else's save is refused with a 409 (`SaveChangesOrConflictAsync`, `PatientRules.ChangedMeanwhileMessage`) instead of writing old values back, so a stale edit can't undo a restriction or an anonymisation. Appointments have one too ([Calendar and appointments](#calendar-and-appointments)); `SaveChangesOrConflictAsync` takes the message to give.
- **Everything about a patient** is loaded by `IPatientRecordRepository` (`PatientRecordRepository`) for the subject access export (`GET api/patients/{id}/export`, admins, `no-store`, itself logged) and for anonymisation. **A new table that holds patient data must be added there,** so both cover it. The export has its own types (`Exported…Response`): staff appear by username only, never with their account IDs, network addresses or notification read times, and the JSON holds exactly what the printable page shows.
- **Anonymisation** (`POST api/patients/{id}/anonymise`, admins, `PatientAnonymiser`) replaces the identifying details and free text with placeholders in place, across every table, and keeps the IDs and structure. **The result is pseudonymised, not anonymous:** the patient ID, the year of birth, dates, templates and who did what remain, so it's still personal data. It needs the patient's full name typed as confirmation and a reason from `AnonymisationReason` (with an optional note), and it's refused while a procedure is under way, an appointment is open (Requested or Booked: cancel it, or record its outcome, first), or the record is restricted. Restricting a patient whose procedures are under way or whose appointments are open asks for confirmation, counting both. Deleting a patient is unchanged.
- **Retention** (`RetentionOptions`, the `Retention` section of `appsettings.json`; `RetentionSchedule`): `GET api/patients/retention-review` lists the records past their minimum period; an admin reviews, keeps (`POST api/patients/{id}/retention/keep`, with a reason and a review date up to two years ahead) or anonymises. **Nothing is ever deleted automatically.**
  - Only the adult and children periods exist yet: the longer specialty classes (mental health, maternity, oncology) don't, so customers using those set `Retention:AdultYears` to their longest class, and the page and the anonymise dialog warn.
  - The conclusion of treatment counts the procedure audit too, so a deleted procedure still counts; a 29 February birthday falls on 1 March in other years (`RetentionSchedule.AddYears`).
- **Sign-ins and the security baseline:** a sign-in throttled by `LoginThrottling` (429) is refused before the handler runs, so it's not in the activity log; the throttling logs it at Warning instead. A name no account could have (`UsernameRules.CouldExist`) is refused as unknown and logged as a refused sign-in with no account. Signing a user out everywhere is logged (`SignedOutEverywhere`), and a password change or reset is logged inside the same transaction as the change and the end of the sessions.
- **Not built yet:** purging sign-in events and other operational data, which needs a scheduled job (`docs/todo.md`).

### Insights

Admins' overview of the work (`/admin/insights`, `GET api/procedures/insights`): headline counts against the same point last week, overdue work by assignee and by priority, procedures created and completed each week, and the average time at each stage of each template.
- **Aggregated in SQL:** the LINQ is in `ProcedureInsightsQueries` (`Application/Procedures/Insights/Common`), each query ending in a `GroupBy` or `Count`; `ProcedureInsightsRepository` runs it, and the unit tests run the same LINQ in memory. `ProcedureInsightsSqlTests` checks that each query translates to SQL Server's SQL (`ToQueryString`, no database).
- **SQL-only functions** go in `InsightsFunctions`, with a C# body for the tests, mapped to SQL in `InsightsDbFunctions` (`SecondsBetween` is `DATEDIFF_BIG`, `JsonValue` is `JSON_VALUE`). They're not in the model snapshot, so they need no migration.
- **Last week's state is rebuilt backwards from now,** from the audit entries since the moment: a procedure's status then is the `"from"` of its first `StatusChanged` entry after it (`{"from":"…","to":"…"}`, as `ProcedureAudit` writes it), or its status now if nothing changed since; its due date then is the `"from"` of its first due date change after it (`DetailsUpdated`, `changes.dueDate`), or its due date now. So keep those details formats. Only recent history is read, and procedures from before the audit log need none. Completions are `StatusChanged` entries to Completed (each time, so one completed twice counts twice), and creations are `Created` entries.
- **Keep SQL Server on the index:** a correlated `TOP(1)` over a procedure's entries seeks the `(PatientProcedureId, AtUtc)` index only while its `ORDER BY` is plain columns; sorting on the details text made it scan the whole table for every procedure. Time a change to these queries on a large synthetic database (the review of #66 has the numbers).
- **Deleted procedures:** with every template, the counts from the audit log (created, completed) include procedures deleted since; with one template, they're matched to existing procedures, so deleted ones drop out, and the templates' weeks needn't add up to the total. Last week's statuses only count procedures that still exist.
- **Drill-down links** go to the procedures list with `mine=false` (so a start-on-mine setting can't narrow them) and the template by its ID (`templateId`). "Completed this week" has no link: no list shows what was completed when.
- **Weeks are UK weeks,** Monday to Sunday (`InsightsPeriod`), and "last week" is the same point in last week as now is in this one. Hourly counts from SQL are summed into weeks in C#, since the UK's offset changes are on the hour.
- **Stage times** run from a stage being reached (the stage before it first finished, or the procedure created) to it being started (waiting), then to its first finish (working). The first finish is from the audit log, because unlocking and finishing a stage again moves its own `CompletedAtUtc`.

### NHS number, FHIR and SNOMED CT

Roadmap step 9's first part. What's built and what's left is in `docs/architecture.md` (step 9) and `docs/todo.md`.
- **The NHS number** (`Patient.NhsNumber`) is optional, stored as its 10 digits with no spaces (`varchar(10)`), and unique when present (the filtered unique index `IX_Patients_NhsNumber`). It's unique across the deployment until step 8 makes it unique within an organisation.
  - `NhsNumbers` (`MedApp.Domain/Patients`) removes spaces, checks the Modulus 11 check digit, spots placeholders that pass it (`IsPlaceholder`: ten of one digit, `0123456789`, `9876543210`) and formats it; `NhsNumberRules` (`MedApp.Application/Patients/Common`) is the validation rule for every command that takes one, and refuses placeholders with their own message. The web form checks the same (`src/utils/nhsNumber.ts`). Accept it with or without spaces; show it as `XXX XXX XXXX`.
  - Another patient with the number is a 409 (`ConflictException`), also when two saves race: the repository turns the unique index's violation into the same 409. SQL Server's message for that violation holds the number, so EF Core's failed-save and failed-command events are logged at Debug (`LogFailedSavesAtDebug` in `AddDatabase`), which isn't written; keep it that way.
  - On update, null leaves it unchanged and empty removes it.
  - `GET api/patients/search` filters by it (`NhsNumber`: numbers containing the digits typed, spaces ignored).
  - The export includes it, and anonymisation removes it (`PatientAnonymiser`), though not from saved searches yet (`docs/todo.md`). **Always Encrypted for it isn't done** (`docs/todo.md`).
  - **Keep it out of new URLs** (a path or a query string): request logs and traces record URLs. Send it in a body, as the demographics lookup does. The FHIR search's query string still carries it, as FHIR defines it, and so does the patients list's filter, which stays in the URL by the product owner's decision on list filters (`docs/todo.md`).
- **The FHIR API** (`FhirController` at `api/fhir`; `MedApp.API/Fhir`, `MedApp.Application/Fhir`, DTOs in `MedApp.Contracts/Fhir`) is read-only FHIR R4 in the UK Core profiles' shape, patients only: `GET api/fhir/metadata` (a minimal CapabilityStatement, open to anyone), `GET api/fhir/Patient/{id}`, and `GET api/fhir/Patient?identifier=https://fhir.nhs.uk/Id/nhs-number|{number}` (a searchset Bundle). A value with no system matches as an NHS number only when it is one, and otherwise matches nothing, as does another system; no identifier, or an invalid number with the NHS number's system, is a 400.
  - **Flagged records:** an anonymised patient is sent as `active: false`, an `anonymous` name, the year of birth alone and no email, never its placeholders as details; a restricted or disputed one carries a `meta.tag` from MedApp's record-flag code system (`FhirPatientMapper`).
  - **Hand-built DTOs, not the Firely SDK.** Its licence (BSD-3-Clause) was fine; its size and dependencies weren't worth it for three resource shapes. Revisit when the API needs more resources (CarePlan, Task) or validation against the profiles.
  - **Return resources through `FhirResult`** (`FhirJson`): `application/fhir+json`, `Cache-Control: no-store`, and no nulls or empty arrays, which FHIR JSON never holds (leave a list null rather than empty).
  - **JSON only:** `FhirFormatFilter` answers a `_format` or `Accept` that doesn't allow JSON with a 406.
  - **Errors are OperationOutcomes, never ProblemDetails:** `FhirExceptionFilter` makes 400 `invalid` and 404 `not-found`, `FhirAuthorizationResultHandler` 401 `login` and 403 `forbidden`, `FhirFormatFilter` 406 `not-supported`, and an unknown path under `/api/fhir` is a 404 `not-supported` (`FhirJson.NotFoundAsync`, mapped before the generic `/api` 404). The forced password change's 403 stays the API's ProblemDetails.
  - **Who:** the Staff policy, with the session cookie; no OAuth clients for other systems yet.
  - **Logged as the pages are:** a read records `PatientViewed`; a search records `PatientsSearched` (filters `["nhsNumber"]`, or `["identifier"]` when it couldn't match an NHS number; the count; `via: "fhir"`) and `PatientListed` for each patient found.
  - The NHS number's verification status is always `02` ("Number present but not traced"), because MedApp doesn't trace numbers with PDS.
- **SNOMED CT codes on stage definitions** (`SnomedCode` and `SnomedTerm`, both or neither): `SnomedCt` (`MedApp.Domain/Terminology`) checks the format only (a concept's SCTID: 6 to 18 digits, no leading zero, partition `00` or `10`, a Verhoeff check digit), through `SnomedRules`. There's no terminology server, so nothing checks that the concept exists or is active, or that the admin's term matches it. They're copied onto a procedure's stages when it's created, like the name, description and instructions.
- **The demographics lookup (PDS)** is `IPersonalDemographicsService`, chosen by `Pds:Mode`: `Off` by default (`NoPersonalDemographicsService`), or `Offline` (`OfflinePersonalDemographicsService`, four synthetic 999 people). `GET api/demographics/status` says whether there's one; `POST api/demographics/lookup` (`{ nhsNumber }` in the body, never the URL) looks someone up (staff, `no-store`; 400 for an invalid number, 404 when nobody has it or there's no lookup). **The real PDS FHIR API isn't wired in:** it needs NHS England's onboarding (`docs/todo.md`).
- **Medical device decision:** all four only identify, label or move data without change, so the decision is unchanged (`docs/clinical-safety/intended-purpose-and-device-decision.md`). Anything that interprets codes or chooses them from clinical data needs a new assessment.

### Migrations

- Migrations live in `MedApp.Infrastructure/Migrations/` with `MedAppDbContextModelSnapshot.cs`. They are a single linear history starting at `InitialCreate`. Always add a new migration on top, and never edit or delete one that has been applied to a database.
- Name migrations in the same past-tense style as commits, for example `RemovedTemplateAuditColumns` or `RenamedTasksToProcedures`.
- **Always read the scaffolded migration before keeping it.** EF can't detect renames of entities or of properties used as keys, so it scaffolds a rename as `DropTable` + `CreateTable`, which deletes the data. When `migrations add` warns that "An operation was scaffolded that may result in the loss of data", rewrite `Up` and `Down` by hand. Drop the keys and foreign keys whose names change, then call `RenameTable`, `RenameColumn` and `RenameIndex`, then re-add the keys and foreign keys with the same `onDelete` behaviour. `RenamedTasksToProcedures` is the reference example.
- **A migration test reads only the columns that exist at its step:** project (`.Select(n => new { n.Id, ... })`) or use SQL, never whole entities (`ToListAsync()` on a `DbSet`), because a later migration can add columns to the same table, and EF would ask for them ("Invalid column name"). Counting (`CountAsync`, `AnyAsync`) is fine.
- After editing a migration, `has-pending-model-changes` must report no changes. Otherwise the snapshot and the model disagree.
- Test a non-trivial migration up **and** down against a throwaway LocalDB database, not the dev `MedApp` database. Pass `--connection "Server=(localdb)\MSSQLLocalDB;Database=MedApp_MigrationTest;Trusted_Connection=True;TrustServerCertificate=True"` to `dotnet ef database update`, seed synthetic rows, apply the migration, roll back with `database update <PreviousMigration>`, then drop the database.
- Applying a migration to someone's local `MedApp` database changes their data, so do it only when asked, and take a `medapp-dev` `save_snapshot` first.

### Auth

- On login, a `UserSession` row is created and its ID goes into an HttpOnly cookie. `SessionAuthenticationHandler` checks the cookie on every request and builds claims, including roles and the session's own ID (`SessionIdClaim`, read with `User.GetSessionId()`).
- **Sessions last 8 hours** from sign-in (`UserSession.Lifetime`), and can be extended to 24 hours at most (`MaxLifetime`; over 20 hours, so WCAG 2.2.1 allows the hard limit). Using the app doesn't extend one; only asking does:
  - `GET api/auth/session` returns the signed-in session's `SessionResponse`: `expiresAtUtc`, `expiresInSeconds` (by the server's clock, so a device with a wrong clock still counts down right) and `canExtend`. Reading it never extends it.
  - `POST api/auth/session/extend` ("Stay signed in") moves the expiry to 8 hours from now, but never past 24 hours from sign-in and never earlier than it was, and sends the cookie again with the new expiry (the cookie expires with the session).
  - Both take the session from the cookie, are open to anyone signed in (`[Authorize]`, no role needed), are sent `no-store`, and are a 401 once the session has ended. `SessionTimeout` in `MedApp.Web` uses them for the warning before a session times out.
  - **The forced password change page has no timeout warning.** `/change-password` is outside the signed-in layout, and `PasswordChangeRequired` doesn't allow the session endpoints, deliberately: that page ends at the session's normal expiry, without a warning, and its change then fails, so its user signs in again.
  - A session isn't ended by a lockout yet (risk S5). Password changes and resets end sessions (below).
- The UI is always on the API's own origin (served from `wwwroot` in production, proxied by Vite in development). So there is no CORS, and the cookie is `SameSite=Lax`.
- **The cookie's name:** outside Development it's `__Host-medapp.session`: `Secure`, `Path=/` and no `Domain`, which browsers require of a `__Host-` cookie, so only this host over https can set it. In Development it stays `medapp.session`, not `Secure` (the Vite dev server is plain http). Only `ISessionCookieService` knows the name (`CookieName`, `TryGetSessionCookie`); read the cookie through it.
- **Sessions end when the password changes** (the handlers call `ISessionService.RevokeUserSessionsAsync`, through `UserSessions.EndSessionsAsync`, inside `IIdentityTransactions.RunAsync` with the change, so both are kept or neither is):
  - changing your own password ends your other sessions and keeps the one you changed it from;
  - an admin's password reset ends all of the user's sessions;
  - **a role change doesn't end sessions:** roles are read on every request, so it applies to the user's next request, and they stay signed in;
  - an admin can sign a user out everywhere: `POST api/auth/users/{username}/sign-out-everywhere` (204, or 404 for an unknown user), and the Users page's "Sign out everywhere" action, with a confirmation.
  - A new account action that changes how someone signs in should end their sessions the same way, in the same transaction. An open live-notifications connection isn't closed when its session ends (`docs/todo.md`).
- **Sign-in throttling** (`MedApp.API/Common/RateLimiting`), in front of Identity's lockout, which stays: `POST api/auth/login` allows 30 attempts a minute per client address (IPv6 counted by its /64) and 5 a minute per username from anywhere, right or wrong. Over either, it's a 429 `ProblemDetails` ("Too many sign-in attempts. Try again in N seconds.") with `Retry-After`, before the password is checked, and the login page shows that title. Behind Traefik, the address comes from the forwarded headers. The counts are in each API copy's memory, so two copies allow twice as many. Settings are in the `LoginThrottling` section (`LoginThrottlingOptions`).
  - **What's counted:** only a name that could be an account's (`UsernameRules.CouldExist`): at most 256 characters, of Identity's `User.AllowedUserNameCharacters` (trailing spaces ignored, as SQL Server ignores them). Any other name is unknown, the usual 401, without a lookup (`IdentityAuthenticationService`), because SQL Server's collation would match some (a byte order mark in front, a NUL after, full-width letters) to a real account. A name over 256 characters is a 400 (`LoginValidator`), and a body over 16 KB a 413 (`[RequestSizeLimit]`). The per-username key is trimmed, NFKC-normalised and upper-cased (`LoginUsernameLimiter.Key`).
  - **Each refusal is logged** at Warning, with the limit and the client's key (its address, or IPv6 /64), never the username (`LoginThrottling.LogRefusal`).
  - **Sizing:** 30 a minute per address suits a site whose staff reach MedApp from their own addresses. A hospital behind one NAT or proxy address (an HSCN gateway) shares that allowance between everyone, and at a shift change a few hundred sign-ins arrive in minutes. If staff report "Too many sign-in attempts", or the refusal warnings show one address, raise `LoginThrottling:PerClientPermitLimit` for that deployment (for example to the number of staff who start a shift together, per copy of the API); keep the per-username limit at the lockout count. The integration tests sign in far more often than people do, so `MedAppApiFactory` sets both limits out of reach, and `LoginThrottlingTests` puts the real ones back on an API of its own. The E2E suite signs in as its admin once a run, well under the limits, so CI's `e2e` job needs no setting. The per-address limit is the `login` rate limiting policy; the per-username one is the `[ThrottleLoginByUsername]` action filter, because the username is in the body.
- **Common passwords are refused** when a password is set (creating an account, changing or resetting a password), never at sign-in: `CommonPasswordValidator` (`MedApp.Infrastructure/Common/Identity`) holds the 10,000 most used passwords from the NCSC's list, embedded from `Passwords/common-passwords.txt`, compared ignoring case. Its source and licence are in `Passwords/NOTICE.txt`. Generated passwords never match it (a test makes 500).
- **Security headers** (`MedApp.API/Middleware/SecurityHeaders.cs`, first in the pipeline) go on every response: `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy` that turns off device features. Every `/api` response is `Cache-Control: no-store`, with `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
  - **Pages, outside Development, get a Content Security Policy with a new nonce for each response:** scripts only from the app's origin or with that nonce, styles from the origin and inline (the server writes style attributes), `connect-src 'self'` (which covers the notifications WebSocket), `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`. `SsrPages` sends the nonce to the page server in `X-MedApp-Csp-Nonce`; `server.mjs` passes it (if it's base64) into the request's context; `createSsrRouter` gives it to the router (`ssr.nonce`), which puts it on every script it writes and in a `csp-nonce` meta tag for the browser's router. The client-rendered fallback (`index.html`) has no inline scripts, so `'self'` covers it.
  - **Never add an inline script or `eval`** to the app: the policy refuses them. A new external origin (fonts, images, an API) needs the policy changed, deliberately.
  - In Development the API sends only `frame-ancestors 'none'` to non-API paths: pages come from Vite there, and Swagger UI needs inline scripts. `SecurityHeaders:PageCspReportOnly=true` sends the page policy as report-only, an emergency switch that needs no new build.
- The threat model is `docs/security/threat-model.md`, and the ASVS 5.0 Level 2 checklist is `docs/security/asvs.md`. A change to authentication, sessions, headers or a data flow should update both.
- The roles are `Admin` and `User`. Staff (either role) use `[Authorize(Policy = AuthPolicies.Staff)]`: patients (with their timeline, which shows staff less than admins: see [Patient timeline](#patient-timeline)), the FHIR API (its CapabilityStatement is open to anyone) and the demographics lookup, creating and working on procedures, attachments (staff delete only their own: see [Attachments](#attachments)), everyone's calendars, meetings and every appointment, and the blocks, own day and week templates (anyone's can be read) and default week of their own calendar. Admin-only endpoints use `[Authorize(Roles = "Admin")]`: users and roles, stage definitions and templates (staff can read them), activity types (staff can read them), arranging, changing and cancelling meetings (staff can read them), the team view and suggested meeting times, assigning staff, unlocking stages, deleting procedures, the procedure audit log, Insights (`GET api/procedures/insights`), the activity log, a patient's export, restriction, dispute, anonymisation and retention review, and monitoring rules (`api/monitoring/rules`). Admins can also change anyone's calendar blocks, day and week templates and default week (`CalendarGuards.EnsureCanChangeTemplatesOf`, checked in the handlers), and finish a stage that needs a visit without one ([Calendar and appointments](#calendar-and-appointments)). There may be several admins; never assume one. The `SelfUserOnly` policy limits a user to their own `{username}` route.
- Procedure handlers get the signed-in user as a `ProcedureActor`, from `User.ToProcedureActor()` (`MedApp.API/Common/Authentication/ClaimsPrincipalExtensions.cs`).
- The app seeds no users; its only `HasData` seed is a default stage definition. **Locally, sign in as `admin` / `admin`.** `medapp-dev` creates that test login (`ensure_test_admin`, and on every `reset_demo_data`), bypassing the password rules. It exists only in local dev databases.
- **A deployed database gets its first admin deliberately:** `dotnet MedApp.API.dll create-first-admin` (`FirstAdminSetup`) makes the Admin and User roles and an admin with both (User lets them change their own password) from the `FirstAdmin:Username` and `FirstAdmin:Password` settings, but only while there are no accounts at all, then exits. The Helm chart's migrations Job runs it after migrating, with the credentials from a Secret.
- **The server generates every new account's first password;** there is no default password. `POST api/auth/users` takes only a username, creates the account with a generated first password that meets the `Identity` rules (`IIdentityUserService.CreateUserAsync`, the same generator as a reset), and returns it once in `CreateUserResponse`. The password is shown once, and its user must change it before doing anything else (below). The Users page shows it to the admin once (`OneTimePassword`, with a copy button), to pass on securely, and forgets it when the dialog closes.
  - **A generated password must be changed at first sign-in.** `ApplicationUser.MustChangePassword` is set by `IdentityUserService` when it creates an account or resets a password, in the same save as the password, and cleared when `UpdateUserPasswordAsync` succeeds, in the same update. A new password must differ from the current one (`UpdateUserValidator`).
  - **How it's enforced:** `SessionService` reads the flag on every request, and `SessionAuthenticationHandler` turns it into a claim (`SessionAuthenticationDefaults.MustChangePasswordClaim`). `whoami` reports it as `mustChangePassword`. While it's set, `PasswordChangeRequired` (`MedApp.API/Common/Authentication`, between authentication and authorization) refuses every `/api` request, the notifications hub included, with a 403 `ProblemDetails` (title "Password change required", `code: "password_change_required"`). It allows only what every `AccountHold` allows (`GET api/auth/whoami`, `GET api/auth/me/settings`, `GET api/auth/features`, `POST api/auth/login` and `login/two-factor` (signing in again checks afresh and replaces the session), `POST api/auth/logout`, and the anonymous `password/forgot`, `password/reset` and `email/confirm`), and `PUT api/auth/users/{username}/update-password` for their own username (compared as `SelfUserOnly` compares it, `AuthPolicies.IsOwnUsername`). Pages and static files pass: the web app's `_app` guard sends them to `/change-password`, which asks for the given password and a new one, then opens their start page. A page already open when the flag is set finds out from its next API call: the API client sends any 403 with that `code` to `/change-password` with a full page load (in the browser only).
  - **Exempt:** the first admin (`FirstAdminSetup`), whose password comes from the secret store, set by whoever deploys (on kind, `up.sh` generates it, and it can be read back from the cluster's secret store, which is acceptable for a local cluster); and every account `medapp-dev` makes or sets a password on (`create_user`, `set_password`, `ensure_test_admin`, and `reset_demo_data`'s staff, except its new starter, who shows the forced change), so they can sign in and work at once.
  - **`CreateUserResult`** carries a password exactly when the account was created: make it with `Created(password)` or `Failed(result)`. It and the password responses never print the password in `ToString()`, and the API sends them with `Cache-Control: no-store`.
  - **Accounts created before #53** (from the Users page or the Blazor client) were given the published password `DefaultPassword1`, and may still have it. An admin should reset those accounts' passwords, or ask their users to change them. Finding them is a to-do (`docs/todo.md`).
- Identity password and lockout rules live under the `Identity` section of `appsettings.json`.

### Email, password reset and two-factor authentication

Built on `feature/email-2fa`, with codes by email added on `feature/email-2fa-codes`. Everything here is optional: an account without an email address or two-factor signs in exactly as before.
- **Sending email:** handlers call `IEmailSender.SendAsync(EmailTemplates.…)` (`MedApp.Application/Common/Email`) after their own change is saved. It's best effort: `EmailQueue` (Infrastructure) queues the message in memory and returns at once, and `EmailDispatcher` sends it over SMTP with MailKit in the background, notices and two-factor codes before links, logging failures by category, exception type and SMTP status only (a server's message can quote the address). Each copy sends at most `Email:MaxPerHour` an hour (`EmailBudget`, default 100, 8 on Azure under the managed domain's 10), a fifth kept for notices and a fifth for two-factor codes (`EmailCategory.Code`), which links (anyone can ask for a reset link) can't use; codes may also use what links leave. Over it a message is dropped and logged. `IEmailSender.HasRoomFor` looks before a code is made, so a code that can't go isn't promised. Codes by email still need a mail service with a bigger allowance than Azure's managed domain: a handful of sign-ins use up its hour. Nothing is retried, and a message still queued when the API stops is lost; every email today can be asked for again.
  - **Settings** (`Email` section): `LinkBaseUrl` (where links point: configured, never from the Host header), `FromAddress`, `FromName`, `MaxPerHour`, and `Smtp:{Host, Port, Security, Username, Password, TimeoutSeconds}` (`Security` defaults to `StartTls`: TLS required; `None` only for a local catcher such as Mailpit). Without a host and a from address nothing is sent; without `LinkBaseUrl` no email with a link is sent. `EmailAvailability.CanSendLinks` says whether both are set, and `GET api/auth/features` tells the web app, which hides "Forgot your password?" and email fields when it's false.
  - **Development:** the AppHost runs **Mailpit** (`axllent/mailpit`), which catches every email: open its **Inbox** link on the dashboard. kind runs it too (`mailpit.enabled`; read it with the port-forward in `deploy/kind/README.md`). Azure sends through Azure Communication Services' SMTP relay (`deploy/azure/README.md`, Email).
  - **Templates** (`EmailTemplates`): plain, accessible HTML (a language, a title, real links, no images) and the same words as text, every value HTML-encoded. **Never put clinical text in an email** (no patient, procedure or notification text: a notification's title is a procedure's title), **and never a password, an authenticator key or recovery codes.** The one code an email may carry is a short-lived, single-use two-factor code (`EmailTemplates.TwoFactorCode`), with nothing else in that email but what it's for, how long it lasts and what to do if you didn't ask for it (no username, no link), and never in its subject. A new account's welcome is only the link to confirm its address.
  - **Security notices** (`ISecurityNotices`): a short email to the account's confirmed address when its password is reset by link, two-factor is turned on (with the app or codes by email) or off or reset by an admin, recovery codes are used or replaced, a new address is asked for (sent to the confirmed one) or its address changes (sent to the old one) or is removed (by its owner or an admin), or wrong codes lock it. `SendToOtherAdminsAsync` emails every other admin with a confirmed address when an admin turns two-factor on, off or has it reset.
- **Staff email addresses** are Identity's `Email` and `EmailConfirmed`, plus `ApplicationUser.PendingEmail`: a new address waits there until the link sent to it is opened, and the old one stays in use until then. Only a confirmed address is ever used or returned as the account's (`UserResponse.Email`; the pending one is `PendingEmail`). Several accounts may share an address. An admin can give one when creating an account (`CreateUserRequest.Email`), and remove any account's (`DELETE api/auth/users/{username}/email`, recorded with the admin; the address is told). People set, change or remove their own in Account Settings (`GET`/`PUT`/`DELETE api/auth/me/email`), with their password (`PasswordConfirmation`: a wrong one is a 400 on `Password` and counts towards the lockout), at most 3 changes in 15 minutes (`AccountAttemptLimiter`, 429). Only the bare address is stored (`EmailAddressRules.Normalize`: a display name is dropped, lists and line breaks refused). The link opens `/confirm-email`, which posts to `POST api/auth/email/confirm` **signed in as the account the link is for**: the link proves the mailbox, the session the person, so whoever reads a mistyped or shared address can't confirm it (signed out: 401, and the page asks them to sign in, then confirms; another account: 400 `WrongAccount`). Every hold allows it, so someone held to choose their first password can confirm the address an admin gave them. Each account needs an address of its own, not a team mailbox. The token is Identity's change-email token, bound to the address and the security stamp, valid 24 hours. **While an account signs in with codes by email,** its address can't be removed (a 409, `RemoveMyEmailHandler.SignsInWithEmailCodes`, and for admins `RemoveUserEmailHandler.SignsInWithEmailCodes`: turn two-factor off, move to the app, or reset it, first); a change of address keeps the method, and codes go to the new address only once it's confirmed.
- **Emailed links carry their token in the fragment** (`/reset-password#user=…&token=…`, `EmailLinks`), which browsers never send to a server, so tokens stay out of access logs and the Referer header; the page reads it after mounting.
- **Forgot your password?** `POST api/auth/password/forgot` with a username or an address always answers 202, whatever matched, and emails a reset link to the account with that username and to every account whose confirmed address it is (none without a confirmed address). It's throttled per client address (the `login` policy) and per username or address (`ThrottleResetRequestsAttribute`: 3 in 15 minutes, `LoginThrottling:ResetRequests…`). `POST api/auth/password/reset` takes the link's user and token and the new password: Identity's reset token from `PasswordResetTokenProvider` (30 minutes; single-use, because a reset changes the security stamp). A bad, used or expired link, or an unknown user, is the same 400 `InvalidToken`; the new password must meet the rules, avoid the common ones and differ from the current one (`SamePassword`). On success, in one transaction with the new password, every session ends; the must-change-password flag clears, any lockout ends, and the owner gets a notice. Two-factor stays on (for an account with codes by email, the next code goes to the same mailbox as the link: threat model T-52).
- **Data protection keys** (which seal every Identity token) are in the database (`DataProtectionKeys`, `PersistKeysToDbContext`), so every API copy shares them and a link made by one opens on another; on Azure `DataProtection:KeyVaultKeyUri` wraps them with a Key Vault key (the API's workload identity). Without it they're stored unwrapped, beside the security stamps, so a copy of the database could forge reset links: the API warns at startup outside Development (`DataProtectionKeyCheck`), and so does the chart's `NOTES.txt`. The application name is fixed (`MedApp`). Integration tests keep the table across resets.
- **Two-factor authentication** has one method per account (`ApplicationUser.TwoFactorMethod`, a `TwoFactorMethod`, stored by number, so never renumber it: `None = 0`, `Authenticator = 1`, `Email = 2`; read it through `EffectiveTwoFactorMethod` or `ITwoFactorService.GetMethodAsync`, which count two-factor on with no method recorded as the app). Moving between them means turning one off and the other on, except from codes by email to the app, which `POST …/authenticator` and `POST …/enable` allow while codes by email are on (with the current factor as well), so two-factor never goes off. **After rolling the image back and forward again,** an account given an app on the older version (which ignores the column) may still read as `Email`: look at accounts with `TwoFactorEnabled = 1` and `TwoFactorMethod = 2` that someone says use an app (a switch in progress looks the same, so it isn't fixed automatically) and reset their two-factor.
- **The authenticator app** (TOTP) uses Identity's authenticator support for the key, the recovery codes and `TwoFactorEnabled`, but checks codes itself (`Totp`, `TwoFactorService`): against `TimeProvider`, one 30-second step either side, and each code once (the last step accepted is kept as a user token, `[MedApp]`/`AuthenticatorLastTimeStep`). It's the stronger choice.
  - **Setting up** (Account Settings, Security): `POST api/auth/me/two-factor/authenticator` gives a new key, as text and as a QR code drawn on the server (`QrCodeRenderer`, Net.Codecrete.QrCodeGenerator, MIT) and sent as one SVG path, so the web app needs no QR library and the CSP needs no change; `POST …/enable` with the password and a code turns it on, returns ten recovery codes once, and ends the account's other sessions. `POST …/recovery-codes` (the password and a code) replaces them; `POST …/disable` needs the password and a code (or recovery code). Wrong codes there count towards the lockout and the account's code limit, and these endpoints are limited per address like sign-in. Responses with keys or codes are `no-store`, and those records never print them.
  - **Codes by email** (`IEmailCodeService`, `EmailCode`, `EmailCodes`), for someone with a confirmed address, are the weaker choice: anyone who gets into the mailbox gets the code (NIST SP 800-63B doesn't accept email for out-of-band authentication), and for these accounts a reset link and a code reach the same mailbox. A code is 6 digits from `RandomNumberGenerator`, valid 10 minutes (`EmailCode.Lifetime`), used once, stored only as a SHA-256 hash bound to its row and compared in constant time, sent only to the confirmed address, never logged. Each account has one live code per purpose (`EmailCodePurpose`: `SignIn`, bound to its challenge, which then lasts 10 minutes, `SignInChallenge.EmailLifetime`, and the code ends with it, as its email says; `TurnOn`, bound to the address it went to; `Confirm`, for turning off, new recovery codes, switching to the app and moving the address), and a new code replaces the last; a filtered unique index (`IX_EmailCodes_UserId_Purpose`, outside sign-in) stops two first sends at once both standing. A code out of tries isn't live, so asking again makes a fresh one. Every check cleans a code the same way (`TwoFactorCodes.Normalise`: no whitespace, line breaks included), and `EmailCodeService.CheckAsync` answers `Right`, `Wrong` (a guess, counted) or `NotLive` (nothing that could work: not counted, "ask for a new one"). A code can be sent again at most once a minute and three times (`EmailCode.ResendInterval`, `MaxResends`, one SQL statement, `TryResendAsync`), and each account gets at most 10 emailed codes in 15 minutes (`AccountAttempt.EmailCode`, `LoginThrottling:EmailCodesPerAccount…`); over either is a 429 with `Retry-After`. Codes for turning on and confirming allow five tries each (`TryReserveAttemptAsync` on the code); a sign-in's use its challenge's.
    - **Turning them on:** `POST api/auth/me/two-factor/email` with the password (refused, 409, while two-factor is on, without a confirmed address, or where email can't be sent) emails a code (a 202 `EmailCodeSentResponse`: where, masked, `j•••@example.com` (`EmailAddressMask`), and when it can be sent again; calling it again resends); `POST …/email/enable` with that code turns two-factor on with `Email`, returns ten recovery codes once, ends the other sessions, and tells the owner (`EmailCodesEnabled`) and, for an admin, the other admins. A wrong code there doesn't count towards the lockout, as with setting up the app.
    - **While they're on:** `POST …/email/code` with the password (a 400 on `Password` when wrong, counting towards the lockout) emails a `Confirm` code (409 for any other account, or when it can't be sent now); `POST …/disable` and `POST …/recovery-codes` take it as their `code` (disable takes a recovery code too), counted exactly as an authenticator code (`TwoFactorCodes.VerifyOrThrowAsync`). **Moving to the app** (`POST …/enable`) needs it as `currentCode` (or a recovery code), and **moving the address** (`PUT me/email`) as `code`, so a session and the password can't swap the second factor; a switch emails the owner and, for an admin, the other admins (`TwoFactorSwitchedToApp`, `AdminTwoFactorSwitchedToApp`). A held admin may call `…/email/code`, to switch. `GET …/me/two-factor` gives the `method` (`None`, `Authenticator`, `Email`), `canUseEmailCodes` and `emailCodesUnavailableReason` (`NoConfirmedAddress`, `EmailUnavailable`).
  - **Signing in:** for an account with two-factor, `POST api/auth/login` answers **202** with a `TwoFactorChallengeResponse` (its `method`, and for codes by email `emailCode`: where it went, masked, or null if none could be sent) and no session or cookie; for codes by email the password step emails the code. `POST api/auth/login/two-factor/resend` with the challenge sends a new one (401 `sign_in_expired` for an unusable challenge, 409 for an account without codes by email, 429 too soon or too often); every hold allows it, as it allows signing in. The challenge (`SignInChallenge`) is 256 random bits, stored only as a SHA-256 hash, bound to the user, valid 5 minutes, allowing 5 codes, and deleted when used (so only one request can finish a sign-in). `POST api/auth/login/two-factor` with the challenge and a code (the app's, or the one emailed for this challenge) or a recovery code makes the session as sign-in always has. A wrong code is a 401 and counts towards the lockout, emailed or not; with two-factor on, a right password doesn't clear the count (only a complete sign-in does), so codes can't be guessed by re-entering the password.
  - **Codes sent at the same moment** get no more checks than codes sent one by one: each challenge attempt is **reserved in one SQL statement before the code is checked** (`TryReserveAttemptAsync`: `WHERE FailedAttempts < 5 AND ExpiresAtUtc > now`; none left is the same 401 `sign_in_expired`), and wrong passwords and codes are counted in one statement (`IAccountLockoutRepository`), never Identity's read-then-write `AccessFailedAsync`, which loses counts to its concurrency check and leaves a failed update to break the activity log's save (after a failed Identity update, `Forget` the user). Each account gets at most 10 code checks in 15 minutes from anywhere (`AccountAttemptLimiter`, `LoginThrottling:TwoFactorCodesPerAccount…`, a 429 with `Retry-After`; in each copy's memory). A lockout caused by codes lasts the usual 5 minutes, doubling each time (`CodeLockouts`, `ApplicationUser.TwoFactorLockouts`, to a day at most) until a complete sign-in, and emails the holder. `ParallelCodeTests` sends 30 at once, authenticator and emailed codes, and 30 resends at once (one email goes); keep it passing. An unusable challenge is a 401 with `code: "sign_in_expired"` (start again). A recovery code used to sign in emails the owner. The forced password change comes after the code.
  - **Admins:** `POST api/auth/users/{username}/reset-two-factor` turns someone's two-factor off and forgets their key and codes, ending every session they have (not your own: 400 `OwnTwoFactor`). The admin setting **Require two-factor authentication for admin accounts** (`/admin/settings`, `GET`/`PUT api/auth/security-settings`, one `SecuritySettings` row) can only be turned on by an admin who uses the authenticator app, and needs the app: codes by email don't meet it (they're weaker), so while it's on an admin without the app (two-factor off, or on with codes by email) is held from their next request by **`TwoFactorSetupRequired`**, an `AccountHold` beside `PasswordChangeRequired` (which comes first): a 403 with `code: "two_factor_setup_required"` for everything but setting it up (and what every hold allows), and the web app sends them to `/set-up-two-factor`; `whoami` reports `mustSetUpTwoFactor`, and the hold page says why for an admin with codes by email. Setting up the app replaces their codes by email. They can't turn it off while it's required. `SessionService` reads the setting only for an admin without the app. Admin Settings' `adminsWithoutTwoFactor` counts admins without the app.
  - **A new hold** derives from `AccountHold` (its allowlist, title and `code`), is added to the pipeline after `PasswordChangeRequired`, and gets a guard in the web app's `_app` route and `src/api/client.ts`.
- **Security events** (two-factor changes, codes by email turned on or off, resets and their requests, email address changes, recovery codes used, the admin requirement) go through `ISecurityEventLog` (`MedApp.Application/Common/Security`). `ActivitySecurityEventLog` writes each to the activity log (`ActivityAction` 28 to 41; `ActionFor` maps them: `EmailCodesEnabled` is 40, `EmailCodesDisabled` 41; moving from codes by email to the app is `TwoFactorEnabled` with `switchedFrom: "email"`) and to the application log (`LoggingSecurityEventLog`). An event about someone's own account is by them; one an admin made (a two-factor reset, an address given or removed) is by the admin, with the account as its target; one from a request nobody was signed in for (a reset link asked for or used) is by nobody, from the request's address, with the account as its target; a reset request that matched nothing is by no account. Never put an email address, password, token or code in an event.
- **Signing in with two-factor in the activity log:** a right password records `TwoFactorChallenged` (no session yet; `method: "email"` when a code was emailed); the second step records `SignedIn` (with `secondStep`: `authenticator`, `email` or `recoveryCode`) or `SignInFailed` (with `reason`: `InvalidCode`, `InvalidRecoveryCode`, `LockedOut`, `ChallengeExpired`, `TooManyCodes`, or a wrong code that locked the account), by the account the challenge was for. Never the code, and never the address.

## Frontend conventions (MedApp.Web)

All UI work goes in `MedApp.Web`. Its conventions are in `MedApp.Web/AGENTS.md`, which Claude Code loads when working in that folder, and its layout and scripts are in `MedApp.Web/README.md`. In short:
- UI is built only from Astryx components, or composites of them in `src/components/`; icons come from `AppIcon`.
- Pages live in `src/pages/`, with thin route files in `src/routes/`. List pages keep their page, sort and filters in the URL.
- Data goes through TanStack Query and the typed `api` client (`src/api/`).
- Every component and page has a Vitest test.
- After an API DTO or endpoint change, run `npm run gen:api` with the AppHost running, and commit `src/api/schema.d.ts`.

### UI parity screenshots

`tools/ui-parity/` is the Playwright tool that compared the Blazor and React apps screen by screen during the migration. It writes `tools/ui-parity/report.html`. It's a development aid, not E2E tests.
- **Don't capture every screen after every change.** A full run takes about a minute, and reading the images costs tokens, so keep it targeted:
  - **While working,** capture only the screens your change affects, by name (from `screens.ts`), and look at their `react.png`. With the AppHost running, in `tools/ui-parity`: `npm run parity:react -- -g "patient-view|patients-list"`. Sign-in still runs first; one screen takes a few seconds. For a shared component (`Page`, `DataTable`, the side nav), pick two or three screens that use it rather than all of them.
  - **The whole set** (`npm run parity:react`) is only for a change that touches many screens at once (the layout, the theme), or when the user asks. It isn't part of merging.
- The Blazor screenshots on disk are the last baseline from before cutover. Capturing Blazor again means running `MedApp.Client.Deprecated` by hand and allowing its origin in the API again.
- **New screens or states** go in `tools/ui-parity/screens.ts`. Never make a screen confirm a destructive action; only open the dialog.
- **Credentials** live in the git-ignored `tools/ui-parity/.env`; never commit them. Setup and run steps are in `tools/ui-parity/README.md`.

### Dev MCP server (`medapp-dev`)

`.mcp.json` registers `medapp-dev` (`tools/MedApp.DevMcp`) and the Astryx docs MCP (`astryx`).

**Use `medapp-dev` for local account and app-state chores,** instead of hand-written SQL or one-off programs:
- create, reset or unlock dev accounts, and set roles
- sign accounts out
- seed synthetic patients
- check migrations and row counts
- snapshot and restore the whole local database
- reset everything to the standard synthetic demo data set (`reset_demo_data`: about 18 months of a synthetic clinic, replayed through the app's own rules; see below)

It only runs against a local database: by default the AppHost's SQL container, using the password from the AppHost's user secrets, so the AppHost must have run once. It protects `admin`, and destructive tools need `confirm: true`.
- **Before a destructive experiment:** take a `save_snapshot`.
- **Build it first:** `dotnet build tools/MedApp.DevMcp`, because `.mcp.json` runs it with `--no-build`.
- **While it runs, `dotnet build MedApp.sln` fails** with "file is locked by: MedApp.DevMcp". The unit and integration tests reference the tool, and the tool isn't in the solution, so a solution build always rebuilds it as Debug, into the folder the running tool uses. Build and test in Release instead (`dotnet build MedApp.UnitTests -c Release`). The running tool keeps the code it started with, so after a change to the app's rules or the seed, give it the new code: stop it in Claude Code's `/mcp`, run `dotnet build tools/MedApp.DevMcp`, then start it again.
- **`reset_demo_data`** (`tools/MedApp.DevMcp/DemoData`) wipes the data and replays a clinic's 18 months: staff (with a second admin using two-factor, a new starter, a locked-out account and a deleted leaver), about 260 patients, six templates with distinct weekly volumes, about 650 procedures and 2,500 appointments (the numbers vary a little with the day it's run), calendars, notifications, monitoring rules, 60 days of activity log, settings, today's sessions and, when Azurite answers, files. History goes through the shared code the handlers call (`ProcedureChange`, `ProcedureCreation`, `StageFinishing`, `ProcedureDetails`, `StageVisits`, `AppointmentChange`, `AssignmentNotifications`, `AppointmentNotifications`, the monitor's `FindMatchesAsync`, `PatientSearch.FiltersUsed`, the activity log's writer) and, where only a handler is right, its commands, with a clock the seed moves. It returns the generated passwords and the two-factor key and recovery codes. Locally, pass `keepUsers: ["dev-parity"]`. `docs/demo-data.md` is the guided tour of what's in it.
  - **When the app's rules change:** a change to shared code (an audit entry's details, a notification's wording, a stage's visit, a calendar clash) changes the demo data with it. The seed still writes its history's sign-in and search activity entries itself: `DemoActivityParityTests` (unit tests) runs the real commands and fails if they write something else. So change the seed's copy with them.
  - **Its tests:** `DemoDataSeedTests` (integration tests) runs the whole seed at fixed moments (a Saturday, just after midnight the day after a clock change, a Friday afternoon seeded twice) and checks it obeys the app's rules: visits before finishing, no calendar clashes for appointments or stored blocks, nothing before a patient existed or after "now", the same counts from the same seed. `DemoCalendarsTests` checks the calendars at a dozen moments.
- **What the app's layers need from the host,** the tool registers itself in `DevMcpServices` (an activity log actor, `medapp-dev`, and no live notifications). `DevMcpServicesTests` builds them with validation on, so a new service the layers need fails there, not at the tool's start.
- **Docs:** see `tools/MedApp.DevMcp/README.md`.

## Local dev gotchas

- **Docker Desktop must be running.** The dev database is SQL Server 2022 in a container started by the AppHost, with its data in the `medapp-sql-data` volume, on host port `14330` (bound to `127.0.0.1`).
  - The container is **persistent**: it keeps running after the AppHost stops, so `dotnet ef` and `medapp-dev` can still reach it. `docker stop` it to free memory; the next AppHost run starts it again.
  - **Attached files** are in Azurite, another persistent container the AppHost starts, with its data in the `medapp-azurite-data` volume. `medapp-dev`'s snapshots and `reset_demo_data` cover only the database, so after restoring an older snapshot some files' bytes may be missing (a 404 on download) and some blobs orphaned. Its blob endpoint is on host port `14331` (bound to `127.0.0.1`), so `reset_demo_data` can attach files with Azurite's well-known development account (`devmcp.json`); without it, the reset skips files and says so.
  - Aspire generated the `sa` password on the first run and keeps it in the AppHost's user secrets (`Parameters:sql-password`). The database in the volume only accepts that `sa` password, so don't delete or change it.
- **Keeping memory down.** Docker Desktop runs containers in a WSL 2 virtual machine. By default that machine may take half the PC's memory, and it keeps what it used as cache.
  - **The AppHost is the light setup:**
    - in Docker: SQL Server (capped at 2 GB with `MSSQL_MEMORY_LIMIT_MB`, which otherwise takes up to 80% of the machine's memory), Azurite and Mailpit
    - ordinary processes: the API, the Vite dev server and the dashboard
    - the integration tests' SQL Server has the same cap
  - **The kind cluster is the full production-like setup** (the locked-down chart, the separate page server container, Argo CD and the rest), and much the heaviest. It uses memory and CPU even when idle. Start it only to test the chart or a deploy, and stop it afterwards (`deploy/kind/README.md`, Stopping and starting).
  - **Most changes need no containers:**
    - builds, unit tests and Vitest run without Docker
    - the AppHost is for trying the app
    - the integration tests start their own containers and remove them afterwards
  - **A cap for WSL itself** is a setting on each PC, not in the repo. `%UserProfile%\.wslconfig` with `[wsl2] memory=12GB` keeps Docker under 12 GB on a PC with more than 24 GB (below that, the default of half is already lower).
    - Raise it to 16 GB if you run kind and the AppHost together.
    - Current WSL already gives cached memory back when idle (`[experimental] autoMemoryReclaim=dropCache`, the default).
    - To apply it, quit Docker Desktop first, then run `wsl --shutdown`, then start Docker Desktop. Shutting WSL down under Docker kills its containers mid-run.
- The API's `appsettings*.json` have **no connection string**: the AppHost injects `ConnectionStrings__DefaultConnection`. Running the API on its own needs that variable set.
- **An empty database** (a new volume) isn't migrated at startup. Apply the migrations with the command under [Commands](#commands), then load the demo data with `medapp-dev`'s `reset_demo_data`.
- The React dev server (`npm run dev`: Node with Vite, rendering pages on the server) proxies `/api` and `/swagger` to the API, and its own server-side API calls go through that proxy too. If `/api` calls start returning the app's HTML instead of JSON, the proxy has dropped out; restart the AppHost.
- **Server-side rendering in production** (`MedApp.API/ServerRendering`): the page server (`MedApp.Web/server/server.mjs`) is in the image at `/app/ssr/`, with its bundled entry and a copy of the client build's manifest, outside `wwwroot`, so no static file path reaches it. It runs one of two ways:
  - **In Kubernetes, in a container of its own** (the chart's `pages` container, `api.pageServer`): the same image with `node /app/ssr/server.mjs`, in the API's pod, as its own non-root user, read-only, with no capabilities and its own resource limits. It gets none of the API's secrets or environment, only `HOST=127.0.0.1`, `PORT=8082`, `HEALTH_PORT=8083` and `MEDAPP_API_URL=http://127.0.0.1:8080`, so code running in Node can't read the API's connection strings. The API's `Ssr:ServerUrl` (`http://127.0.0.1:8082`) points at it, and the API doesn't start Node itself. It runs as a service of its own: its first process only supervises, running the page server in a worker process that it starts again (after 1 s, doubling up to 30 s while it keeps failing soon after starting) whenever it exits, is killed for running out of memory, or misses its heartbeat for 15 s (a stuck event loop). So the container keeps running, and the API's pod stays in service, while pages fall back for a moment. It has only a liveness probe (`GET /alive` on 8083, answered by the supervisor, which the network policy keeps from everything but the kubelet), and deliberately no readiness or startup probe: either would take the API's pod out of service whenever the page server is. Its own log is `kubectl logs deploy/medapp-api -c pages` (the pod's default container is `api`). It has no renderer key (below), and needs none: the API never redirects requests it received on a loopback address.
  - **Anywhere else** (`docker run`, CI's `e2e` job), with no `Ssr:ServerUrl`: the API starts it with `node` on a free local port, as `Ssr:ScriptPath` (`ssr/server.mjs`, relative to the content root, `/app`). It's never restarted if it stops. Node gets only the environment variables it needs (an allowlist in `SsrServer.StartInfo`), so the API's secrets aren't in Node's environment and can't leak from it by accident, e.g. into logs. That isn't isolation: Node runs as the same user in the same container, so code running in it could still read the API's environment from `/proc`. Its own API calls also carry a key the API gave it (`SsrServer.IsFromRenderer`).
  - **Either way,** the API forwards page requests to it (only the path and query: the host is always Node's), with the CSP nonce in `X-MedApp-Csp-Nonce`, and falls back to `index.html` if Node is missing, not ready or stopped, if a render fails in any way or Node answers with a 5xx, as long as nothing has been sent yet; a page that fails part-way is cut short. Its `ssr` HttpClient has no resilience handler, so a render is never retried. `Ssr:RenderTimeout` covers only getting the page started (its status and headers), and `HttpClient`'s default 100 s timeout applies too; nothing times out a page that's still streaming, so a render that stalls part-way holds the browser's request until the browser gives up. Rendered pages hold the user's data, so they're sent with `Cache-Control: no-store`. Any path with an empty segment (`//`) is refused (`PageServerFiles`), and so, as defence in depth, are `/ssr` and `/.vite`, where the page server and the manifest used to sit in `wwwroot`. The API doesn't apply the https redirect to requests it received on a loopback address, so an https port (`ASPNETCORE_HTTPS_PORT` in `api.env`) can't break the page server's calls for a page's data. Settings are in the `Ssr` section (`SsrOptions`); a `Ssr:ServerUrl` that isn't an http address of a server alone stops startup (the page server serves no https).
- **The production image** is `MedApp.API/Dockerfile`, built from the repo root: `docker build -f MedApp.API/Dockerfile -t medapp-api .`. It builds the React app with Node and the API with the .NET SDK (with SkiaSharp's native library for thumbnails, from its NuGet package), then puts both on the `aspnet` runtime with Node's binary, running as a non-root user on port 8080 (TLS ends in front of it). The app goes in `/app/wwwroot`, and the page server in `/app/ssr` (`dist/ssr` from the build, with the client manifest; `dist/.vite` is left out). The Helm chart runs the page server from this same image, with its own command. The root `.dockerignore` keeps Windows `node_modules`, build output and local secrets out of the build. If you change which projects the API references, update the Dockerfile's `COPY` lines too.
- Kestrel's `https` profiles need the ASP.NET Core dev certificate. If startup fails with "the default developer certificate could not be found", run `dotnet dev-certs https`.
- Session cookies are `SameSite=Lax` everywhere, and `Secure`, with the `__Host-` name, outside Development (the Vite dev server is plain `http://localhost`). Deploying the rename signs everyone out once: browsers still send the old `medapp.session` cookie, which the API no longer reads.

## Testing conventions

- The stack is NUnit 3, FluentAssertions 8, Moq and AutoFixture with AutoMoq. FluentAssertions prints a license banner when tests run; it's expected and not an error.
- The test tree mirrors the source: `MedApp.UnitTests/Application/<Area>/Commands/<Action>/<Action>HandlerTests.cs` and `...ValidatorTests.cs`. Note that `Authentication` maps to `Auth` and `Sessions` to `Session` in the test tree.
- Fixtures are `[TestFixture] public sealed class`, with setup in `[SetUp]`. Build the system under test with `AutoFixtureFactory.Create()`, then `_fixture.Inject(mock.Object)`, then `_fixture.Create<Handler>()`.
- Test names follow `Method_Scenario_ExpectedResult`, for example `Handle_PatientDoesNotExist_ReturnsNull`.
- Put shared test data in `MedApp.UnitTests/Common/Constants/*TestConstants.cs`, and add new constants there rather than inlining magic values.
- Use synthetic data only. This is a medical app, so never put realistic patient PII in tests, seeds or fixtures.
  - **NHS numbers come only from the 999 range** (`999 xxx xxxx` with a valid check digit), which is never issued to real people. Never a number outside it, even a made-up one, as it could be someone's.
- Procedure handler tests derive from `ProcedureHandlerTestBase` (mocked repository and username lookup, fixed clock), and build procedures with `ProceduresTestConstants.CreateProcedure`.
- Handlers that write the activity log get a `RecordingActivityLog` (`_fixture.Inject<IActivityLog>(...)`), which makes entries as the real one does and keeps what's recorded, so tests can check the entries.

**Integration tests** (`MedApp.IntegrationTests`) test behaviour through HTTP that unit tests can't: real SQL translation, real Identity stores and transactions, the authentication handler and policies, the middleware.
- `TestEnvironment` (a `[SetUpFixture]`) starts SQL Server and Azurite (the image the chart runs, with `--skipApiVersionCheck`) once per run, applies the migrations and starts the API against both. Blobs aren't emptied between tests; every file has a new ID. Before each test, `IntegrationTest` empties the database with Respawn (keeping the migrations history, the seeded stage definition and activity types, and the data protection keys), then makes the first admin with the deploy's own `FirstAdminSetup`.
- Do everything through the API where you can, with the helpers in `IntegrationTest` (`SignInAsAdminAsync`, `CreateStaffAsync`, `CreatePatientWithProcedureAsync`, ...). Use `RunInScopeAsync` for a service, and `ExecuteSqlAsync` only for what the API can't do, such as making a session expire.
- A test that acts as an account an admin made must first change its generated password, or every other `/api` call is a 403 `password_change_required`. `CreateStaffAsync` does when the account has a role; an account with no role can't change it (that needs the Staff policy), so it keeps its generated password and stays held. To test the Staff policy itself, give the account a role, let it choose its password, then remove the role (`AuthorisationTests.StaffEndpoint_RolesRemoved_*`). `Auth/PasswordChangeRequiredTests` tests the hold itself, with `CreateForcedUserAsync`.
- Constants are in `Common/Constants/IntegrationTestConstants.cs`.
- **Emails and the clock:** the API's `IEmailSender` is a `FakeEmailSender` (`Api.Emails`), which keeps every message, and its `TimeProvider` is a `TestClock` (`Api.Clock`, or `Clock` in a test) that a test can move on (`Advance`) or set (`SetUtcNow`, or `MoveClockPast` for just after a time): an appointment's start, a day becoming past, a challenge's expiry, the next authenticator code. Both reset before each test. `AccountSecurity` has the helpers: confirm an address from its emailed link, turn two-factor on, make the next code as an app would, and sign in in two steps. `SmtpEmailTransportTests` sends through the real transport to Mailpit in Docker.

**End-to-end tests** (`MedApp.E2ETests`) drive the React app in Chromium, against the AppHost locally and the production image in CI. They derive from `E2ETest`.
- Open pages with `OpenAsync`, which waits until React has taken over the server-rendered page; typing or clicking before then is lost.
- Find elements as people do: `GetByRole` and `GetByLabel`, with their accessible names.
- Make the data a journey needs through the API (`Api`), with unique synthetic names (`E2EData.UniqueName`), and register every clean-up with `Data.OnCleanUp`. Rely on nothing you didn't make, except the signed-in account and the default stage definition. The E2E account must be an admin.
- Give accounts a test makes a password from `E2EData.NewPassword()`, new each run, never one written in the source, and keep passwords out of messages.
- Missing `E2E_USERNAME` or `E2E_PASSWORD` fails the suite in CI (`CI=true`) and skips it locally. With `E2E_TRACE_DIR` set (only `main.yml` sets it), a failed test's Playwright trace is saved there.

## CI

`.github/workflows/main.yml` runs on PRs to `main`, with nine jobs:
- `changes` decides whether this push needs the build and tests. A push that changes only `docs/` (a review document with no fixes, say), on top of a commit whose run passed, with nothing merged into the base branch since that run started, would be tested exactly as that run was (a run tests the PR merged into its base), and nothing that builds or tests reads `docs/`. So `web`, `image`, `e2e`, `helm`, `integration-tests` and `unit-tests` are skipped (a job skipped by its `if` counts as passing a required check), and the run takes under a minute. Everything else runs them all:
  - a new or reopened PR, or a force push
  - a previous run that failed, was cancelled or hasn't finished
  - anything merged into the base branch since that run started (the commits API, by date)
  - any change outside `docs/`, a merge from `main` among them (a file moved in or out of `docs/` counts by both names)
  - a push of 300 files or more (the comparison lists only that many)
  - `changes` failing, since the jobs run unless it says `false`

  It compares the push (the commit before it and after it), not the whole PR, which `paths-ignore` can't do. The run's summary says what it decided and why. A new file under `docs/` that a build or test reads would break this: put such a file elsewhere.
- `web` checks `MedApp.Web`: `npm ci`, `npm audit --audit-level=high` (a high or critical advisory fails it, except the IDs accepted until a date in the step's `ACCEPTED`: see the supply chain rules), lint, type check, a check that the built theme is up to date, Vitest with coverage, and the full production build (`npm run build`: the client, the server rendering bundle and the page server).
- `image` builds the API's image from `MedApp.API/Dockerfile`, as Publish does, without pushing it, so a broken Dockerfile or bundle fails on the PR. It shares the GitHub Actions build cache with Publish. Then Trivy scans it: every finding with a fix goes to code scanning (SARIF), and a critical vulnerability with a fix fails the job. Trivy runs from its own image, pinned by digest (`TRIVY_IMAGE`), never from `aquasecurity/trivy-action`, whose tags were hijacked in March 2026. `web`, `helm`, `unit-tests`, `image`, `integration-tests` and `e2e` are all required checks on `main`.
- `dependency-review` fails a PR that adds or updates a dependency (npm, NuGet, actions) with a known high or critical advisory, and comments on the PR when it does.
- `helm` lints the Helm chart (`deploy/helm/medapp`) in its main configurations (its own SQL Server, kind's values with External Secrets and TLS, an external database, and Azure's values), renders it, and compiles and lints the Azure Bicep (`deploy/azure`). It also renders the cluster services (Traefik, cert-manager, External Secrets and Argo CD) at the versions in `deploy/versions.sh`, with every values file and `--set` value that `deploy/kind/up.sh` and `deploy/azure/bootstrap.sh` give them. After changing one of those values files, run the same `helm template` locally.
- `unit-tests` builds the dev MCP tool (`tools/MedApp.DevMcp`, which isn't in `MedApp.sln`), then runs `dotnet test MedApp.UnitTests` in Release with coverage.
- `integration-tests` runs `dotnet test MedApp.IntegrationTests` in Release, with SQL Server and Azurite in the runner's Docker (Testcontainers).
- `e2e` tests the production image under the chart's restrictions (a read-only root with a writable `/tmp`, every capability dropped, no privilege escalation; one copy, without kind's Valkey backplane). It builds the image itself, reading the cache earlier runs left (it runs alongside the `image` job, so on a cold cache both build from scratch). It starts SQL Server in a step (no file storage, so attachments answer 503 there; no E2E test uploads), on the runner's loopback with a random masked password, migrates with the image's `/app/efbundle`, makes the first admin with `create-first-admin` and a password generated for the run, starts the API on http://localhost:8080, then runs `MedApp.E2ETests` against it. A failed test's Playwright trace is uploaded as the `e2e-traces` artifact. The session cookie stays `Secure`: browsers keep it from `http://localhost`. Both new jobs read the repository only (`permissions: contents: read`).
- `coverage-comment` posts one sticky PR comment with both: .NET classes and React files under 80% line coverage.

What coverage counts (the aim is full coverage of everything with behaviour worth testing):
- **.NET:** handlers, validators, domain logic, Infrastructure services, and the API (controllers, middleware, authentication, server rendering). Excluded: commands, queries, DTOs, repositories, DbContext, migrations, generated code (`obj/`), the Aspire service defaults, and wiring (`ServiceExtensions`, `ApplicationBuilderExtensions`, `Program`), plus `SessionService` and `IdentityTransactions`, which need a real database (the integration tests cover them, but don't count towards coverage).
- **React:** everything in `src/` except generated code, the theme build, test helpers, the thin route files and the browser entry. `npm run coverage` (CI's web job) fails below the thresholds in `vite.config.ts`, set just under the current figures (99% lines, statements and functions, 92% branches).
- New code comes with tests that cover it. Leave a branch uncovered only when it's unreachable or needs a real browser or database, and say so in the PR.

`.github/workflows/codeql.yml` runs CodeQL on PRs to `main`, on pushes to `main` and weekly: C# (built), JavaScript and TypeScript, and the workflows themselves. Results go to the repository's code scanning alerts.

`.github/dependabot.yml` has Dependabot propose weekly updates, grouped (minor and patch together), for GitHub Actions, NuGet, npm (`MedApp.Web` and `tools/ui-parity`) and Docker. It can't read the Dockerfile's `ARG` image tags or `DOTNET_EF_VERSION`, so bump those by hand.

**Supply chain rules:**
- **Pin every third-party action to a full commit SHA,** with its tag in a comment (`uses: actions/checkout@<sha> # v4.4.0`). Resolve the SHA from the tag yourself (`gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, dereferencing an annotated tag), never from a README. Dependabot keeps them current.
- **Give each job only the permissions it needs,** at the job, not the workflow.
- **NuGet audit:** every csproj treats NU1903 (high) and NU1904 (critical) as errors, for transitive packages too, so a newly published advisory fails the build until the package is updated. There's no `Directory.Build.props`, because the Dockerfile copies only the csproj files before restoring.
- **When a gate fails overnight** (an advisory published against a package with no fix yet, or a base image Microsoft hasn't rebuilt), don't switch the gate off. Accept the one known issue for a short, dated time, in the same PR as a `docs/todo.md` entry it expires with:
  - **NuGet:** `<NuGetAuditSuppress Include="https://github.com/advisories/GHSA-…" />` in an `ItemGroup` of only the affected csproj, with a comment giving the reason, the date it was added and the date to review it (at most 30 days).
  - **npm:** an `overrides` entry in `MedApp.Web/package.json` that forces a fixed version of the transitive package, if one exists. If none does, add the advisory's GitHub ID to the `web` job's audit step (`ACCEPTED`, space-separated), with a comment saying what it is and why it's safe to wait, and set `ACCEPTED_UNTIL` at most 30 days on. Only those IDs pass; any other high or critical advisory still fails, and after that date the audit counts them all again by itself.
  - **Trivy:** a `.trivyignore` file at the repository root, one line per CVE with an expiry (`CVE-2026-12345 exp:2026-12-31`) and a comment above it with the reason, passed to both Trivy runs (`--ignorefile /out/.trivyignore`). Trivy stops ignoring it on that date, so the gate fails again if nothing has changed.

`.github/workflows/e2e.yml` runs the E2E suite by hand against an app already running somewhere (a URL you give it), with the credentials in the `E2E_USERNAME` and `E2E_PASSWORD` repository secrets (an admin account). **Those secrets don't exist yet: create them for a known deployment before using it.** Without them, the run fails rather than skips (in CI, missing credentials fail the suite; locally they skip it). It saves no traces, as a trace records the real credentials.

`.github/workflows/publish.yml` runs on every push to `main` except docs-only changes, so it runs after each merge:
1. `image` builds the API's image and pushes it to GHCR (`ghcr.io/aliator/medapp-api:<commit>`). It then makes an SPDX SBOM of the pushed image (`anchore/sbom-action`, also uploaded as the `medapp-api-sbom` artifact) and attests both the build provenance and the SBOM (`actions/attest`), pushed to GHCR beside the image. It's the only job with `id-token: write` and `attestations: write`. Check an image with `gh attestation verify oci://ghcr.io/aliator/medapp-api:<commit> --repo Aliator/MedApp`. Nothing checks the attestations before a deploy yet.
2. `deploy-kind` records that commit on the `env/kind` branch, with the tag in `deploy/argocd/kind-image.yaml`: a commit whose files are exactly `main`'s plus that file, except `.github/workflows`, which keeps the branch's own (`.github/scripts/deploy-to-env.sh`). Argo CD deploys that branch (`deploy/argocd/README.md`). `azure` does the same for `env/azure`, once Azure is set up. The two deploy jobs need only `image`, so one failing doesn't stop the other. Started by hand on another branch, it builds and pushes the image but deploys nothing. A re-run of an older run doesn't move a branch back.

When you've merged, its run is the deploy. Check it the same way as CI.

### Checking CI on PRs you opened or pushed to

After you open a PR, or push to the branch of one you opened, check its CI result before you call the work done. Don't stop at "pushed".

**Don't block the user while CI runs.** Hand steps 1–3 to a background subagent (in Claude Code, the `Agent` tool; it notifies you when it's done). Tell the user it's watching CI, and carry on with whatever they ask next. Give the subagent the branch, the pushed commit SHA and this section to follow. Rules for the subagent:
- **Read-only:** no edits, commits or pushes. Its job is to report, not to fix.
- **Waiting:** poll about every 30 seconds using the harness's wait mechanism (a background command or monitor; foreground `sleep` may be blocked). The workflow usually takes about 9 minutes, and under one for a push of only `docs/` after a passing run. Give up after 15 minutes and report the run as still pending, with its URL.
- **One PR each:** a watcher waits for one PR's run, never several, so a PR that's ready isn't held up by another's CI.
- **Report:** return the run URL, the result, and for a failure the failing step, the error, the cause, whether it's already broken on `main`, and a proposed fix as an exact diff.

When the subagent reports back, do step 4 yourself, and don't interrupt the user's current task to do it. Mention the result at the next natural break, or right away if it failed.

1. **Find the run for your commit.** The repo is public, so the GitHub REST API works without auth. Use `gh` instead if it's installed and logged in (it may not be).
   - Runs: `GET https://api.github.com/repos/Aliator/MedApp/actions/runs?branch=<branch>`. Only trust a run whose `head_sha` matches the commit you just pushed. A new run can take a minute or so to appear, and until then the API returns the previous run. If you don't see a matching run, say the check is still pending and check again later. Don't report the old run's result as the new one.
   - Then read its jobs (`/actions/runs/<run_id>/jobs`) to see each step's `conclusion`.
2. **If it passed**, say so in one line, and mention any coverage problems from the sticky PR comment, such as handlers, validators or React files under 80%.
3. **If it failed**, find the cause before reporting.
   - Note which step failed. A failure in "Set up job" means the workflow itself is broken (bad action ref, runner image), not the code.
   - Read the annotations with `GET /repos/Aliator/MedApp/check-runs/<job_id>/annotations`. Full job logs need auth, so read them through `gh run view <run_id> --log-failed` when `gh` is available.
   - Reproduce only the failing tests locally, the way CI runs them: `--configuration Release` with a `--filter` for those tests, or the `web` job's npm script with the failing files.
   - Check whether the failure is yours or already broken on `main`, for example when the workflow file is unchanged by your branch.
4. **Prompt the user before fixing.** Tell them which step failed and the error, the cause, whether your change caused it or it was already broken, and the fix you propose with the exact diff. Wait for them to approve before you commit or push it, unless they've already told you to fix it. After pushing a fix, check the new run again (step 1).

## Git workflow

- Branch from `main` as `feature/<name>`, and merge back through a PR to `main`.
- Commit messages are short, capitalised and past tense, for example "Updated patient task routing", "Added get all methods for tasks".
- Never commit `bin/`, `obj/`, `.idea/` or `*.DotSettings.user`.

### Effort for each stage of a change

The user wants each change made in three stages, each at its own reasoning effort (in Claude Code, the Agent tool's `effort`):

| Stage | Effort | Who does it |
|---|---|---|
| **Thinking:** understanding the task, reading the code, the design and the plan | **xhigh** | The main session (its effort setting is `xhigh`). |
| **Implementation:** writing the code, tests and docs to the plan | **high** | A subagent with `effort: "high"`, given the plan, the files and the conventions. The main session checks its work (a build, the tests for what changed, a read of the diff) before calling it done. |
| **Review:** a fresh, adversarial look at the whole PR | **xhigh** (**high** for a small change) | A subagent with `effort: "xhigh"` that wasn't told the author's conclusions, as part of every merge (below). |

**Small changes are lighter:**
- **What counts:** a fix or tweak in a few files, with no new endpoint, table, migration or dependency, and nothing that touches sign-in, security, privacy rules, patient data, clinical safety, CI or deploying. When unsure, it isn't small.
- **Implementation:** the main session makes it itself. A subagent's cold start (reading this file and the code afresh) costs more than a change this size.
- **Review:** at **high** (`effort: "high"`), not xhigh. Measured on recent small changes, the xhigh review was the longest stage, at a quarter to a third of the time from asking to deployed.
- Small, mechanical edits (a typo, a one-line config change) need no stages at all until they're shipped.

### "Merge it" or "ship it": the full merge flow

**Only run this when the user explicitly asks you to merge**, for example "merge it" or "ship it" (they mean the same). Without that, stop at committing or at an open PR, as usual. Opening a PR or seeing CI pass is not permission to merge.

**The medical device decision:** a change that adds calculations, scores, dose checks, decision support, triage or prioritising, alerts from clinical values, or medical claims must update `docs/clinical-safety/intended-purpose-and-device-decision.md` before it merges.

When the user says to merge, do every step, in order, without stopping to ask again:
1. **Commit** any outstanding changes on the feature branch (branch from `main` first if you're on it), and push. New scripts need their executable bit set in git (`git update-index --chmod=+x`), since this checkout doesn't track file modes.
2. **Open a PR** to `main` if there isn't one already. If there is one, reuse it.
3. **Review the PR at xhigh** (high for a small change: see [Effort](#effort-for-each-stage-of-a-change)), with a subagent (`effort: "xhigh"`, or `"high"`), and write it up as a review document:
   - **A small change's reviewer checks it's small:** a review at high starts by saying whether the change meets the Effort rule's definition of small. If it doesn't, it's reviewed again at xhigh.
   - **What to review:** the PR's whole diff against `main` (`git diff main...HEAD`), its description, and the code around the changes. Give the reviewer the PR and the files, not your own conclusions, so its view isn't anchored on yours.
   - **What to look for:** correctness, security, data loss, operational and deploy risks, judgement (was this the right design?), consistency between docs and code, whether the governance documents in `docs/governance/` are still true (a change to what personal data is held, who can see it, where it goes or how long it's kept must update them in the same PR), and whether the tests really test the change. Every finding needs file:line evidence, a concrete failure scenario, a severity (critical, high, medium, low), a confidence, and a suggested fix.
   - **How the reviewer checks:**
     - by reading the code
     - for anything it doubts, with the narrowest test: a filtered unit test run, or Vitest on named files
     - it starts no Docker, AppHost, kind cluster or browser, and runs no full suite: CI does that, and step 4 waits for it
   - **The document:** `docs/reviews/pr-<number>-<short-name>.md`. Commit it to the branch and push, so it's merged with the PR. Write it in the format below (see [Review document format](#review-document-format)).
   - **If it finds anything high or critical, stop.** Don't merge. Check those findings yourself against the code, then report them to the user with the fixes you propose, and wait. Medium and low findings are recorded in the document and don't block. Mention them when you report the merge.
4. **Wait for the workflow** run whose `head_sha` is the last pushed commit (the one with the review document) to complete (see [Checking CI](#checking-ci-on-prs-you-opened-or-pushed-to)). In this flow, waiting is the point, so wait for it rather than moving on. When that push is only the review document, after a passing run, it skips the build and tests (the `changes` job) and finishes in under a minute; fixes from the review, or a merge from `main`, run everything again.
   - **If it fails, stop.** Don't merge. Report it and propose a fix, as in step 4 of the CI section.
5. **Merge** the PR with a merge commit (`gh pr merge <n> --merge`), matching the existing "Merge pull request #N" history. If the local checkout has uncommitted changes, stash them first, or the merge's local step fails after the merge on GitHub has already happened.
6. **Delete the branch**, both on GitHub and locally (`--delete-branch` handles both).
7. **Pull `main` locally:** `git switch main` then `git pull`, so the working copy is up to date and ready for the next change. Then confirm the merge commit and that the working tree is clean.
8. **Check the deploy:** each merge runs the Publish workflow, which deploys through the environment branches (`deploy/argocd/README.md`). Check that its run for the merge commit succeeded, as with CI. A green Publish run only means `env/kind` moved, not that the cluster took it.
   - **If the kind cluster is running,** check that Argo CD's `medapp` Application is **Synced and Healthy** at that commit (`kubectl --context kind-medapp -n argocd get application medapp`).
   - **Don't start the cluster just for this.** When it next starts, Argo CD catches up with `env/kind` by itself. A change to how MedApp is deployed was already tried on kind before merging ([Commands](#commands), Testing a change).
   - A change that adds a secret store entry needs `deploy/kind/up.sh --argocd` run against the existing cluster before it merges (`deploy/kind/README.md`).

### Review document format

Write each review so someone who didn't make the change can follow it quickly: short sections, bullets with bold lead-ins, short sentences, and any term that isn't obvious explained the first time it appears. Keep the depth in the findings and the detail at the end.

Start with the PR's link and branch, the commit reviewed and the `main` it was compared with, the date, and whether any finding is high or critical. Then use these sections, with these names, in this order (a review may add sections, but not rename or drop these):
1. **Summary:** what the PR does, in one or two sentences.
2. **What changed, and why:** each change, what it does here, and why it was needed.
3. **Design choices:** for each real choice, the main alternative and the trade-off, including what the chosen option is worse at.
4. **How it was checked:** tests, builds, screenshots and anything run by hand, with the results.
5. **Findings,** most severe first. Each has:
   - a severity (critical, high, medium or low, as graded in `docs/reviews/README.md`) and a confidence
   - what could go wrong, as a concrete scenario
   - the evidence (`file:line`)
   - the fix, and what happened to it (fixed in the PR, documented, or left as a to-do)

   With no findings, say so.
6. **Remaining risks:** what's still weak or left to do after this PR.
7. **Detail** (optional): diffs, longer reasoning, and anything else only an engineer needs.

Personal preferences for how reviews or explanations are written belong in a contributor's own git-ignored `CLAUDE.local.md`, not in this file.
